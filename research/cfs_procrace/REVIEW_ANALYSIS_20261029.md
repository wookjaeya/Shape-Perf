## 2. CR 판단에 대한 분석

### 2.1 그대로 받을 만한 것

1. **우선순위 재정렬** (CR 결론, §13.1).
   - 다음 과제는 판정의 타당성, 정상 경로의 오경보, C5에서 공통 엔진을 그대로 쓸 수 있는지다. 외부 실행 비교는 조건부로 둔다.
   - PD28 §3("process-level 방법끼리 비교, 실행 불가·범위 밖·미탐지 구분")과 충돌하지 않는다. 그 비교를 언제 할지를 좁힌 것이다.
2. **발생 비교의 짝짓기 수정이 먼저**(§6.1). 앱 귀속을 결과로 내세우는 연구에서 다른 앱의 호출을 같은 발생으로 맞추는 것은 비교 신뢰를 직접 깎는다.
3. **83/86과 76의 해석**(§5). 이미 PD28 §3·STATUS §3.1과 같다. 76을 "독립 증거 76건"으로 쓰지 않는다는 점도 같다.
4. **H4 재구성**(§11.8): 개념, 적용성, 실행의 셋으로 나누고, 실행은 앞의 둘이 성립할 때만 한다.
   - 결과 기록도 여러 축으로 나눈다(§11.6): 접근·실행 / 대상 도달 / 사건 표현 / 결과 / 의미 확인 / 적용 형태 / 설명.
   - 지금 H4 문서의 다섯 범주보다 정확하다. 특히 "목표 경로 미도달"과 "유보"를 미탐지에서 떼어 낸다.
5. **C5는 계측 경로로 먼저, F0 대조는 필요할 때**(§9.4). STATUS §5 결정 3의 선택지 중 하나와 같다. 다만 C5의 선행 작업에 ELF32 B′를 넣어야 한다.
6. **수정 후 판의 보류 지점**(§9.8). 6.4.2에서 부모를 잠금 안에 세우고 자식의 `GetAppID`를 기다리면 정체가 생긴다. 이것은 원 race가 아니라 제어 계획의 결함이다. 판마다 잠금 문맥을 반영해 계획을 따로 만들어야 한다.
7. **A8 갱신**(§9.7). `OS_TaskGetId` 0 → 잘못된 AppID 경로는 OSAL·glibc 소스 순서로는 생기지 않는다. 기본 경로는 `CFE_ES_ERR_APPID` 실패다. 잘못된 AppID 경로를 만들려고 낡은 표 상태를 임의로 넣지 않는다.
8. **회수 기능의 범위**(§10). 구현 완료와 cFS 실사용 검증을 구별한다. W5는 런타임 0.3.0 빌드여서 회수 검증으로 세지 않는다. STATUS도 그렇게 적었다.
9. **기대 판정의 독립 근거**(§13.2). 프로필이 선언한 조건을 정답으로 다시 읽으면 자기 검증이 된다. 원 이슈·코드·실행 사실에서 기대 판정을 따로 세우는 연결표가 필요하다. 지금 저장소에 없는 산출물이고, 가장 큰 보완점이다.

### 2.2 받되 고쳐 적용해야 하는 것

- **CR §13.5 단계 A**: 기록이 없어져서 "기존 결과 파일 재대조"를 할 수 없다.
  - 고쳐 적용하면: 먼저 비교기를 고치고 도구 시험을 붙인다. 실제 기록 재대조는 다시 만드는 실행에서 한다.
  - 그 실행 캠페인은 처음부터 여러 목적을 함께 맡도록 설계한다. 단계 A의 재대조, 단계 D의 정상 대조, §7.3의 R2 구간 질문(초기화 구간 대 OPERATIONAL 뒤 구독·종료 구간)이다.
- **CR §9.3 큐 값**: 구성에서 계산 근거가 있으면 구현자가 값을 제안·기록할 수 있다고 한다.
  - `CONDITIONS_POLICY.md`와 맞추면: 값은 빌드 소스 상수에서 유도하고 인용하면 레퍼런스 기반이다("구성에서 유도한 값"). 따져 볼 상수는 파이프 깊이, 메시지 크기, 동시에 만드는 큐 수, `RLIMIT_MSGQUEUE` quota이고, TO_LAB도 포함한다.
  - 반면 IPC namespace 안에서 한도를 올린다는 방식의 채택과 D19 기준과의 관계는 PI 결정으로 남는다.
  - CR이 지적한 대로 32는 아직 전체 빌드의 검증된 최대값이 아니다. TO_LAB을 읽지 않았다.
- **CR §8.2 남은 위치 의존**(SCOPE, 여러 짝 후보의 선택, Observe의 마지막 writer).
  - R2 새 F0에서 TO_LAB 사건이 명령 재시작 뒤 종료 중에 기록됐다. 그래서 SCOPE 문제는 지금 기록에도 해당한다.
  - 회귀 시험은 합성 도구 시험으로 먼저 하고, 실제 확인은 새 기록에서 한다.

## 5. 결정이 필요한 것

1. **원 기록·빌드의 보존 위치.** 이 세션 컨테이너는 사라질 수 있음이 확인됐다. 선택지:
   - (가) 실행 묶음마다 압축한 원 기록과 해시 목록을 이 저장소(또는 별도 저장소)에 넣는다. GitHub의 파일당 한도(100 MB)를 넘지 않게 나눈다.
   - (나) 사용자 쪽 저장소(컴퓨터 폴더 등)로 옮긴다.
   - (다) 기록은 다시 만들 수 있다고 보고, 결과 문서의 요약과 해시만 남긴다.
   - 권고는 (가)다. 큰 빌드 산출물은 넣지 않고, 다시 빌드할 수 있게 명령·입력 해시를 남긴다.
2. **CR의 평가 계획 채택 여부.** CR은 검토 권고다. §2.1의 아홉 가지와 §2.2의 조정을 작업 기준으로 받아들일지.
3. **`STATUS_20261028.md` §5의 C5 결정 다섯 가지.** CR 반영 뒤 내용은 이렇다.
   - 큐 조건: 방식은 IPC namespace (c). 값은 이번 빌드 구성에서 유도하고 그 근거를 기록한다.
   - 빌드 host 이탈(DV-H) 승인: 그대로 남는다.
   - F0 비교 경로: CR은 "계측 경로를 먼저 쓰고, F0는 필요할 때"를 권고한다.
   - 보류 지점: 판마다 잠금 문맥을 반영해 정한다.
   - 32비트 회수 방법: 그대로 남는다.
