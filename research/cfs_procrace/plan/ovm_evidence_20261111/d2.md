Two layers, kept apart on purpose. **Layer A** is the pure black box: only controls and outputs the framework itself offers. **Layer B** is the smallest look inside I could not avoid: a generic delay at task creation/entry and a generic API-boundary return trace. Every verdict names its layer.
Check of the angle's premise against the dossiers (rule 2). "The steady state must not depend on init order" is stated by NO framework document: S§D found no sentence on start order. It is a postulate of this method, to pre-register with the PI. Taken literally it is also false for healthy systems (the count of the INFORMATION event "no subscribers" differed 12 vs 17 between two recordings of the same build, K3 R2§11 L6) and blind to R2 (order fixed, "no functional steady-state difference", K3 R2§7, §13). I therefore weaken it to: **the harm-class part of the steady state must not depend on an order the framework leaves open**, and I state where even that is insufficient.

## 1. Definition
- **Units.** Layer A: the `CFE_APP` entries of the shipped startup script. Layer B adds every task spawned in the run.
- **Legal schedule.** The shipped build and tables, started through degrees of freedom the framework leaves open or offers: (a) the shipped script unchanged; (b) entry X removed from the script and started by `CFE_ES_START_APP_CC` with the values of X's own line at a time the tool chooses (same `CFE_ES_AppCreate` as the script, S§E, ES/cfe_es_task.c:763; init order of script apps is open, S§B O1, O5); (c) Layer B only: a bounded delay of a task at its entry or of a creator right after a spawn returns.
- **Harm set Harm(σ)** of a schedule σ, computed from its canonical record at quiescence (section 2):
  - H1 process: abnormal termination, panic, processor reset (S§A2: `CFE_PSP_Panic`, `CFE_ES_ResetCFE`).
  - H2 application: an app the script (or the tool's start command) requested is absent from the ES application list at quiescence, or its exit carries `CFE_ES_RunStatus` in {APP_ERROR 3, SYS_EXCEPTION 4, CORE_APP_INIT_ERROR 8, CORE_APP_RUNTIME_ERROR 9} (S§C, ENUM:116-161).
  - H3 structural loss: a record keyed by stable names (task, SB pipe, SB route, TBL registry entry or its `TableLoadedOnce`, EVS registration, CDS entry; O§f) that exists in the compared schedule and not in this one.
  - H4 error-class signal: an event with `EventType` ERROR 3 or CRITICAL 4 (S§C); in Layer B also an API return with cFE severity bits 11 or a negative OSAL status (S§C).
  - H5 informational: events of type 1 or 2, counters, free syslog text. Never harm.
- **Report.** "A requires B first" is reported iff two legal schedules exist, σ- (A started first, B's start follows by lag d >= 0) and σ+ (B quiescent before A starts), equal in everything else, such that in r of r repetitions each: (1) Harm(σ-) minus Harm(σ+) contains an item of H1-H4; (2) Harm(σ+) minus Harm(σ-) contains no item of H1-H4 (monotone); (3) no repetition of σ+ shows the item. Grade **P** (persistent) if the item is in H1-H3 at the final quiescence, after B was started too; grade **T** (transient) if only H4 remains. Class **V1** (startup violation) if σ- is the shipped baseline itself or d < T_F; class **V2** (tolerated dependency, with measured tolerance d*) if harm needs d >= T_F. Other labels: **V3** order-sensitive, informational only; **N** harm items that differ between repetitions of ONE schedule (nondeterminism, not localized); **X** direction undecided (both differences non-empty); **NC** not controllable in this layer.

## 3. Candidate discovery
- S0 Baseline: k boots of the shipped script. Yields the volatile mask, the baseline harm set (for example a script app absent at quiescence) and N findings.
- S1 Leave-one-out late start L(X), one boot per app X: boot script minus X; at quiescence dump (the **prefix** record: the world without X); START X; at the next quiescence dump (the **final** record: X started last). n boots give, for every ordered pair, one run with X absent while A initializes and one run with A started after everything else.
- Why not permute script lines: the script fixes task creation order only (S§B E8), every new task first sleeps one poll period (E9) and init order stays open (O1); a permuted script does not determine the order of two inits, a late start does. Permutations are therefore not used as evidence.
- S2 Sensitivity: A is order-sensitive iff the harm items keyed by A differ among baseline, final(L(A)) and prefix(L(X)), X != A.
- S3 Provider: if A is unharmed in baseline and harmed in prefix(L(X)), the edge "A requires X" follows directly (control = baseline). If A is harmed in baseline too, the baseline is no control; run L2(A, X) for each X: script minus {A, X}; START A; dump; START X; dump. A harmed in L2(A, X) and unharmed in final(L(A)) gives the edge. Leave-one-out finds AND-shaped providers only.
- S4 Lag probe per edge: script minus {A, B}; START A, wait d, START B. d = 0 imitates two adjacent script lines; d* = smallest d with harm, by bisection between 0 and W. The mirror probe (START B, wait d, START A) gives the head start B needs; harm at head start 0 means that no order of script lines is safe (the C1 reporter saw CF fail with BP started first, K1§1.6).
- S5 (optional, same boots) RESTART X after the final dump of L(X); a harm-class difference afterwards is labelled restart dependence (stale references after cleanup, S§E; K1§4 obs 8). None of the five cases is of this kind.
- **Identity of the shared object.** Layer A does not resolve it: its unit of report is (victim app, provider app). Records are joined across runs by stable names only (O§f); numeric IDs are never compared. Layer B names the object: record every framework API return of the victim's tasks in a harmed and an unharmed run, align per call site, and take the first call whose status class differs; the object is (API of that call, value of its string or ID argument captured at run time). A key that exists only at run time is thereby read where it becomes a plain argument (C1: the table-loaded name is a string at the OSAL boundary, K1§4 obs 4). An ID argument is replaced by the creation call instance that returned it in that run.
- **Actor attribution.** Provider = the unit the tool moved. Victim = the `AppName` key of the differing record (Layer A). This key is derived inside the system from the caller's self-lookup and is unsound when that lookup is wrong (SAMPLE_APP reported as SAMPLE_LIB in both 6.4.x versions, K5§15). Layer B binds thread to application through the creation edge (the creator's app-create call instance, its name argument, the spawn instance, the child's first execution; K5§15 obs 2-4, O§e).

## 4. The oracle
Decision. Given σ- and σ+ of section 1: the order of σ+ is called required, and σ- a violation, iff the H1-H4 difference is one-sided against σ- and reproducible. Nothing else is consulted.
| Harm(σ-) minus Harm(σ+) | Harm(σ+) minus Harm(σ-) | Where harm appears | Output |
|---|---|---|---|
| has H1-H3 | no H1-H4 | baseline, or lag d < T_F | V1, grade P |
| H4 only | no H1-H4 | baseline, or lag d < T_F | V1, grade T |
| has H1-H4 | no H1-H4 | only at d >= T_F | V2 with d* (P or T) |
| has H1-H4 | has H1-H4 | any | X, direction undecided |
| H5 only | H5 only or empty | any | V3 |
| empty | empty | - | no dependence observed |
Why the inference is legitimate:
1. The script is the shipped statement of what must run: "The cFE shall create and start cFE Applications according to the entry in the cFE Startup File" (cES1508.1, S§D). An app the script names and the system does not keep is a deficit against the system's own configuration (H2), not against a rule of mine.
2. Both schedules are ones the framework lets happen: it orders task creation only, not init completion (S§B E8, O1), it documents start by command (S§E), and no document says script order is an init order (S§D).
3. The classes of H1-H4 are the framework's vocabulary, and each instance is classified by the shipped code itself at run time (the `EventType` argument the developer wrote; the run status the app passed to `CFE_ES_ExitApp`).
4. σ+ is an existence proof: this build, with these tables, can deliver the superset state without the error-class signals. Everything except order is equal, so the deficit of σ- is caused by order. "Required order" is shorthand for "the only explored order in which the system meets its own script".
5. Whatever a design does in both orders cancels in the difference: designed probes, designed absences, routine error statuses.
Learned invariants (from passing runs, as the angle asks): (i) the volatile mask from repeated baseline runs; (ii) the reference state = the record of the harm-minimal schedule; (iii) Layer B add-on E2: per call site, "the status class is success" learned from later executions of the same site in the same run; a site whose error-class returns all precede all its successes is a prefix-failure candidate. E2 is not differential and has a lower evidence grade; it exists only because of R2 (section 6).
What is reported when it cannot decide: V3 (only H5 differs); X (two-sided difference); N (varies under one schedule); V2 with d* (harm only beyond T_F); "no dependence observed in the explored family" (not a proof of absence); NC (no control over the units involved).
Two cautions built into the classes. The ES event for an error exit has type INFORMATION (S§C), so H2 uses the app list and the run status, not the event type. Counters and syslog carry no class (S§C), so they never decide.

## 5. Enforcement and feasibility
- Layer A knows the other order can happen in one sense only: it produced it with a framework command. Whether it also happens in plain startup is argued by (i) baseline repetitions that show it, (ii) the lag probe: harm at d < T_F means the provider can be that late inside what the framework still calls nominal startup [I], (iii) S§B O1.
- Layer A cannot show that an order is fixed. It labels core applications NC: stop and restart refuse CORE applications and require `AppState == RUNNING` (own read V/es/fsw/src/cfe_es_apps.c:81-94; S§E), and core tasks are not script entries.
- Layer B recognizes enforcement by perturbation: delay unit X at its entry; if the units that should overtake it do not start or progress until X is released (the creator waits), the order is enforced by synchronization and the pair is closed as "enforced". Reaching the framework's own bound (panic) confirms enforcement and is never counted as harm.
- Artifacts of the intervention and how each is recognized: (a) excess lag: the lag bisection and T_F; a harm that needs d >= T_F is V2, never V1. (b) Barrier semantics: for an app started after OPERATIONAL both wait calls return at once (S§A5 iii; the API header allows the use, "Although it will cause no harm", S§D); any finding whose moved app calls a sync API is flagged "barrier semantics changed" (call sites from the 2a facts; 5 application sites in v7.0.1, S§A5). (c) Command start differs from script start: the canonical diff of the app's own ES record (priority, stack size, exception action, file, entry) between a script start and a command start must be empty; a zero stack size is replaced by a default on the command path (own read V/es/fsw/src/cfe_es_task.c:751-755). (d) Shifted creation serials: IDs are dropped by type. (e) The driver app is present in every run including the baseline. (f) Messages sent while X is absent produce "no subscribers" events, which the framework documents as expected during initialization (S§D) and types INFORMATION: H5. (g) Layer B delays sit at API entry, task entry or spawn return only, never inside an OSAL create (the -35 path, K1§1.5, §4 obs 7). Every delay is a hold with a time cap that releases itself (the runtime has per-point timeouts, R/kairos/docs/event_semantics.md:113-132 [F]); a hold while a program lock is held is taken only under the explicit allow flag of the existing context rule (:168-182 [F]) and is reported as such. "Absorbed" is decided from the record: between hold and release no other unit executed a framework API call that it executes in the unperturbed run.

## 7. False positives and false negatives
False positives. (1) Monitors: HS looks up monitored apps by name and sends an ERROR event the first time one is missing (O§g A4-A6); CS does the same for checksummed apps (A9). In prefix(L(X)) they fire by design. The method reports them, but as grade T (the structure converges after X starts) and, if they need d >= T_F, as V2; a monitor that fires at d < T_F would still be printed as V1/T. (2) Late start of an app that others reach through the startup barrier: flagged (b), not removed. (3) An app whose developer typed a routine message as ERROR. (4) Victim naming through an unsound self-identity (K5§15).
False negatives. (1) Silent channels: a message sent before the subscriber exists returns `CFE_SUCCESS` and is dropped (O§d); an event rejected for an unresolved caller leaves no trace (O§d, obs 6): R2. (2) Harm kept in application memory and exposed by no dump: a C1 variant in which CF kept running without its semaphore would be invisible to Layer A. (3) Framework-internal orders (C3, C5, R2) in Layer A. (4) Interleavings inside two inits: Layer A orders whole inits; the -35 window of K1§1.5 is out of reach. (5) OR-shaped providers and three-party conditions beyond leave-one-out and pairs (C3 needs two publishers late; found only by "X first"). (6) Libraries cannot be started by command (S§E): order O2 of S§B is unexplored. (7) Dependences that need traffic after startup: the steady state is compared without stimulus. (8) Fixed-order premature uses in general: outside the definition.

## 8. Cost and construction
Boots, Layer A, n = script apps, v = order-sensitive victims harmed in baseline, e = edges: k + r x [ n + v x (n - 1) + e x (1 + ceil(log2(W / poll))) ]. C1 build: n = 5 (K1§1.2), v = 1, e = 1, W / poll = 120: k + 17 r for the buggy version, k + 13 r for the fixed one (v = 0). Each boot is bounded by D_boot + 2 W. Restart checks reuse the L(X) boots. Layer B: r x (2 T + S), T = tasks spawned at startup ("X first", "X last"), S = spawn call instances; 2a rows can order the runs (a spawn whose row shows an empty lock set first, K5§9 row C31) but never decide.
Instrumentation. Layer A: none in the system under test; one driver app in the script and host-side collection of dump files and console. The EVS local log keeps only the first `CFE_PLATFORM_EVS_LOG_MAX` = 20 events in discard mode (own read V/evs/fsw/inc/cfe_evs_internal_cfg.h:128, :194) and the text port has no type field (S§C), so events are taken from the driver's subscription to the event message, the local log, and the console text joined on (AppName, EventID). Layer B: entry/return records at the thread-create primitive, at task entry and at framework API returns, plus bounded holds.
State in Kairos. Exists: function entry/return observation on the unmodified binary (R/kairos/docs/observer.md:7-9 [F]); hold control with gates, releases, timeouts and context refusal (event_semantics.md:113-132, :168-182 [F]); record/control modes of the runtime (:210 [F]); P0 thread-create family and actor roots in the 2a facts ([M] relations.txt:17 of the five builds). New: schedule generator (script rewriting, command sequences), driver app, dump collectors for each framework generation (6.4.x layouts differ, S§G), type-driven canonicalizer, differ with the H classes, lag bisection, trace first-divergence differ, E2.

## 10. The weakest point
The method can only see harm that has a framework-visible footprint, and only vary orders the framework lets an outsider vary. On the development set this means that **the black box alone reaches one case of five (C1)**; C2 cannot be evaluated; C3 and C5 need Layer B, which is no longer a black box and inherits the unsolved problems of identity and automatic hold generation; and **R2 is not a violation at all under "determinism is the specification"**, because its order never varies and its loss leaves no trace. E2, which I add for R2, is a second oracle of a different and weaker kind, and nothing in this design proves it keeps false positives low. A second soft spot is the V1/V2 boundary: T_F reuses a framework soft limit for a purpose the framework never stated, and the fixed C1 changes class if that constant is 30000 instead of 1000. Third, C1 itself is caught only because buggy CF happens to exit; a consumer that continued silently would pass.
