**6.1 What S1–S3 imply (inference, not executed).**
- With the default object table and a startup that does not time out, the start of S1 is a single control flow in the ES startup thread. It forces EVS's (B) or ES's and EVS's (M, D) `*_TaskInit` to complete before the SB task is created.
- So the reads in U-SB and U3 run before the store at L126 on every boot. The returned status is `ILLEGAL_APP_ID` every time.
- No allowed schedule of the default configuration produces the publish-before-use order for these callers.
- By roadmap §7.3 this is the row "the startup procedure of this configuration always forces the unready use", i.e. a deterministic initialization-dependency defect.
- Two things remain open before this can be stated as a result:
  - Q1, the ES claim at B;
  - D5, the S7 window, a separate and improbable path that would also affect later callers.

## 7. Required order and its provenance

**Statement.**
- `CFE_SB_AppInit` must store a valid SB AppId (`cfe_sb_task.c` L126 at B) before any task runs an SB API path that emits an event with `CFE_SB_Global.AppId`. For the event to be generated rather than handled as unregistered, SB must also be registered with EVS (L193) first.
- For R2's callers, this means U1 (EVS init) and, at M and D, U2 (ES init) would have to run after SB's AppInit. They do not (§6.1).

**Provenance:**
1. API documentation (fact). The public header for `CFE_EVS_SendEventWithAppID` ([B cfe_evs.h L165-L172](https://github.com/nasa/cFE/blob/fc8c48ad09460ce0277ad2bfcd81d376634aa2c6/modules/core_api/fsw/inc/cfe_evs.h#L165-L172); identical text at L165-L172 in M and D) says:
   - "Note that this function should really only be used from within an API in order to preserve the context of an Application's event. In general, #CFE_EVS_SendEvent should be used." (L165-L166)
   - "The Application ID must correspond to a registered application or core service. For messages outside the context of a registered application (for example early in app initialization or if registration fails) #CFE_ES_WriteToSysLog can be used for reporting." (L169-L172)
   - It lists `CFE_EVS_APP_ILLEGAL_APP_ID` as a return (L196-L200).
   - Inference: the header directs early-init and outside-registration reporting to `CFE_ES_WriteToSysLog`. It does not say how SB-attributed events, emitted on behalf of a caller before SB is ready, should be handled (Q5).
2. Code (fact):
   - an undefined ID gives NULL and then `ILLEGAL_APP_ID` (§4);
   - SB's AppId is undefined until L126 (§4).
3. The issue (fact, with the reporter's hedged cause): "presumably because CFE_SB has not been registered with event services".
   - Inference: code points to the **AppId publication** (L126), not the EVS registration (L193), as what selects `ILLEGAL_APP_ID`.
   - Registration alone would select `EVS_NotRegistered` (L187-L191).
   - The `CFE_EVS_APP_ILLEGAL_APP_ID` comment in `cfe_error.h` ("Application ID returned by #CFE_ES_GetAppIDByName is greater than #CFE_PLATFORM_ES_MAX_APPLICATIONS", [L260-L267](https://github.com/nasa/cFE/blob/fc8c48ad09460ce0277ad2bfcd81d376634aa2c6/modules/core_api/fsw/inc/cfe_error.h#L260-L267)) is outdated relative to the resource-ID code.
4. [R2-analysis] (inferred to be `issuecomment-5588955819`), retrieved in part as search snippets (§1.3; model-mediated, truncated). Its ordering analysis:
   - "SB attributes pipe-creation events to ... itself using CFE_SB_Global.AppId, but that field is only filled in CFE_SB_AppInit (cfe_sb_task.c:138) when the SB task runs."
   - "Whichever core app's init runs before that sees SB call CFE_EVS_SendEventWithAppID with an undefined AppId, which is exactly the error reported here."
   - This is the commenter's code reading, not an execution result (roadmap §1, source fact vs analysis). It agrees with item 2 and with the inference in item 3 that the AppId publication, not EVS registration, selects `ILLEGAL_APP_ID`.
   - Its "deterministic" ("EVS_GetAppDataByID is deterministic in the ID") is about the lookup function and the vacuity of PR #2820, not a classification of R2.

2. **Q2. [R2-analysis] remainder.** Most of the analysis comment, and the CCB comment (whose snippet shows no truncation mark), are retrieved as search snippets (§1.3). Still open: the three elided spans, a verbatim check of the model-mediated text, the confirmation that the analysis comment is `issuecomment-5588955819` and that the CCB comment is dzbaker's, and both exact timestamps (D3). 3. **Q3. Execution check.** Are the per-boot hit sets at U0 (task, AppID, EventID, status) the same on every boot, at B and at D or M? §5 gives lower bounds from code (B: at least 4, all in `CFE_EVS`; M/D: at least 9), not exact counts, so a 4th or later hit at B is expected and is not a race signal. A race signal would be a hit set that differs between boots of the same build and configuration.
4. **Q4. Exact reporter environment.** Which commits, root or user, `OMIT_DEPRECATED`, compiler and gdb versions? None is stated.
5. **Q5. Intended fix semantics.** Should SB events emitted on behalf of a caller before SB is ready be attributed to SB? That would need SB's AppId before SB runs, e.g. assigned at app-record reservation, which is an order guarantee. Or should they be dropped silently (current behaviour), queued, or logged to syslog? References for the options, none of them a decided fix:
   - The API header directs reporting "outside the context of a registered application (for example early in app initialization or if registration fails)" to `CFE_ES_WriteToSysLog` (cfe_evs.h L169-L172, §7). It does not address SB-attributed events emitted for a caller before SB is ready.
   - The [R2-analysis] snippet proposes two fixes: "have SB resolve its AppId lazily on first use (a one-line check in the event path)", or "have ... CFE_SB_EarlyInit record it since ES already knows the SB app id at that point". The second, as excerpted, does not match the code (inference, §8 caveat).
   - The issue is "Tracked internally" by the CCB (CCB comment); no fix is merged.
6. **Q6. Mission reordering.** At M and D the order is a mission-level CMake list. Does any reference require es and evs before sb? The cFE comment says only that the list order is the init order.
7. **Q7. Relation to C3.** In C3's fixed 6.4.2 code the same residual path affects EVS (C3.md §8.3). Should R2 and C3 share one "SB AppId before publication" pattern in the paper's counting, or not (roadmap §9.3: C3 and R2 share the SB-readiness dependency and are "not treated as fully independent generalization cases")?
8. **Q8. Comment-date precision.** The date `2026-09-08` for `issuecomment-5588955819` rests on the comment-ID adjacency to `issuecomment-5588956244`, on the issue's last update, and on the snippet text ("I opened #2820 ...
