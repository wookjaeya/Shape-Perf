# g_fw_startup — cFS framework model, part A (startup, enforced orders, failure vocabulary, guidance, late start, quiescence)

## Ten-line summary
1. Chain: `main` -> `OS_Application_Startup` (PSP) -> `CFE_ES_Main`; one thread runs all of `CFE_ES_Main` and is the ONLY writer of `CFE_ES_Global.SystemState`.
2. Core start is two-phase: every `EarlyInit` in object-table order, then one task per core app; after each task ES waits until ALL used app records are `RUNNING` (30000 ms, else panic).
3. Core order is NOT constant across versions: v7.0.1 tree = ES, EVS, SB, TBL, TIME (generated from `MISSION_CORE_MODULES`); the two C1 bundles (v7.0.0-rc4+dev) and 6.4.x = EVS, SB, ES, TIME, TBL. Read it from the build.
4. Startup script: one thread, file order. `CFE_LIB` init runs synchronously in that thread; `CFE_APP` returns right after task creation, so app inits are concurrent with each other and with later entries.
5. `SystemState` advances CORE_READY -> APPS_INIT -> OPERATIONAL on SOFT 1000 ms timeouts; OPERATIONAL does not prove that every app finished init.
6. `CFE_ES_WaitForStartupSync` marks the CALLER `RUNNING` at entry, returns void, and returns on OPERATIONAL or on its own timeout; it gives no guarantee about any particular resource of any other app.
7. Failure vocabulary readable from values: `CFE_Status_t` severity bits 31-30 (00/01/11), OSAL status sign, EVS `EventType` argument (1..4), `CFE_ES_RunStatus` constants. NOT readable: `CFE_ES_WriteToSysLog` (free text), EVS port text (no type field).
8. Documents: no sentence found that says applications must not assume a start order; the Application Developers Guide never mentions the sync APIs (0 hits). Guidance exists only as API header notes and config comments.
9. Late start/stop/restart/reload are first-class ES commands (codes 4/5/6/7); command start uses the same `CFE_ES_AppCreate` as the script; stop deletes the app's OSAL objects (tasks, queues, semaphores, mutexes, timers, streams, modules) and memory pools and calls the EVS/SB/TIME/TBL cleanup callbacks (SB pipes, EVS registration, TIME sync callback, TBL access).
10. Quiescence: with SCH_LAB/TIME/ES background task there is periodic activity forever; "startup finished" = `SystemState == OPERATIONAL`, visible as a syslog line; `cfe_es_task.c` refers to `SystemState` only at :134.

### A3. Startup script
- File choice: volatile file first on processor reset, else the path passed to `CFE_ES_Main`; defaults `/ram/cfe_es_startup.scr`, `/cf/cfe_es_startup.scr`. [F] ES/cfe_es_apps.c:115-210; CFG:366,381; V/cfe/docs/src/cfe_es.dox:116-121.

## B. Framework-level happens-before a method may assume (v7.0.1), and what is open
Enforced:
- E1 Every core `EarlyInit` completes, in table order, before any core task is created. [F] ES/cfe_es_start.c:751-773 before 775.
- E2 Core task i has finished its `TaskInit` and reported `RUNNING` before core task i+1 is created; otherwise the system panics. [F] :810,835-846. Exception: ES reports `RUNNING` even after a failed init (A2).
- E3 The core order is the order of `CoreObjectTable` of THAT build (A2, G). Do not hard-code it.
- E4 No script entry is processed before all core apps are `RUNNING` and `SystemState == CORE_READY`. [F] :188,194,201.
- E5 Core tasks do not enter their command loops before `SystemState >= CORE_READY` (or their 30000 ms wait expires). [F] ES/cfe_es_task.c:134-157 and the four other task files (A2).
- E6 Script entries execute in file order in one thread. [F] ES/cfe_es_apps.c:222-326.
- E7 A library's init function has returned before any later script entry is parsed, hence before the task of any app listed later is created. [F] :1016, 313.
- E8 For a `CFE_APP` entry, module load and `OS_TaskCreate` are finished before the next entry is parsed (task creation order = script order). [F] :841-854.
- E9 An app's entry function is called only after its task record has `AppId` and `EntryFunc`, and after at least one 50 ms `OS_TaskDelay`. [F] :573-596.
- E10 `APPS_INIT` and `OPERATIONAL` are set only after the whole script was parsed. [F] ES/cfe_es_start.c:201-234.
Left open (no framework mechanism):
- O1 Relative order of the init code of two script applications (concurrent; depends on scheduling and on the priorities written in the script). [F] ES/cfe_es_apps.c:427,848-854
- O2 Init of an application versus the init of a library listed LATER in the script (library init runs in the ES main thread while earlier apps run). [I from E6-E8]
- O3 Whether all apps finished init when `APPS_INIT`/`OPERATIONAL` is set (soft timeouts). [F] CFG:868-870
- O4 Order between core command loops and script apps after `CORE_READY`. [I]
- O5 When an application is started, stopped, restarted or reloaded by command relative to everything else (section E). [F]
- O6 Effect of priorities and of task-creation semantics on the actual interleaving. [U] not examined in this part.

## H. Document-versus-source contradictions found
1. API/cfe_es.h:441-442 says the `CFE_ES_WaitForStartupSync` timeout "must be at least 1000. Lower values will be rounded up." The v7.0.1 source does no rounding (ES/cfe_es_api.c:616-619). The rounding exists in 6.4.1 (X1/es/cfe_es_api.c:685-688). The header text is stale.
2. cfe_es.dox:151-152 says Exception Action "0 = Do a cFE Processor Reset, Non-Zero = Just restart the Application". The script comment (V/cfe/cmake/sample_defs/cpu1_cfe_es_startup.scr:18-19) and the code (ES/cfe_es_apps.c:413-422; ENUM:65,70: `RESTART_APP = 0`, `PROC_RESTART = 1`) say the opposite.
3. cfe_es.dox:156-157 says "the ES Application first looks for the volatile startup script"; in the code the script is processed by the `CFE_ES_Main` thread, not by the ES core task (ES/cfe_es_start.c:201).
4. Config comment names the core apps "(ES, SB, EVS, TIME, TBL)" (default_cfe_core_private_internal_cfg.h:50); this is not the creation order of any tree examined.
5. Project case notes agree with the source on the v7.0.1 order (R/cases/C3.md:572,600; R/cases/R2.md:49) [F]. The order "EVS, SB, ES, TIME, TBL" quoted in several places holds for 6.4.x and the C1 bundles only.

## I. Observations a designer should know (not a design)
- The only framework-enforced happens-before among script applications is task CREATION order and library-init-before-later-entries. Everything about init COMPLETION between two script apps is open (B).
- The framework's own "ready" notion is self-declared: `RUNNING` is set by the app calling an API, not by ES observing anything.
- Framework-level reference values exist for waits: 50 ms poll, 1000 ms soft script timeout, 30000 ms core timeout, 5 x 1000 ms kill timeout. They are configuration macros of the build under test, so a tool can read them from the build instead of inventing thresholds.
- Three channels carry a machine-readable class (status severity bits, OSAL sign, EVS `EventType` argument); syslog and the EVS text port do not. Two caveats: timeout/empty statuses carry the error class, and ES reports an `APP_ERROR` exit with an INFORMATION event.
- The framework documents that event floods ("No Subscribers" etc.) are expected during system initialization (D), so a failure-class observation at startup is not by itself evidence of a violation.
- Late start and restart are framework operations with a fixed, documented cleanup set (E); they give a framework-level argument for considering "X starts last" and "X restarts" as schedules.
