## 0. Status, and the decisions I need from you

### 0.1 Interim conclusion

1. **The bug is located in released code. The reported mechanism matches the code (fact).** cFE **6.4.0** and **6.4.1** do the following in `CFE_ES_AppCreate`:
   - release the ES shared-data lock just before `OS_TaskCreate` (`SF-6.4.1:cfe/fsw/cfe-core/src/es/cfe_es_apps.c#L610-L614`);
   - re-take it afterwards (`#L637`);
   - only then write the new task's `TaskTable` entry: `RecordUsed` at L649, `AppId` at L651.

   `CFE_ES_GetAppID` (`SF-6.4.1:.../cfe_es_api.c#L846-L871`) returns `CFE_ES_ERR_APPID` when that entry is not yet `RecordUsed`.
2. **The window was introduced and later fixed at known release boundaries (fact).**
   - Introduced: MKS revision 1.26 (2014-09-05, acudmore). Its log says "remove big shared data lock".
   - Before that, 6.3.2 holds a single lock from L429 to L638, across `OS_TaskCreate`.
   - Fixed: in **6.4.2** (tarball dated 2015-07-13), the lock is held from L571 to L669, across `OS_TaskCreate` and the registration. This matches the GitHub milestone "6.4.2" of #72.
   - No public commit holds the fix. Only the release-level diff 6.4.1 → 6.4.2 does (§8).
3. **GitHub tag `v6.5.0a` does not contain the pre-fix code (fact).** It holds the lock from L629 to L737 across `OS_TaskCreate`. So **no git revision on GitHub contains the bug**; it exists only in the 6.4.0 and 6.4.1 SourceForge tarballs.
4. **The two comments the roadmap cites ([C5-fix] `#issuecomment-536673810` and [C5-context] `#issuecomment-536673820`) were not retrieved.** The issue has 9 comments. Their text is blocked for this session (§14). The roadmap's statements about them stay **unverified**.
   - The only public text near [C5-context] is the MKS log line: "Locking shared data at several points now to give other apps a chance to run". It says nothing about a watchdog.
5. **Current code uses a different mechanism. A possible residual window remains (inference, not verified).**
   - Since 2020 (`0749d692`), `OS_TaskCreate` again runs outside the lock. A wait loop in the new task's entry wrapper replaces lock scope.
   - Since `58abd38d` (2021-02-02) that wait checks only the **task** record. `CFE_ES_GetAppID` also needs the **App** record, which leaves RESERVED only in a later, separate critical section (`CFE_ES_AppCreate` L861–L869 on main).
   - See §9. I did not run anything to confirm it is reachable.

> When starting an application, CFE ES calls "CFE_ES_UnlockSharedData()" before OS_TaskCreate(), then calls CFE_ES_LockSharedData() again to perform several more updates to the global table after the task ID is obtained.
>
> This unlock-relock opens up an opportunity for the child thread to read the shared table data before it is fully populated.  This can cause many problems.  One specific one is that CFE_ES_GetAppID() (which many tasks call very early in their init procedures) will fail, which can have a serious snowball effect.
>
> Note that the initial core app creation (CFE_ES_CreateObjects) and child tasks (CFE_ES_CreateChildTask) keeps the global lock for the entire procedure, so these are safe.

## 4. Resource and its publication site

### 4.1 Resource

The resource is the ES task-registration entry `CFE_ES_Global.TaskTable[TaskId]`, which links the calling OS task to its cFE application. Its fields are `RecordUsed`, `AppId`, `TaskId` and `TaskName`. The index `TaskId` is the OSAL task ID returned by `OS_TaskCreate`; in OSAL 4.1.1 that is an array index.

Readers find it through `OS_TaskGetId()`. It is shared by:

- the creating ES context: the `CFE_ES_Main` startup thread for script-started apps, or the `CFE_ES` task for Start/Restart/Reload (F8);
- the newly created app main task.

Secondary shared fields written in the same window (6.4.1):

- `AppTable[i].TaskInfo.MainTaskId`. OSAL writes it through the pointer passed to `OS_TaskCreate` (OSAL 4.1.1 posix `*task_id = possible_taskid`, [`osapi.c#L690`](https://github.com/nasa/osal/blob/2f1fdb0c89523ba865dda65bbf599671a7a79fa3/src/os/posix/osapi.c#L690)) while the ES lock is not held. **Inference:** this is an unsynchronized write to the shared table.
- `AppStartupCounter` (L670). `CFE_ES_RunLoop` decrements it on the app's first RUN (`cfe_es_api.c#L593`).

### 4.2 Publication site at the buggy revision (6.4.1; same lines in 6.4.0)

- **Write:** `SF-6.4.1:cfe/fsw/cfe-core/src/es/cfe_es_apps.c#L649` (`RecordUsed = TRUE`), `#L651` (`AppId = i`), `#L652` (`TaskId`), `#L653-L655` (`TaskName`).
- **Becomes usable by other tasks** (lock-protected readers): at the unlock, `#L673`.
- **The new task is runnable before this:** from `OS_TaskCreate` (`#L614`) onward. In OSAL 4.1.1 posix, `pthread_create` runs at [`osapi.c#L645`](https://github.com/nasa/osal/blob/2f1fdb0c89523ba865dda65bbf599671a7a79fa3/src/os/posix/osapi.c#L645-L648), before OSAL even returns the ID (L690).
- **The lock is free during that interval:** released at `#L610`, re-taken at `#L637`.

6.4.0 and 6.4.1 `CFE_ES_AppCreate` are byte-identical (`diff` of the function body empty), so the same line numbers apply to `SF-6.4.0`.

### 4.3 No GitHub permalink at the buggy revision

The nasa/cFE git history starts with `26ffd61d` (2017-06-29) and `792f5e35` "Add 6.5.0a from Sourceforge release". Every git revision of `CFE_ES_AppCreate` up to `0749d692` holds the lock across `OS_TaskCreate` (F10, F11). The buggy-revision references are therefore the SourceForge tarball paths above, with sha256 in §15.

## 7. Required order and its provenance

**Statement.** For the main task T created by `CFE_ES_AppCreate`, the creator's registration of T must complete and be released before T's first read of that entry. The registration is `TaskTable[TaskId]` with `RecordUsed=TRUE` and `AppId=i` (6.4.1 L649–L651, released at L673). The first read is `CFE_ES_GetAppID` / `GetAppIDInternal`, or any API that uses them.

Violation is observed as `CFE_ES_GetAppID` returning `CFE_ES_ERR_APPID` (or `RunLoop` returning `FALSE`) for a task that ES is about to register. **A new task merely running before registration is not itself the violation** (roadmap §2.2).

**Provenance:**

1. The issue body: "opportunity for the child thread to read the shared table data before it is fully populated … CFE_ES_GetAppID() … will fail" (F1).
2. The API semantics in code: GetAppID fails unless the entry is `RecordUsed` (F5).
3. The fix enforces exactly this order for lock-protected readers (F9).
4. A later maintainer comment states the same requirement: "potential race condition if the real task code starts and calls … any other function that depends on having an AppID context, before its fully registered in the global app table" (`0749d692` L500–L506, F11).
5. The sample app calls GetAppID-dependent APIs first thing in init (F6).

**Possible residual window (inference; not verified, see D4).**

- On main, the steps run in this order:
  1. `CFE_ES_StartAppTask` creates the task outside the lock ([`L664`](https://github.com/nasa/cFE/blob/12cb84fc3ef22e584d94dba571e0c4f9a59397cb/modules/es/fsw/src/cfe_es_apps.c#L664-L722)).

This fails while the App record holds `RESERVED`.
- Since `58abd38d`, `CFE_ES_GetTaskFunction` checks only the task record. Before that, `0749d692` checked `GetAppRecordByContext`.

- How likely: the poll first sleeps 50 ms (sample), so the gap is hit only if the creator is delayed there. Examples: preemption, or contention for the ES lock at L861 where the higher-priority new task wins the mutex.
- dev has the same structure (StartAppTask L332/L340/L371/L390; AppCreate L529/L537/L565).

- **A7.** Oracle: in the new task, GetAppID returns ≠ `CFE_SUCCESS` while the task's `TaskTable` entry is not `RecordUsed`, followed by the observed downstream effects. A new task merely running early is not counted (roadmap §2.2).

- **A9 (D4, only if pursued).** A current-code variant would need a hold point between `CFE_ES_StartAppTask`'s unlock (main L722) and `CFE_ES_AppCreate`'s re-lock (L861). It must be labeled as a derived probe of a hypothesised window, not a reproduction of #72.
