   - Both are available only as SourceForge tarballs. We downloaded them and recorded their sha256 (§3).
   - The issue's whole path exists verbatim in 6.4.1:
     - creation order EVS, SB, ES, TIME, TBL with priorities 61/64/68/60/70;
     - `CFE_TIME_TaskInit` → `CFE_SB_CreatePipe` → `CFE_EVS_SendEventWithAppID(..., CFE_SB.AppId=0)` → `EVS_NotRegistered` → `EVS_SendEvent` → `EVS_IsFiltered(0xFFFFFFFF)` with no bounds check (§4, §5).
   - The first git revision, `v6.5.0a`, already contains the fix.
4. **The fix has three parts** (§8).
   - F3, an **order guarantee** (Trac #40): ES waits after creating each core task until it reports ready. A timeout panics.
   - F1, a **use-site guard** (Trac #42): range-check `EVS_AppID` before `EVS_IsFiltered`.
   - F2, a **publish-last** change (Trac #42): `EVS_AppID` is assigned at the end of `CFE_EVS_TaskInit`.
   - All three are present in current `dev` (f22e538c) in rewritten form (§9).
   - The fix does **not** make `CFE_SB.AppId` available to core tasks that are created before SB. In 6.4.2 that task is EVS. In current code it is ES and EVS, which is case R2 / #2663 (inference from code, §8.3).
5. **Reproduction.**
   - An original reproduction is **unavailable**: the Microblaze OS, PSP, OSAL and toolchain are not stated in any reference we could reach.
   - A **public-code-derived** experiment is possible on the 6.4.1 tarball code, but it needs the assumptions in §11.

## 4. Resources and where they are published (buggy revision 6.4.1)

The roadmap (§2.2) warns that the SB AppId and the EVS AppId are different fields. They are kept separate here.

GitHub permalinks below point to `v6.5.0a`. That is the earliest public git revision, and it is already **fixed**. It is given only where the cited statement is unchanged from 6.4.1. The buggy pin is the tarball line.

**R-SB: `CFE_SB.AppId`, the SB task's ES application ID, used as the event sender ID by SB APIs.**
- Storage: `cfe_sb_t CFE_SB;` is a file-scope object with no initializer (`641:cfe/fsw/cfe-core/src/sb/cfe_sb_task.c:L105`; same in [v6.5.0a cfe_sb_task.c#L105](https://github.com/nasa/cFE/blob/b2765d9f905aa11f0c3b419b62233597366a7db9/cfe/fsw/cfe-core/src/sb/cfe_sb_task.c#L105)).
  - Its value before publication is therefore 0. This is consistent with the issue ("In this case the value used is actually 0").
  - `CFE_SB_EarlyInit` does not set it (`641:…/sb/cfe_sb_init.c:L121-L166`).
- **Publication site:** in the SB task, `CFE_SB_TaskMain` → `CFE_SB_AppInit` → `CFE_ES_GetAppID(&CFE_SB.AppId);` (`641:…/sb/cfe_sb_task.c:L127, L184, L198`; [v6.5.0a#L206](https://github.com/nasa/cFE/blob/b2765d9f905aa11f0c3b419b62233597366a7db9/cfe/fsw/cfe-core/src/sb/cfe_sb_task.c#L206)).
- SB then registers with EVS: `CFE_EVS_Register(CFE_SB.EventFilters, …)` at `641:…/sb/cfe_sb_task.c:L257`.

**R-EVSID: `CFE_EVS_GlobalData.EVS_AppID`, EVS's own application ID, used by `EVS_SendEvent` for EVS's own events.**
- Initial value: `CFE_EVS_EarlyInit` (run by the ES main thread before any core task exists) zeroes the global, then sets `EVS_AppID = CFE_EVS_UNDEF_APPID` (`641:…/evs/cfe_evs_task.c:L188, L190`).
  - The constant is `#define CFE_EVS_UNDEF_APPID 0xFFFFFFFF` (`641:…/evs/cfe_evs_task.h:L105`; [v6.5.0a#L105](https://github.com/nasa/cFE/blob/b2765d9f905aa11f0c3b419b62233597366a7db9/cfe/fsw/cfe-core/src/evs/cfe_evs_task.h#L105)).
- **Publication site in 6.4.1:** in the EVS task, `CFE_EVS_TaskMain` → `CFE_EVS_TaskInit` → `Status = EVS_GetAppID(&CFE_EVS_GlobalData.EVS_AppID);` (`641:…/evs/cfe_evs_task.c:L320, L372, L385`).
  - This happens **first** in TaskInit: before EVS registers itself (L393), creates its pipe (L401) and subscribes.

**R-EVSREG: `CFE_EVS_GlobalData.AppData[i].RegisterFlag` and the per-app filters, i.e. EVS registration state.**
- Zeroed in `CFE_EVS_EarlyInit` (`641:…/evs/cfe_evs_task.c:L188`).
- Published per app by `CFE_EVS_Register` (`641:…/evs/cfe_evs.c:L127` onwards sets `RegisterFlag = TRUE`).
- EVS registers itself at `641:…/evs/cfe_evs_task.c:L393`.

## 7. Required order and its provenance

**Statement.**
- Before a task executes an SB API path that sends events with `CFE_SB.AppId` (here TIME's `CFE_SB_CreatePipe` in `CFE_TIME_TaskInit`):
  - (a) SB must have published `CFE_SB.AppId` (R-SB) **and** registered with EVS;
  - (b) EVS must have completed `CFE_EVS_TaskInit` (R-EVSID valid and R-EVSREG for EVS set).
- Equivalently, as the issue's sufficient condition: each core app reaches its main loop ("RunLoop") before the next core app starts its init, regardless of priority.

**Provenance.**
- Issue #73 first list, item 1 (the synchronization requirement) and second list, items 3-7 (the failing interleaving).
- 6.4.2 VDD Table 1.2-2 row 1: "This forces each core application to reach its respective main loop before the next core application will be started regardless of the platform's priority settings".
- 6.4.2 VDD Table 1.2-2 row 3: "set the EVS_AppID value last. This will assure that all other initialization is done before the AppID is valid".

**Inference: which part is necessary for the crash.**
- Condition (b) alone avoids the out-of-range index. If EVS has initialized, `EVS_AppID < 32`.
- Condition (a) alone also avoids it on this path. With SB's AppId valid and SB registered, U3 takes the `EVS_IsFiltered(SB's id)` branch instead of `EVS_NotRegistered`.
- The crash needs both to be violated: TIME's `CreatePipe` runs before SB's `CFE_SB_AppInit` reaches L198/L257 **and** before EVS's `CFE_EVS_TaskInit` reaches L385 or L393.
- Inference: if EVS has initialized but SB has not, the event is silently misattributed to EVS (AppId 0) instead of crashing.

### 8.3 What each part guarantees (inference from code unless quoted)

**F3 guarantees the order:**
- Core TaskInit k+1 begins only after core task k has finished TaskInit and called `CFE_ES_WaitForStartupSync`. This holds regardless of priority, because task k+1 does not exist yet.
- The order is the table order EVS → SB → ES → TIME → TBL.
- TIME's `CFE_SB_CreatePipe` therefore runs after SB's AppInit and EVS's TaskInit, which closes §7 (a) and (b) for TIME.
- Failure is **fail-stop**: on timeout, `CFE_PSP_Panic` is called. It is not a soft continue.
- This is a polling barrier (50 ms poll), not a lock or semaphore hand-off.

**F1 guarantees** that `EVS_SendEvent` never indexes `AppData` with an out-of-range `EVS_AppID`. Such an event is dropped ("Otherwise do nothing", VDD). It is a guard, not an ordering.

**F2 guarantees** that a valid `EVS_AppID` implies EVS init is complete (VDD row 3). It narrows, but does not remove, the window in which EVS's own early events are dropped by F1.

**Not guaranteed by the fix:**
- F3's table order puts EVS **before** SB. EVS's own `CFE_SB_CreatePipe` (`642:…/evs/cfe_evs_task.c`, after `CFE_EVS_Register`) therefore still runs while `CFE_SB.AppId == 0`.
- With 6.4.1's table this is AppId 0 = EVS, which has just registered. So the event is attributed to EVS: no crash, but misattribution.
- In current code (§9) the default order is ES, EVS, SB, TBL, TIME. ES and EVS call `CFE_SB_CreatePipe` before SB publishes its AppId, and the undefined AppId yields `CFE_EVS_APP_ILLEGAL_APP_ID`. This is **R2 / #2663**.
- So "use of R-SB before publication" survives the fix for tasks created before SB. Only the crash consequence and TIME's instance were removed.

- `CFE_SB_Global` is zeroed in `CFE_SB_EarlyInit` ([cfe_sb_init.c#L50](https://github.com/nasa/cFE/blob/f22e538cafe56cf44b15996b67bd1e90850a30cf/modules/sb/fsw/src/cfe_sb_init.c#L50)).

- `CFE_SB_CreatePipe` still sends events with `CFE_SB_Global.AppId` ([cfe_sb_api.c#L226](https://github.com/nasa/cFE/blob/f22e538cafe56cf44b15996b67bd1e90850a30cf/modules/sb/fsw/src/cfe_sb_api.c#L226), [#L275-L277](https://github.com/nasa/cFE/blob/f22e538cafe56cf44b15996b67bd1e90850a30cf/modules/sb/fsw/src/cfe_sb_api.c#L275-L277)).
- ES ([cfe_es_task.c#L367](https://github.com/nasa/cFE/blob/f22e538cafe56cf44b15996b67bd1e90850a30cf/modules/es/fsw/src/cfe_es_task.c#L367)) and EVS ([cfe_evs_task.c#L289](https://github.com/nasa/cFE/blob/f22e538cafe56cf44b15996b67bd1e90850a30cf/modules/evs/fsw/src/cfe_evs_task.c#L289)) call it before SB exists. This is the R2 path.

**Verdict.**
- The C3 crash path (TIME before SB/EVS → out-of-range `EVS_IsFiltered`) is **not present** in current code. Both the order guarantee and the guard block it.
- The underlying "SB AppId read before publication" pattern **is present** for ES and EVS (R2).

## 11. What a derived experiment would have to assume (assumptions, not references)

- **A1. Platform substitution.** An x86-64 Linux host with the 6.4.1 `pc-linux` PSP and the POSIX OSAL replaces Microblaze. This is a `deviation` from row 6. Its effect: scheduling, memory layout and fault behaviour differ.
- **A2. OSAL source.** OSAL 4.1.1, obtained from the source the readme names (sourceforge.net/projects/osal or github.com/nasa/osal). Neither has been fetched or verified yet. The exact tag or tarball and its hash must be recorded when chosen.
- **A3. Order control (D3).** Either:
  - honour priorities: main thread at SCHED_FIFO max as the pc-linux PSP does, with RT priorities mapped by OSAL. This requires that the container permits SCHED_FIFO, which is unverified; or
  - use event-based control: hold `CFE_SB_AppInit` and `CFE_EVS_TaskInit` until TIME's first `CFE_EVS_SendEventWithAppID` from `CFE_SB_CreatePipe` has been observed.

  No fixed delay may be used (policy).
- **A4. Outcome criterion (D4).** On a 64-bit host, `&AppData[0xFFFFFFFF]` lands about 4 G × `sizeof(EVS_AppData_t)` bytes past the array. That is likely unmapped, but this is not guaranteed. On a 32-bit target it lands just before `CFE_EVS_GlobalData`, so it may not fault immediately (inference). The primary observable should therefore be "out-of-range AppID reaches `EVS_IsFiltered`". A crash would be secondary.
- **A5. Platform configuration.** Use the 6.4.1 `platform_inc/cpu1/cfe_platform_cfg.h` unchanged. The issue cites the "default/example" values; EVA's actual configuration is unknown.
- **A6. Reset type.** Power-on.
- **A7. Fixed-side control.** Either the 6.4.2 tarball (minimal diff, only the race fixes plus unit-test changes) or `v6.5.0a` (many unrelated changes). Comparisons should use 6.4.2.
- **A8. Ablations** (roadmap §7.2): "order guarantee only" (F3 without F1/F2) and "guard only" (F1 without F3). Both are **constructed** by applying subsets of the 6.4.1 → 6.4.2 diff. They are not historical revisions and must be labelled as such.
- **A9. Recorder independence** (roadmap §6.3 item 5). The recorder must not use EVS, SB or TIME, because they are the resources under test.
