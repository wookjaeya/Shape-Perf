## 3. 보고·판정 원칙 (AD §0.2)

- **기존 방법 비교:** process-level 연구·도구끼리 비교한다. 실행 불가, 지원 범위 밖, 실행 후 미탐지를 구분한다. 내부 F0·G-I 대조는 외부 방법과의 비교를 대신하지 않는다.
- **평가 자료:** 확보한 실제 cFS 사례와 1차 출처를 우선한다. 작은 합성 입력은 구현 검증용 도구 시험으로만 쓰고 사례 수에 넣지 않는다.
- **연구 범위:** 공유자원·의존성과 동기화·실행 제어의 관계에서 생기는 order violation. 최종 오류 결과는 별도 항목이다.
- **수치 보고:** 호출 수와 함께 사례 수, 순서 구조 수, 계획 수, 실행 수를 따로 적는다. 현재 수치는 근거 개선을 보이는 자료이고 정확도 지표가 아니다(AD §3.0 표 "수치의 해석 범위").
- **83/86:** 수집·제어 경로 비교(같은 논리 사건·값·제어 지점을 확보하는가)와 근거 추가의 효과(같은 판정 입력에 제어 근거를 더하면 어떤 호출의 유보가 풀리는가)를 나눠 보고한다. 컴파일러 계측만의 탐지력 차이로 쓰지 않는다(AD §4.4).
- **반환 코드 독립:** P1을 끈 읽기와 반환 코드 의존 전체 제거는 같은 실험이 아니다. 자연 실행의 8건은 `nocode` 읽기로, 제어 실행의 판정은 발생별 control-order 근거로 확인한다(AD §3.2).
- **프로필 판:** 서로 다른 프로필·분석기 판의 결과를 하나의 최신 성과처럼 합쳐 쓰지 않는다(AD §4.5).

## 4. 유지하는 선택 (AD §6.5)

- GCC plugin을 주 계측 경로로, F0를 비교 경로로 유지한다. 공통 분석기를 유지한다.
- LLVM·Clang 시제품은 비교 기록으로 남긴다. 현재 요구에 대한 구체적 개선 없이 주 경로를 바꾸지 않는다.
- MLIR은 모델 추출·분석에서 구체적 이득이 확인될 때 재검토한다(PD26 §2 항목 4와 같음).
- C5를 다음 실제 사례로 삼는다. 원 사례의 버전·등록 관계·문제 창을 확인한다.
- C2는 원 사례의 실제 앱·함수 자료를 어디까지 확보할 수 있는지 먼저 밝힌다. C3는 원 사례의 실행 조건(원 플랫폼·버전·우선순위·task 시작 조건)을 충족했는지 따로 확인한다. 그 조건을 충족하지 않은 실행은 원 사례의 재현으로 세지 않는다. 하드웨어 보드는 당장 연구 전체의 필수 조건으로 두지 않는다.

1. 결정·형상관리 반영(이 문서, `CONFIG_MANAGEMENT.md`, `plan/r2_start_poweron_20261028.md`).

6. 발생별 근거 보존과 병합 순서 도구 시험.
7. C5 적용 준비와 실행: 초기화 전 기록, 사후 앱 귀속, 실패·정체 때 기록 회수를 확인한 뒤 적용한다.
- 병행: 기존 process-level 연구·도구 조사(H4).

5·6의 구현 보완을 모두 마쳐야 4를 시작할 수 있는 것은 아니다(AD §6.1 끝). 다만 같은 제어 근거를 주지 않은 비교를 수집 경로의 우월성으로 해석하지 않는다.
