# Kairos 연구 결정 결과

- 연구: **Process-Level Race Detection in core Flight System**.
- 결정일: 2026-10-15.
- 입력: 사용자가 첨부한 `DECISIONS_20261015.md`, 앞서 검토한 저장소와 작성한 구현·검증 로드맵.
- 저장소 근거 기준: [`2499ad461637a6573d8420620bbcbd96eea71eb2`][R01]. 그 이후의 코드·문서 변경을 확인했다는 뜻은 아니다.
- 문서 성격: **사용자의 결정 위임에 따라 선택한 연구 설계와 실행 범위**. 선택은 사실·실험 결과가 아니며, 코드·환경·파일 변경의 실행 완료 기록과 구분한다.

## 1. 결정의 기준

1. 탐지 대상은 cFS(core Flight System) 애플리케이션·task 사이의 **순서위반 오류**로 유지한다. 운영체제의 서로 다른 프로세스에 한정하지 않으며, 그 운용상 정의를 논문에 명시한다.
2. **C1·C2·C3·C5·R2 다섯 사례의 검증을 목표로 한다.** R2는 첫 전체 구현 대상이다. 다른 네 사례를 현재 버전의 대응 코드 분석으로 대체하지 않는다.
3. 원출처의 사실, 코드로 확인한 내용, 연구자 해석, 실험을 위한 선택을 구분한다. 출처가 정하지 않은 수치는 임의로 확정하지 않는다.
4. 기존 **Process-Level Race 연구끼리 비교**한다. thread data-race 도구를 참조점이라는 이름으로 다시 실험 비교에 넣지 않는다.
5. 기본 구현을 막지 않는 선택은 실행 시점과 확정 방법을 정한다. 모든 후속 실험의 수치까지 지금 채우는 것을 구현 착수 조건으로 삼지 않는다.
6. 결과가 미결정이면 이유를 보고한다. 근거가 부족한 정상·오류 판정을 연구자 규칙만으로 강제하지 않는다.

**표의 ‘승인·채택·제외’는 연구 계획에 대한 결정이다. ‘파일럿 후 확정’은 선택을 미룬 것이 아니라, 무엇을 측정하고 언제 값을 동결할지 정한 절차적 결정이다.**

### 2.1 D20의 추가 완료 조건

**근거:** 명세의 보조정리는 아직 증명 스케치와 미완료 의무를 포함한다. 안전성과 진행성의 분리만으로 그 증명이 완료된 것은 아니다. [R02 §6.2][R02]

다음도 함께 적용한다.

- 정리마다 `증명 완료 / 명시적 가정에 의존 / 미증명`을 표시한다.
- 필요한 증명 의무를 목록으로 작성했다는 이유만으로 ‘증명됨’이라고 출력하지 않는다.
- 조기 반환 `NOT_EVALUATED`의 처리와 실제 실행으로 옮기는 규칙을 일치시킨다.
- R2의 도달 근거에 필요한 L-CONT(c)를 해당 신뢰 원장에 추가한다.
- checker가 확인한 추론 단계와 checker가 신뢰한 추출 사실·공유 코드·가정을 구분한다.

위 두 구체적인 명세 불일치는 기존 검토 처리표에도 남아 있다. [R03 §5 항목 7·8][R03]

### 2.2 D1·D11의 관측 영향 점검

**결정:** ‘실행 사용자·바이너리 유지’와 ‘관측 영향 없음’을 같은 의미로 취급하지 않는다.

- 관측하지 않은 기준 실행과 비교할 수 없는 내부 사건에 대해서는 영향이 없다고 결론 내리지 않는다.
- 커널 변경 후의 기준 실행 재측정을 **S1의 관측 영향 비교보다 먼저** 수행한다.

**판정 기준:** 순서 근거가 달라진 부분에서 기존 고정 오류 판정이 적절하게 철회되는지 확인한다. 철회됐다는 사실만으로 전체 안전성을 인정하지 않는다. 구성·버전 차이는 같은 바이너리의 스케줄 의존성을 증명하는 자료가 아니다. [R02 §9.3, App. A.1][R02]

### 3.3 P-C1HOLD — C1 실행 보류

**결정: provider의 생성 직전 보류 실험을 채택한다. RESERVED 구간 실험은 후속 과제로 분리한다.**

- 정상 경로는 생성·조회 사건을 직접 기록한다.
- 실패 경로 확인 시 provider를 생성 직전에 보류하고, CF의 재시도 종료 또는 최종 초기화 결과라는 **사건**을 기준으로 해제한다.
- 선택한 CF 버전의 실제 재시도 수와 지연 값을 읽는다. 25 또는 100 ms를 모든 버전에 고정하지 않는다.
- 재시도 수×지연을 곧바로 벽시계상의 안전한 대기 상한으로 간주하지 않는다. 관측 영향과 실제 종료 시간을 파일럿에서 확인하고, 중단 조건·감시 한도를 본실험 전에 기록한다.
- 보류로 만든 실패는 자연 실행과 구분한다. 단순 timeout 관측만으로 영구 교착이라고 판정하지 않는다.
- RESERVED 조회·lock 잔류는 OSAL 구현 결함 후보의 추가 검증으로 취급한다. 원 C1 검증의 착수 조건이나 다섯 사례 성과 수에 추가하지 않는다.

### 3.4 D13·Q16 — C3·C5의 6.4.x 기준

**결정: (a) 분석 전용 파싱 인정, (b)(i)부터 시작, (c) F1 전에 배치한다.**

- 해시가 확인된 6.4.1·6.4.2와 관련 OSAL 소스를 기준으로 한다.
- 현재 컨테이너의 32-bit 헤더를 사용하는 첫 파싱은 **분석 전용이며 차이가 있는 조건**으로 표시한다. 이것을 원 플랫폼 실행 재현으로 인정하지 않는다.
- 생성 설정, include 목록, 정수·포인터 크기, 매크로가 선택한 소스 경로, 구조체·반환값 해석을 확인한다.
- 관련 경로나 자료형 해석이 헤더·환경에 민감하면 문헌상 host의 sysroot를 확보하는 (ii)로 전환한다. 민감성이 해소되기 전에는 영향을 받는 결과를 보류한다.
- Q16의 버전별 상태·반환값·소스 위치 대응을 명시하고 시험한다. 입력·대응 실패를 탐지 기법의 실패로 세지 않는다.
- 과거 코드의 실제 실행 검증은 분석 전용 작업과 별도 산출물로 보고한다.

### 3.5 P-C2·Q22 — C2 역할 재구성

**결정: 코드 읽기·정적 분석에서 시작하되, 역할 재구성 실험까지 진행한다.**

**선택 이유:** 정적 barrier 목록만으로는 다섯 사례 중 C2의 현상을 도구가 다룬다고 검증할 수 없다. 원 애플리케이션의 비공개 부분을 사실처럼 채우는 대신, 공개 보고에서 확인되는 역할 관계를 재구성한다. [R07]

- provider의 late initialization과 consumer의 의존 사용을 구분한다.
- 단일 단계/두 단계 시작 동기화와 기존/수정 provider 역할을 교차하는 2×2 검증을 준비한다.
- 요청 방식·초기화 내용·우선순위·timeout은 재구성 실험의 선택으로 기록한다. 원 보고자의 값으로 인용하지 않는다.
- **Q22:** 1차 대조는 provider의 late initialization이 정상 완료하는 구성으로 둔다. 초기화 실패까지 가능한 구성은 별도 보조 실험으로 구분한다.
- ‘초기화는 실패하지 않는다’는 가정은 재구성 구성에만 적용한다. 실제 cFS 전체의 보장으로 일반화하지 않는다. 모델 분류는 가정의 포함 여부와 함께 보고한다.
- 평가에는 각 셀을 그대로 제시한다. 2×2의 네 셀을 독립된 실제 결함 네 개로 세지 않는다.

결과 명칭은 **C2 메커니즘의 역할 기반 검증**이다. 비공개 원 시스템 재현으로 쓰지 않는다.

### 3.7 P-F1GATE — 평가 동결 전 조건

**결정: 승인하고 다섯 사례의 실질적 준비 상태를 함께 기록한다.**

- D13·D22·P-C2의 선택과 필요한 세부 조건을 F1 전에 기록한다.
- 사례별 자체 기준 구성, 기대 결과표, 필요한 구현 기능과 검증 단계가 존재해야 한다.
- 수행하지 못한 사례는 그 이유와 연구 범위의 제한을 명시한다. 다른 코드의 결과로 완료 처리하지 않는다.
- 특정 사례를 수행하지 않기로 했다는 기록만으로 다섯 사례 검증이 완료되는 것은 아니다.
- 기대 결과표는 해당 사례의 첫 출력 전에, 평가 엔진·규칙은 본 평가 전에 동결한다. F1을 기다리다가 첫 출력 전에 해야 할 기록을 놓치지 않는다.

**실행 상태:** 이 문서는 삭제 범위를 결정한 결과다. 실제 삭제·커밋·원격 반영은 수행한 결과로 보고하지 않는다.

### 6.2 인용 정리 원칙

1. 현재 명세와 설명 문서에서 CORD에 근거한 인용을 찾아 분류한다.
2. **gdb 자료가 직접 뒷받침하는 사실만** 해당 자료로 연결한다. 예: 현재 저장된 세 gdb 실행의 설정 전 사용 24회와 대응 오류 결과.
3. CORD에서만 측정한 11회 구성, 계측 바이너리의 결과, 해당 기록기의 순서 분석·성능 수치는 지운다. gdb가 같은 실험을 했던 것처럼 출처만 바꾸지 않는다.
4. CORD 결과와 gdb 결과의 비교에서 얻은 해석도 의존성을 점검해 제거한다.
5. 본문뿐 아니라 표·그림·완료 조건·요약·예정 명령을 함께 정리한다.
6. 과거 상태 문서는 과거에 보고한 내용을 보존할 필요가 있으면 과거 커밋 링크로 참조하고, 현재 실행·평가의 근거 문서와 구분한다. 과거 기록을 새로운 관측으로 덮어쓰지 않는다.

이 결정은 앞서 작성한 로드맵의 CORD 인용·과거 관측 유지 방침도 변경한다. 다음 문서 갱신에서 해당 표와 근거를 함께 수정한다.

### 6.3 환경 스크립트

**결정:** CORD 전용 코드·분기·기본 경로는 제거한다. 일반적인 기존 빌드 실행 기능과 `CFS_DIR` 지정 기능은 필요성과 재현성을 확인해 유지한다.

유지 조건은 다음과 같다.

- 사용한 실제 소스 경로·커밋·바이너리 해시·설정을 기록한다.
- 기준 빌드와 파생 빌드를 혼동하지 않는다.
- 기준 실행에서 임의의 다른 디렉터리로 조용히 전환하지 않는다.
- CORD 전용 의존성을 제거한 뒤 기준 gdb 실행과 일반 기준 실행이 가능한지 확인한다.

첨부 문서의 자동 권한 차단 기록은 그 실행 환경의 사건 기록이다. 이번 결정문은 실제 삭제의 성공이나 해당 차단의 해소를 증명하지 않는다.

## 7. 구현 담당자에게 전달할 실행 순서

1. **결정 반영:** `PI_DECISIONS.md`, 명세, 한국어 설명·그림의 해당 항목을 이 선택과 일치시킨다. 아직 실행하지 않은 결과는 완료 상태로 바꾸지 않는다.
2. **핵심 명세 정정:** 조기 반환과 실제 실행 보장 문장을 맞추고 R2 신뢰 원장·증명 상태를 고친다.
3. **CORD 정리:** 파일 목록 확인, 인용의 근거별 처리, 스크립트 일반 기능 분리, 기준 자료 유지 확인 순으로 변경한다.
4. **R2 전체 구현 착수:** 추출·관측·판정·근거 재확인을 연결한다. 필요한 정리가 미증명인 동안은 그 상태를 출력한다.
5. **동시에 기준 준비:** C1의 공개 BP 구성, C2 역할 재구성, C3·C5 과거 버전 대응표를 만든다.
6. **S1 측정 후 수치 동결:** 목적별 실행 횟수·관측 비교 조건을 정하고, 보류·탐색 단계에서는 각 단계의 예산과 중단 기준을 확정한다.
7. **사례별 검증:** R2 대조, C1 재시도·순서 변화, C2·C3·C5의 고유 현상을 검증한다. 모든 결과의 근거 종류를 유지한다.
8. **비교·논문 평가:** Process-Level Race 원문·도구·기법의 적용과 자체 기능 제거 시험을 분리해 보고한다. 누락·미결정 사례를 공개하고 주장 범위를 정한다.
