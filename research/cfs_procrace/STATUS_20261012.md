# 현황과 결정 요청 (2026-10-12)

연구: Process-Level Race Detection in core Flight System (학회 논문 목표)

## 0. 요약

- **새 탐지기의 아키텍처를 확정했다.** 이름은 작업용으로 **Kairos**(명령 접두사 `kz`)라고 붙였다. 아직 코드는 한 줄도 쓰지 않았다. 전체 문서는 `Architecture/` 폴더에 있다. 시각화된 아키텍처와 워크플로우, 형식 모델, cFS 대응, 평가 계획, 로드맵, 설계 결정 기록(ADR)이 들어 있다.
- **어떻게 정했나.**
  1. 조사 7건을 했다(`Architecture/background/`): cFS 구조 3건, 문헌 2건, 설계안 v0.1 비판, 이 머신에서의 구현 가능성.
  2. 서로 다른 관점의 설계안 3개를 만들었다(정적 모델 우선, trace 우선, 계층형 하이브리드).
  3. 심사 3명이 평가해 만장일치로 하이브리드를 골랐다. 점수는 146, 138, 129점이었다.
  4. 다른 두 안의 장점을 합쳐 종합안을 만들었다.
  5. 적대적 검토 3건에서 쟁점 57건이 나왔고, 모두 반영했다(critical 4, major 32, minor 21).
- **CORD는 폐기했다.** 이 연구에 쓰지 않는 파일(이전 프로젝트, 사례 clone, cache)도 모두 지웠다(`env/HOST_CLEANUP_20261012.md`).
- **'계약'이라는 용어를 다시 검토했다(§1A).** 받은 AI 논문(FSE 2014)과 관련 연구 52편을 조사했다. 결론은 둘이다. **"invariant"는 맞지 않는다.** 이 계열 연구에서 invariant는 정상 실행에서 학습한 조건을 뜻하기 때문이다. **"계약"은 일부 경우에만 맞는다.** 권고하는 이름은 **"준비 상태 명세(readiness specification)"**다. 결정은 T1이다.
- **조사하다가 결함 후보를 찾았다.** 다섯 사례 밖이고, 모두 코드 해석일 뿐 실행하지 않았다.
  - OSAL 이름 조회가 생성 중인 객체를 만나면 table lock을 놓지 않아 deadlock이 날 수 있다.
  - ES `GetAppIDByName`이 생성 중인 앱에 대해 성공을 반환하면서 잘못된 ID(0xFFFFFFFF)를 준다.
  - 새 task가 300 ms 대기를 넘기면 조용히 사라질 수 있다.
  - SBN이 준비되기 전에 자신의 준비 단계를 선언한다.

## 1. Kairos의 핵심 (자세한 것은 `Architecture/01_overview.md`, `02_architecture.md`)

| 질문 | 답 |
|---|---|
| 무엇을 판정하나 | cFS 빌드 안의 모든 **준비 계약(readiness contract) 인스턴스**를 판정한다. 준비 계약 인스턴스는 "프레임워크 자원이 특정 상태여야만 맞는 사용"이다. 클래스는 다섯 가지다: `inactive`, `protected`, `fixed-order`, `schedule-dependent`, `unknown(이유)`. 판정마다 어떤 스케줄 의미(σ)와 OSAL 모델 수준(M)에서 성립하는지, 증거가 무엇인지 함께 적는다. **"경보 없음"을 "안전"으로 바꾸는 클래스는 없다.** |
| 왜 새 도구가 필요한가 | 세 가지 이유가 있다. **(1)** R2의 위반 24건은 순서가 보장된 채로 **잘못된 방향**으로 일어난다. 그래서 "순서가 없는 쌍"만 찾는 HB·예측 탐지기는 원리상 보고하지 못한다. **(2)** C1·C5는 lock으로 보호되어 있는데도 순서가 위반된다. 그래서 lockset 계열이 보지 못한다. **(3)** cFS의 시작 barrier는 timeout이 있는 polling이라 기존 HB 규칙에 없는 조건부 순서다. |
| 구조 | **하나의 typed event model과 cFS 프로파일 Φ**를 세 방식으로 해석한다. **정적**: 구성을 닫은 프로그램 위에서 반드시 앞서는 순서를 증명하고 인증서를 만든다. **동적**: 수정하지 않은 gcc 바이너리를 uprobe/eBPF로 관측해, cFS 규칙을 반영한 HB 위에서 계약을 검사한다. **조작적**: 후보별로 제한된 탐색을 한다. 그다음 실제 바이너리에서 확인 실행을 하고, 결과를 다시 앞 단계로 돌린다. 인증서는 생산 코드와 코드를 공유하지 않는 별도 checker가 다시 검증한다. |
| 개방성 | 앱 15개에서 찾은 계약 종류 15개를 모두 다룬다. 다섯 사례가 포함하는 것은 그중 3개뿐이다. 계약은 API 문서, 코드 주석, 재시도·timeout 패턴에서 나오고, 추가할 때마다 출처를 기록한다. 엔진 코드에 사례 식별자를 넣지 못하게 lint로 막는다. 평가는 held-out 출처와, 과거 수정 이력에서 만든 mutant로 **놓친 것(recall)**까지 잰다. |
| 기술 | 핵심은 C/C++다. Python과 JSON은 쓰지 않는다. Clang/LLVM 23은 기존 빌드를 재사용하며 분석에만 쓴다. 실행하는 바이너리는 기준 gcc 빌드 그대로다. MLIR과 SMT는 선택 사항이며, 측정에서 이득이 확인될 때만 쓴다. 최소 핵심 범위(thin MVC)는 새 패키지를 설치하지 않고 만들 수 있다. |
| 학술적 위치 | 기존 기법을 빌려 쓴다. HB·vector clock, 이벤트 구동 시스템의 순서 규칙(CAFA, DCatch), 예측 분석(SyncP, RVPredict, GPredict), DPOR, PCT를 cFS의 준비 계약과 결합한다. 새로운 점은 세 가지 가설이다: 프레임워크 수준의 준비 계약, 조건부 barrier edge, 고정 순서와 스케줄 의존을 인증서로 구분하는 것. 문헌은 검증한 것만 인용했다. 원문 PDF는 열지 못해 일부가 미검증 상태다(P-PAPERS). |

## 1A. 용어 검토: '계약(contract)'이 타당한가

조사 보고서는 `Architecture/background/08_terminology.md`(영문)에 있다. 조사는 네 갈래로 했다: AI 논문 정독, 'contract' 용어의 계보, 대안 용어, 52편의 용어 사용 비교. 이어서 인용 검증과 반론 검토를 거쳤고, 쟁점 32건을 반영했다.

### 받은 논문: Zhang et al., "AI: A Lightweight System for Tolerating Concurrency Bugs", FSE 2014

- **무엇을 하나.** 정상으로 판정된 실행에서 변수 접근 순서를 학습한다. 학습하는 것은 각 명령 직전에 다른 thread에서 같은 주소에 접근한 명령의 집합(BSet)이다. 이것을 **Anticipating Invariant**라 부른다. 운영 중 위반 직전 지점(turning point)에 다다르면 그 thread를 잠시 멈춰(stall) order·atomicity violation을 막는다. 실제 버그 35개를 대상으로 했고, 오버헤드는 대부분 1% 미만이라고 보고한다.
- **Kairos와의 관계.**
  - **R2:** 잘못된 순서가 매 부팅 일어나고 출력 검사도 통과한다. 그래서 AI 같은 학습 방식은 이것을 "정상"으로 배운다. 손으로 guard를 넣어도 순환 대기가 될 뿐이다. SB의 게시가 ES가 그 사용 지점을 지나야 진행되기 때문이다.
  - **C1:** AI는 침묵할 가능성이 크다. OSAL의 이름 탐색은 모든 slot·객체 종류·호출자가 같은 load 명령 하나를 쓰기 때문이다. 만약 AI가 멈춘다면, 제공 앱이 필요로 하는 table lock 안에서 멈추게 된다.
  - **SB 손실:** 출력 기반 학습 검사를 원리상 통과한다.
- **설계에 반영할 것(권고).**
  - 같은 trace 위에서 동작하는 **AI 방식 비교 기준**(AI-all, AI-lc)을 기준선에 추가한다. golden test는 논문 그림으로 만든다.
  - 관련 연구에 AI를 넣는다. 함께 넣을 것: concurrent typestate(Joshi & Sen, ASE 2008), framework lifecycle typestate(Lifestate, ECOOP 2019), Dwyer 등의 specification pattern.
  - AI의 "stall은 해롭지 않다"는 가정은 cFS에 맞지 않는다. cFS의 barrier와 재시도는 timeout에 의존하기 때문이다. Kairos의 hold가 timeout 영향을 따로 표시하는 근거가 된다.

### '계약'이 맞는 곳과 맞지 않는 곳

| 사례 | 근거 | 계약으로 볼 수 있나 |
|---|---|---|
| **R2** | cFE `cfe_evs.h` 문서의 Assumptions에 "The Application ID must correspond to a registered application or core service."라고 적혀 있다. 다만 같은 함수 문서가 `\retval CFE_EVS_APP_ILLEGAL_APP_ID`를 정상 반환값의 하나로 적어 둔다 | **부분적으로.** Design by Contract의 "호출자 의무"에 가깝지만, 교과서적인 계약 위반은 아니다 |
| **C1** | OSAL은 `OS_ERR_NAME_NOT_FOUND`를 정상 결과로 문서화한다. 요구 조건은 CF가 동료 앱에 대해 스스로 둔 가정이다. 코드 주석에 "assume"이라고 쓰고, 재시도로 견딘다 | assume-guarantee 의미로만 볼 수 있다. 그러나 Kairos는 그 이론(정제·합성)을 쓰지 않는다 |
| **SB 구독 전 송신 손실** | cFE 요구사항 cSB4305.5의 근거 문장: "It is not considered an error if no Applications have subscribed … during initialization of a multi-processor system, this can easily occur." | **아니다.** 공급자 쪽 문서가 이것을 오류가 아니라고 정한다 |

- race·order-violation 문헌 52편 가운데 요구 순서를 "contract"라 부른 연구는 없다. 쓰이는 이름은 다음과 같다: 의도(Lu et al. 2008), 학습된 invariant(AVIO, DefUse, PSet, CCI, AI), 도구에 내장된 HB 모델(이벤트·분산 시스템 연구), 작성된 specification(typestate, Lifestate, GPredict 등).
- "invariant"는 쓰지 않는다. 이 계열에서 invariant는 정상 실행에서 학습한 조건이다. 그래서 매번 일어나는 위반(R2)을 정상으로 흡수한다.
- 다른 후보는 cFS·Kairos 용어와 겹친다. protocol은 CFDP·SBN 코드, requirement는 cFE 기능 요구사항 ID와 `Req` 필드, dependency는 의존 그래프, assumption은 spec §6.1의 가정 A, rule은 HB 규칙 R1–R19와 겹친다.
- "readiness"는 cFE 자체의 용어다(`CFE_ES_SystemState_CORE_READY`). 그래서 유지할 수 있다.

- 이름을 바꾸는 작업(spec, `Architecture/` 문서, Φ 문법)은 **T1이 결정된 뒤에** 한 번에 한다. 지금 문서들은 아직 "계약"을 쓴다.
- **인용 검증에는 한계가 있었다.** 검색 예산이 바닥났고 proxy가 논문 host를 막았다. 그래서 일부 인용은 다시 검증해야 한다. Meyer 1992, Nienaltowski et al. 2009, Joshi & Sen 2008, Lifestate 2019, Lu et al. 2008의 정의 문구 등이다. 원문으로 확인한 것은 AI 논문(받은 PDF)과 cFS 문서뿐이다.

## 2. 제 판단: 범위를 잘라서 시작해야 한다

- **설계는 학술적으로 탄탄하다.** 정의가 엄밀하고, 모르는 것은 정직하게 `unknown`으로 남기며, 놓친 것까지 측정한다. 다만 **규모가 크다.** 설계자가 추정한 공수는 S0–S9 전체가 수십 person-week다. 계획용 추정일 뿐 측정값이 아니다.
- **권고: 첫 목표를 thin MVC(S0 + S1 + S2 + S3a)로 정한다.**
  - S0: 형식 코어와 Φ 문법·의미
  - S1: 미수정 바이너리를 관측하는 기록기. R2를 다시 관측하는 것이 통과 조건이다.
  - S2: trace HB와 계약 검사
  - S3a: 구성 닫기, 인증서, 독립 checker
- **MVC만으로 논문이 주장할 수 있는 것:**
  - 계약 인스턴스 전수 조사(census)
  - R2의 fixed-order 인증서와 독립 검증
  - 구성 닫기로 얻는 `inactive`·provider 판정
  - 이 층들의 recall
- **늘려 갈 순서:** 예측(S5), 확인 실행(S6), 탐색기(S7) 순으로 붙인다. MLIR(S8)과 PCT·RT 실험(S10)은 필요할 때만 한다.
- **구현 원칙:** 코드는 인터페이스(스키마, Φ 문법과 의미, 판정 기록)를 먼저 검토받은 뒤에 쓴다. 단계마다 exit gate를 통과해야 다음 단계로 간다.

| **T2** | 근거 종류에 cFE 기능 요구사항(`requirement`)을 추가할지. 그리고 SB 구독 전 송신 손실을 cSB4305.5에 따라 "문서화된 허용 손실(documented_drop)"로 볼지 | 근거 종류는 **추가한다.** 손실은 **허용(allowed)으로 분류하되 손실량은 따로 보고한다.** 요구사항이 오류가 아니라고 하므로 위반으로 세지 않는다 |
| **T3** | AI 방식 비교 기준(AI-all, AI-lc)과 관련 연구 추가(AI, Joshi & Sen, Lifestate, Dwyer 등) | **승인** |

## 4. 아직 하면 안 되는 주장

- Kairos가 무엇을 탐지했다. 아직 구현하지 않았다.
- AI나 그 밖의 학습 기반 도구가 R2를 놓친다. 지금은 정의에서 나온 분석일 뿐이고, 같은 trace에서 비교해야 주장할 수 있다.
- SB 구독 전 송신 손실이 결함이다. cFE 요구사항(cSB4305.5)은 이것을 오류가 아니라고 한다.
- 조사 중 찾은 결함 후보가 실제 결함이다. 코드 해석일 뿐 실행하지 않았다.
- 기존 도구가 이 계약 위반을 놓친다. 같은 trace에서 비교하기 전에는 원리적 분석에 그친다.
- cFS에 대한 동시성 검증 연구가 없다. "찾지 못했다"고만 쓴다.
- 이전에 나열한 주장 금지 목록(STATUS 2, 3)도 그대로 유효하다.
