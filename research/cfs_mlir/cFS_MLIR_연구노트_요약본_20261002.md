## 1. 한 문단 요약

이 연구는 NASA cFS 앱 사이의 순서 결함을 MLIR 기반 정적 분석으로 찾을 수 있는지 검토한다. 대상은 메시지 순서, 메시지로 갱신되는 상태, startup·재시작·Table Services 의존이다. 공유 메모리 data race는 대상이 아니다. **[확인된 사실]** cFE `546a002`의 SB는 목적지별 전달 실패를 발신자에게 알리지 않는다. ES의 startup 동기화는 timeout이 있는 soft limit이다. TBL 잠금은 handle 단위다. 전달 lock 위치와 재시작 동작은 버전에 따라 다르다. **[실측]** 실제 cFS C 파일 154개가 조건부 compile flag로 MLIR LLVM dialect에 진단 없이 import되었다. 코드에서 정의한 MID는 call site 상수로 회수되었다. 그러나 구독 site 47곳 중 8곳은 table·명령·설정에서 MID를 받는다. MID 이름은 IR에서 사라진다. **[설계 제안]** 노트는 결함 범주 F1–F8, `cfs` dialect, 사건 모델과 HB 규칙, 상관을 보존하는 추상 도메인, 세 층의 평가, 관문을 둔 16주 계획을 제안한다. 분석기는 구현하지 않았다. 검출 결과, 검출률, 신규성, MLIR의 우월성은 주장하지 않는다. **[해석]** 현재 판단은 조건부 GO다.

## 2. 결론

### 2.1 확립된 것
- **[확인된 사실]** cFE `546a002`에서 경로 없음, 목적지 0개, MsgLim 초과, pipe full은 모두 발신자에게 `CFE_SUCCESS`다 (검증 C09).
- **[확인된 사실]** startup script 앱의 ES 동기화는 soft limit이다. OPERATIONAL은 모든 앱의 RUNNING을 뜻하지 않는다 (C11).
- **[확인된 사실]** TBL 잠금은 handle 단위다. `NEVER_LOADED`의 구현은 header 설명과 다르다 (C13, C14).
- **[확인된 사실]** 전달 lock 위치(`550e7f7d`), TBL 재등록(`c1ab1b7`), TO_LAB 지연 구독(`d3d52da`)은 버전에 따라 바뀐다 (전체 노트 §3.6).
- **[실측]** C → LLVM IR → MLIR import 경로는 실제 cFS 코드에서 막히지 않는다. 다만 154/154는 C17 정정 조건에서만 성립한다 (이 요약본 §8).
- **[해석]** 비용은 import가 아니라 의미 복원에 있다. 복원할 것은 MID 이름, table·명령 유래 MID, out-parameter, field 이름이다 (C18).
- **[확인된 사실]** cFE #73의 crash 경로는 현재 코드에서 닫혀 있다 (C12). C21 정정: #73의 수정 전 6.4.1과 수정 후 6.4.2가 SourceForge에 공개되어 있다. `UNDEF_APPID`는 수정 전부터 있던 sentinel이다. SB AppId 초기화 불일치는 고쳐지지 않았고 #2663으로 남아 있다. **[실측]** 이 경로는 gdb로 관측했다 (전체 노트 §2.2).

### 2.2 제안한 것
- **[설계 제안]** 결함을 네 조건으로 정의한다. 필요 순서 `Req`, 보장 부재, Σ에서의 실행 가능성, 관측 가능한 결과다 (전체 노트 §1.1). 결과는 후보(L0), 모델상 가능(L1), 재현(L2)으로 나눈다 (전체 노트 §8.1).
- **[설계 제안]** `cfs` dialect(전체 노트 §5), cFE 의미에서 얻는 HB 규칙과 상관 보존 도메인(전체 노트 §6)을 둔다.
- **[설계 제안]** 세 층(합성 앱, 공개 앱 결함 주입, 역사적 사례)으로 평가하고(전체 노트 §8), 관문 GO-1–GO-8을 둔 16주 계획을 따른다(전체 노트 §9).

### 2.3 모르는 것
- **[미확인]** Q1: 같은 SB·ES·TBL 모델을 넣은 CodeQL이나 AST 구현이 같은 후보를 내는지 모른다.
- **[미확인]** Q2: 읽지 못한 선행 본문(R03, R16, R17, R04 등)이 같은 일을 했는지 모른다.
- **[미확인]** Q3: 앱별 계약 없이 `Req`를 얼마나 얻는지 모른다.
- **[미확인]** RTOS build에서의 순서 의미를 모른다.
- **[미확인]** Swift/BAT race의 원인과 cFE와의 관계를 모른다 (C22, contested; 이 요약본 §4).
- **[미확인]** F4의 신규성을 모른다 (전체 노트 §4.7.3).

### 2.4 계속 여부와 관문 — **[해석]** 조건부 GO
- 근거는 두 가지다. frontend 경로가 막히지 않았다. cFE 의미가 `Req`와 `G`의 구체 출처가 된다.
- 다음 단계는 전체 노트 §7.13.4의 23개 site 추출 정답표를 자동으로 재현하는 것이다. race 판정은 그다음이다.
- GO-2(W4 말)는 23/23과 table 값 집합을 본다. 47곳 분류는 보고 항목이다. 실패하면 RQ1을 철회하고 앱 내부 분석으로 줄인다.
- GO-3(W9 말)에서 세 조건이 모두 맞으면 MLIR 기반을 철회한다. AST 경로가 추출을 맞히고(PIVOT-1), `cfs` dialect가 E-llvm보다 나은 점이 없고(PIVOT-2), Clang CFG 위 시제품이 원노트 §44 예를 맞히는 경우다.
- 그때도 도메인 의미의 기여는 계속 검증한다 (전체 노트 §9.3.5, §9.9).
- Q1–Q3이 닫히기 전에는 신규성과 MLIR의 이점을 주장하지 않는다.

## 3. 연구 문제, 결함 범주, 가정, 연구 질문

### 3.1 연구 문제와 결함 정의
- **[원노트 구상]** 대상은 앱·메시지·프레임워크 서비스·상태 갱신·lifecycle event 사이의 순서를 프로그램이 보장하는지의 정적 판정이다.
- **[설계 제안]** 입력 System은 튜플이다. cFE·OSAL·PSP revision, 앱 소스와 `compile_commands.json`, build 설정과 MID 매핑 header, table 이미지, `cfe_es_startup.scr`, 실행 가정 Σ로 이루어진다.
- **[설계 제안]** 사건 쌍 `(e1,e2)`가 다음 네 조건을 모두 만족하면 결함이다.
  1. `Req(e1≺e2)`의 근거가 있다. 근거는 cFE API 의미, 데이터 의존, 앱별 계약, 공개 결함 기록 중 하나다.
  2. 가정 없는 HB 규칙의 추이 폐포 `G0`로 증명되지 않는다. `G_A`로만 증명되면 `GUARANTEED_UNDER(가정)`로 따로 보고한다.
  3. Σ 아래에서 `e2`가 먼저 오는 실행이 있다.
  4. 관측 가능한 결과가 있고, 그것을 흡수하는 guard나 재시도가 없다.
- **[설계 제안]** 증거 수준은 L0 `CANDIDATE`, L1 `MODEL_POSSIBLE`, L2 `REPRODUCED`다. 세 수준은 따로 센다.
- **[확인된 사실]** "순서 명세 획득 → 위반 탐지" 분해는 TaxDC §8.4 [R12]에 이미 있다. 구현·평가된 검출기는 없다.
- **[해석]** 정의 자체는 기여가 아니다. 원노트 §47의 식은 조건 1–3만 담고 조건 4가 빠져 있었다.
- **[설계 제안]** 'race'는 두 순서가 모두 실행 가능하고 결과가 달라질 때만 쓴다. 정적 결과는 '후보'라 부른다. '검출'은 재현 수준에만 쓴다.

### 3.2 결함 범주 F1–F8
**[설계 제안]** 원노트 F1–F6에 F7(메시지 간 도착 순서)과 F8(재시작 창)을 더했다.

| ID | 이름 | 핵심 근거 | 공개 양성 사례 |
|---|---|---|---|
| F1 | 첫 메시지 유실 | **[확인된 사실]** 경로 없는 MID 발행도 `CFE_SUCCESS`이고 durability가 없다. **[실측]** 미구독 MID `NoSubDelta=1`, 해지한 MID `NoSubDelta=0`, rc=0 | 없음. 합성·주입 필요 **[해석]** |
| F2 | 첫 갱신 전 사용 | 메모리 초기값은 유효 입력이 아니다. `allows_default(f)` 계약으로 허용을 표시한다 **[설계 제안]** | HS #148, MD #79는 순서 무관 결정적 결함 **[해석]** |
| F3 | 갱신 경계를 넘은 사용 | β는 사건 경계다. **[확인된 사실]** header 시각은 전송 시점으로 덮어써지고 TIME은 `NOT_SET`으로 시작한다 | LC 주입(INJ-LC-1, INJ-LC-2)으로 평가 |
| F4 | 다중 stream snapshot 불일치 | 기존 정의가 있는지 **[미확인]**. child task 공유는 `UNKNOWN(atomicity)` **[설계 제안]** | 없음 |
| F5 | 시작 시 서비스·자원 의존 | **[확인된 사실]** script 앱 sync는 1000 ms soft limit이고 `WaitForStartupSync`는 void wrapper다 | #73(닫힘), #198, CF #184, #2663 |
| F6 | Table 수명 프로토콜 위반 | **[실측]** handle 단위 잠금에서 포인터 A가 1 대신 3을 읽었다. `NEVER_LOADED`는 NULL·무잠금이다 | 대부분 단일 앱 API 결함 **[해석]** |
| F7 | 메시지 간 도착 순서 | **[확인된 사실]** `550e7f7d`(v7.0.0)부터 put이 mutex 밖이다. 그래서 cFE 버전이 매개변수다 **[해석]** | 없음 |
| F8 | 재시작 창 | **[확인된 사실]** cleanup은 pipe를 지우고 경로·sequence counter는 남긴다. **[실측]** 재등록은 `DUPLICATE_NOT_OWNED` | 현재 버전 관측 하나 |

- **[설계 제안]** F6는 같은 앱 안이면 API 프로토콜 오용, 다른 앱이 끼면 순서 결함, owner 재시작이면 F8로 센다.
- **[해석]** F8에서 관측된 증상은 sharer의 옛 값 읽기가 아니라 owner 재등록 실패다.

### 3.3 실행 가정 Σ
- **[설계 제안]** 모든 보고에 System commit과 Σ를 적는다. Σ가 다른 결과는 합산하지 않는다.

| 매개변수 | 결과를 바꾸는 근거 |
|---|---|
| cFE·앱 버전 | **[확인된 사실]** `550e7f7d`, `c1ab1b7`, `d3d52da`가 의미를 바꾼다 |
| 우선순위 적용 | **[확인된 사실]** permissive mode에서 권한이 없으면 SCHED_OTHER로 조용히 강등된다 |
| CPU 수·affinity | **[실측]** relay 역전이 1 CPU에서 500/500, 4 CPU에서 0/500이었다 |
| 실효 pipe 깊이 | **[실측]** 비root는 `msg_max`=10으로 잘린다. `CAP_SYS_RESOURCE` 없는 root는 EINVAL로 초기화가 멈춘다 |
| MID 매핑 | EDS에서는 runtime 함수다. EDS는 실행하지 않았다 **[미확인]** |
| table 이미지·지상 명령 | 구독·발행 MID를 정한다 |
| startup script | **[실측]** load 순서와 완료 순서가 다르다 (6회에 6종) |

- **[설계 제안]** RQ3의 기준 Σ는 Σ1(1 CPU + SCHED_RR)과 Σ2(4 CPU + SCHED_OTHER)다.
- 제외 범위: 공유 메모리 race(#950, #2523, #1034), SB 내부 routing race(#1073), driver·interrupt, WCET, SBN·다중 노드, 다중코어 memory model, 물리 시간 freshness, 보안, 순서 무관 결정적 결함, buffer 수명, EDS build, RTEMS·VxWorks 실행이다.

### 3.4 연구 질문과 가설 (**[설계 제안]**)

| RQ | 질문 | 현재 근거 | 관문 |
|---|---|---|---|

| RQ3 | 필요 순서의 보장을 Σ별로 판정하는가 | 수정 전후 쌍 #198, CF #184, #73 파생 | GO-5 |
| RQ4 | 설계된 허용을 구별하는가 | 정상 대조 HK·Ogma·TO_LAB, AB3. 미구현 **[미확인]** | GO-6 |

| RQ6 | MLIR이 같은 의미의 대안보다 무엇을 개선하는가 | E-dialect, E-ast, E-llvm 비교. **[실측]** 154 파일 진단 0(조건부), ClangIR 사용 불가 | GO-3, GO-8 |

- H1′: code-literal·table 구독 간선의 누락이 0이다.
- H2′: 근본 원인마다 후보가 하나 이상 나오고, 정상 대조에서는 후보가 0이다. 중복은 FP11 키로 합친다.
- H3′: field 출처 ablation에서 판정 차이가 없으면 기각한다.
- **[해석]** RQ1은 기반 작업이지 기여가 아니다.

- **[확인된 사실]** #73 실패 경로: 6.4.1에서 TIME이 먼저 실행되었다. `CFE_SB_CreatePipe`가 AppId 0으로 EVS를 불렀다. `EVS_IsFiltered(0xFFFFFFFF)`가 범위 검사 없이 index해 segfault가 났다. **[해석]** 범위 밖 index는 SB AppId가 아니라 EVS sentinel이다.
- **[실측]** `546a002`에서는 24회 모두 ES, EVS, SB, TBL, TIME 순으로 init했다.
- **[실측]** #2663은 gdb `cfe_evs.c:188`에 실행당 24번 도달했다(EID 5 2번, 10 4번, 14 18번). 2회 모두 같았다. **[해석]** crash 없는 조용한 event 손실이다.
- Swift/BAT와 cFS의 관계 (검증 C22, contested):
  - **[확인된 사실]** NTRS 20090005965 'cFE Heritage' 슬라이드가 "Swift BAT (12/04)"를 나열한다. 출처는 제3자 GitHub mirror의 OCR이다.
  - **[해석]** BAT가 cFE를 실행했다는 근거는 없다. heritage의 방향은 OCR 배치 손실 때문에 추론이다.
  - 검증자 2명은 보정, 1명은 기각으로 판정했다. 그래서 cFE 이전 heritage의 동기 사례로만 인용한다.
  - **[원노트 구상]** 원노트의 `Observation(t1)+Attitude(t0)` 도식은 추론이다. 실제 구조로 쓰지 않는다.
- 지지하는 것: core startup 결함의 발생과 수정, #2663 잔여 형태, 사용자 앱 간 startup 의존(CF #184, #198), `WaitForStartupSync`의 void 반환.
- 반박된 것: "OPERATIONAL 성공은 모든 앱의 준비를 뜻한다." **[실측]** 지연 앱이 있어도 24/24에서 OPERATIONAL에 들어갔다.
- 근거 없음: 비행 중 발생, 현재 동일 결함, 원 환경 재현, Swift epoch 혼합, Swift=cFS, 검출 성능, 발생률, IV&V 판단, 신규성.
- **[해석]** F5 근거가 가장 강하다. F1·F4·F7은 공개 양성 사례가 없다. F8은 관측 하나다. F6은 대부분 단일 앱 API 결함이다.

## 5. cFS 의미론 핵심: 분석기가 모델링해야 할 사실
동작은 **[확인된 사실]**, 측정값은 **[실측]**, M 열은 **[설계 제안]**이다 (전체 노트 §3.1–§3.8).

| ID | 사실 | 측정·근거 | 모델링 (M) |
|---|---|---|---|
| SB-3 | Transmit은 lock 아래에서 목적지를 표시하고 lock 밖에서 put한다. 원자적 broadcast가 아니다 | **[실측]** 1 CPU·RR에서 200/200 반환 전 수신 실행, 4 CPU에서 6/200, 3/200 | M1 tx 종료와 handler 사이에 간선이 없다 |
| SB-5, SB-6 | 경로 없음은 counter와 EID 14 뒤 SUCCESS다. 목적지 0개는 counter·event 없이 SUCCESS다 | **[실측]** `NoSubDelta` 1과 0, sequence 1→5 | M2 발행 성공은 전달 성공이 아니다 |
| SB-2 | 구독 이전 발행은 보존되지 않는다. `CFE_SB_Qos_t`는 쓰이지 않는다 | 코드 읽기 | M3 구독과 첫 발행 사이의 HB를 증명해야 한다 |
| SB-7 | MsgLim·pipe full은 그 pipe에서만 drop하고 SUCCESS를 반환한다 | **[실측]** MsgLim 2·5회 발행에 2개 수신(+3), depth 3에 3개 수신(+2) | M4 `msglim`, `depth_eff`는 매개변수다 |
| OS-1 | pipe 안은 FIFO다. pipe 사이에는 전역 순서가 없다 | **[실측]** priority 없는 실행에서 도착 순서가 바뀌었다(15/500, 30/500) | M5 pipe 사이 순서는 HB가 아니다 |
| SB-9 | 수신 결과는 네 갈래다. buffer 포인터는 같은 pipe의 다음 receive까지 유효하다 | 코드 읽기 | M6 상태 갱신은 성공 경로에만 둔다 |
| ES-4–6 | script 앱 sync는 1000 ms polling soft limit이다. `WaitForStartupSync`는 상태를 버린다 | **[실측]** 2.5 s 지연에도 24/24 OPERATIONAL, 다른 앱 Wait는 1.95–2.01 s 뒤 성공 | M7 startup sync는 조건부 간선이다 |
| ES-7, ES-8 | RUNNING은 init 완료를 뜻하지 않는다. child task 호출은 부모 앱에 귀속된다 | 코드 읽기 | M8 분석 단위는 task, 정체성은 앱이다 |
| ES-9, ES-10 | 재시작은 요청 기록 → scan → CleanUpApp → AppCreate 순이다 | **[실측]** 1.57–1.63 s, 새 AppId | M9 재시작은 새 AppId와 re-init이다 |
| TBL-1 | 한 번도 load되지 않은 table은 `0xcc000005`와 NULL을 주고 잠그지 않는다. header 설명과 다르다 | **[실측]** R1–R4 모두 `ptr=(nil)` | M10, M11 |
| TBL-2, TBL-3 | 잠금은 descriptor 단위다. 해제 없이 다시 `GetAddress`하면 보호가 새 buffer로 옮겨 간다 | **[실측]** 포인터 A가 1이 아니라 3을 읽었다 | M10 TBL 추상 상태 |
| TBL-5 | double buffer는 활성화 때 잠금을 검사하지 않는다 | **[실측]** holder는 옛 내용, 다음 load는 `NO_BUFFER_AVAIL` | M10 |
| TBL-7 | 재시작한 owner의 Register는 `DUPLICATE_NOT_OWNED`, sharer는 `UNREGISTERED`를 받는다 | **[실측]** sharer는 약 1.5 s 동안 옛 포인터로 성공했다 | M9, M10 |
| TBL-9 | INFO 코드는 양수다 | **[실측]** Share 직후 `0x4c00000e` | M11 |
| EVT-1–3 | 등록 전 SendEvent는 실패한다. filter에 상한이 있다. SB AppId가 0인 동안 event가 사라진다(#2663) | **[실측]** gdb 24번 도달 | M12 EVS는 진단 근거로 약하다 |
| EVT-4, EVT-6 | TIME은 `NOT_SET`으로 시작한다. header 시각은 발행 시각이다 | **[실측]** syslog 시각이 1980-001에서 1980-012로 뛰었다 | M13 |
| 전체 노트 §3.7 | table·명령·build 설정이 MID를 정한다 | **[실측]** Subscribe 47곳 중 8곳이 data 구동 | M14 그래프 입력에 table·명령·설정을 넣는다 |

버전에 따라 바뀌는 의미 (**[확인된 사실]**):

| 변화 | 도입 | 영향 범주 |
|---|---|---|
| lock 밖 put | `550e7f7d` (2024-02-26, v7.0.0부터) | F7 |
| `NEVER_LOADED` NULL, 재등록 때 이름 유지 | `c1ab1b7` (2026-01-22) | F6, F8 |
| core 앱 직렬화 | 6.4.2 (2015-07-13) | F5 (#73 닫힘) |
| TO_LAB 지연 구독 | `d3d52da` (2026-04-21, v7.0.1에만 있음) | F1 정상 대조 |

- **[설계 제안]** 가정해도 되는 사실은 A1–A11이다. 예를 들어 pipe 안 FIFO(A1), 한 Transmit 안의 head-first put(A2), core 5개 `TaskInit` 뒤의 script 앱 생성(A4), `SystemState`의 단조 증가(A6)가 있다. 조건을 벗어나면 'unknown'으로 둔다.
- **[미확인]** VxWorks queue 순서와 RTOS 선점, child task의 영향, owner `Load`의 lock 밖 구간(TBL-6), `SystemState`의 다중 코어 메모리 순서는 모른다.

## 6. 선행연구와 신규성 경계

## 7. 설계 핵심
모든 dialect·pass·규칙·도메인은 **[설계 제안]**이다. 구현·실행 결과는 없다.

### 7.1 `cfs` dialect
- D1 overlay: import된 `llvm.func` 안의 `llvm.call @CFE_*`만 `cfs` op로 바꾼다. 나머지는 LLVM dialect로 둔다.
- D2: out-parameter를 SSA 결과로 꺼내고 전역이면 `cfs.state.update`로 쓴다. **[실측]** out-parameter 쓰기는 IR에서 store로 보이지 않는다. D3: handle 타입은 함수 안에서만 쓴다. D4: 주소 없는 resource는 거칠게 나눈다.
- D5: verifier와 `cfs-lint`를 나눈다. D6: Location을 보존한다. D7: 모르는 MID는 `cfs.mid.from_value`와 `#cfs.mid_src`로 두고 ⊤로 본다. D8: `cfs-close-world`가 entry 밖 함수를 private로 만든다.
- 타입: `!cfs.pipe`(**[실측]** i32), `!cfs.msgid`, `!cfs.buf`(수신 buffer 수명 토큰), `!cfs.tbl`(**[실측]** i16), `!cfs.appid`(IR 폭 **[미확인]**).
- 속성: `#cfs.mid<value,kind,name>`와 `#cfs.mid_src<kind,ref>`가 있다. `mid_src` kind는 code_const, param, table_image, cmd_payload, runtime_state, runtime_fn, unknown이다.
- resource: `CFS_SBRoutes`, `CFS_SBQueues`, `CFS_ESState`, `CFS_TBLRegistry`, `CFS_EVSState`는 주소가 없다. `CFS_TBLBuffers`만 주소가 있다.
- **[확인된 사실]** 로컬 `1053047a`에는 resource 위계가 없다. upstream `ccac700c`에는 `getParent`·`isAddressable`이 있다. 첫 구현은 로컬에 머물고 domain alias 구현 하나를 등록한다.
- op: ODS 초안은 `sb.subscribe`, `sb.receive`, `sb.transmit`, `tbl.get_address`, `state.update` 다섯 개다. 컴파일하지 않았다. op 하나는 cFE API 하나에 대응한다.
- 검사: verifier V1–V11과 lint L1–L5를 둔다. lint L1–L5는 평가의 증거 수준 L0–L2와 다른 ID다.
- lifting pass: P0 build·import, P1 `cfs-close-world`, P2 `cfs-recognize-api`, P3 `cfs-fold-mid`, P4 `cfs-resolve-fields`, P5 `cfs-bind-headers`, P6 `cfs-recover-dispatch`, P7 `cfs-attach-config` 순이다.
- **[실측]** 손으로 쓴 sample_app lifted IR은 IRDL 검사를 통과했다. neg1·neg2의 타입 오류는 잡았고 neg3는 잡지 못했다(`irdl.any`).
- **[해석]** IRDL로 보인 것은 타입 구분뿐이다. IRDL에는 `MemoryEffectOpInterface`가 없어 effect가 필요한 op는 ODS/C++로 정의해야 한다. effect, V1–V11, pass는 확인하지 않았다.

### 7.2 사건 모델과 HB 규칙
- 원칙 AP1–AP6:
  - AP1 `G0`에는 Σ와 무관한 규칙만 둔다. 가정이 필요하면 `G_A`에만 둔다.
  - AP2 `Req`는 `G`를 보지 않고 만든다. AP3 상태 변경 사건은 API 성공 경로에만 둔다. 반환을 검사하지 않은 호출은 `unchecked`다.
  - AP4 정보 손실은 경고가 아니라 `unknown`이다. AP5 결과는 세 증거 수준이다. AP6 의미 모델은 cFE 버전을 인자로 받는다.
- 사건: `sub`, `unsub`, `tx.b`/`tx.e`, `enq`/`drop(why)`, `rcv`, `hdl(b,m,cc)`, `w(b,f,o)`, `r(b,f,u)`, `ready`, `waitok`, `sys`, `tget`/`trel`/`tact`, `treg`/`tunreg`, `rst.req`/`rst.clean`/`rst.create`. `drop`의 이유는 NO_ROUTE, ZERO_DEST, MSGLIM, PIPE_FULL, INACTIVE 중 하나다.
- `r`은 분기 조건, transmit payload, 모델 없는 외부 호출 인자로 흐를 때만 소비다. `CmdCounter++` 같은 read-modify-write는 소비가 아니다.
- 한정자 `once`, `first`, `each`를 둔다. task 사이 순서는 `once`·`first` 사이에만 만든다. "k번째 발행과 k번째 수신" 관계는 표현하지 않는다.

### 7.3 추상 도메인
- 상태는 `σ♯ = (Prov, Mem, Aux, Facts)`다.
- **[실측]** `LocalAliasAnalysis`는 서로 다른 전역을 MayAlias로, `llvm.call`을 모든 위치에 ModRef로 판정했다. 그래서 field를 `(전역 symbol, 상수 byte 범위)`로 식별한다.
- 출처 `Origin`은 `Msg`, `Tbl`, `Init`, `Const`, `OutParam`, `Time`, `Param`, `Unknown(reason)` 중 하나다.
- 상관 보존: field별 출처 집합의 합은 가짜 조합을 만든다. 그래서 경로별 공동 배정 `Joint`의 집합 `Disj(S)`를 쓴다. `|S| > K`면 `NonRel`로 사영하고 `lostAt`을 기록한다. K는 4, 16, 64로 돌려 `lostAt`이 더 줄지 않는 최소값을 기본으로 한다. widening 없이 높이가 유한하다. **[미확인]** 갈루아 연결 건전성은 증명하지 않았다.
- 초기화 격자는 `Mem(f)` ∈ {ZERO_STATIC, WRITTEN, UNDEF, ⊤}, `Inp(f)` ∈ {⊥, NONE, RCVD, MAYBE}, `Val(f)` ∈ {VALIDATED, UNCHECKED}다. `Inp`를 출처에서 유도하므로 guard 분기가 Joint를 걸러 guard를 인식한다. Aux는 `bufOf`, `tblPtr`(PROTECTED, UNPROTECTED, RELEASED, NULL), `subs`, `readyMark`, `status`를 담는다.
- freshness는 사건 경계 β("MID `m_β` handler 진입")로 잰다. timestamp 층은 계약이 있을 때 F4 guard 인식에만 쓴다. 원노트의 20 ms, 100 ms는 기준값으로 쓰지 않는다.
- 함수 사이: `--inline` 뒤 `setInterprocedural(false)`로 두고, 남은 호출은 summary와 API 모델로 처리한다. **[해석]** upstream 기본의 context-insensitive 합류는 상관을 깬다.
- **[확인된 사실]** dataflow solver에는 thread 개념이 없다. task 사이 순서는 solver 밖 그래프 엔진 `BUILD_HB`에서 계산한다.

### 7.4 판정 파이프라인
- 처리 단계는 S1 frontend → S2 보조 입력(AST, table 이미지, MID header) → S3 closed world → S4 lifting → S5 구조 복원 → S6 task 내부 분석 → S7 사건과 `G0`·`G_A` → S8 `Req` → S9 판정이다.
- `Req` 규칙 (`G`를 입력으로 받지 않는다):
  - R-F1c는 계약 `must_receive_first`가 있을 때만 만든다. R-F1i는 일회 발행, 다른 발행 site 없음 등 네 조건에서 추론한다.
  - R-F2는 계약 없이 만든다. 단 `allows_default(f)`면 만들지 않는다. R-F5(API 전제, 늦은 초기화)와 R-F6(table typestate)도 계약 없이 만든다.
  - R-F3, R-F4는 계약(`requires_updated_since`, `requires_same_instance`, `requires_same_cycle`)이 있을 때만 만든다. 없으면 F4는 latest-value 조합 목록만 낸다.
  - R-F7c는 계약 `order(m1,m2)`, R-F7i는 relay 구조에서 추론한다. R-F8은 sharer 해제가 owner 재등록보다 앞서야 함을 뜻한다. 추론으로 얻은 `Req`는 `inferred`로 따로 센다.
- 판정 순서는 처음 맞는 하나다: `UNKNOWN(flags)` → `GUARANTEED` → `GUARANTEED_UNDER(A′)` → `NO_EFFECT` → `SUPPRESSED(reason)` → `VIOLATED_ALWAYS` → `CANDIDATE`.
- `CANDIDATE` 위에 `MODEL_POSSIBLE`(witness)과 `REPRODUCED`(재생 성공)를 둔다. `unchecked` 사건을 `e1`로 둔 `Req`는 `GUARANTEED`가 될 수 없다.
- witness 탐색은 관련 앱만 자른 유한 상태 모델에서 한다. 기본 `k_m = 2`, loop 3회다. 못 찾으면 "한계 안에서 발견 안 됨"이며 안전 증명이 아니다. 탐색 도구는 정하지 않았다.
- 재현은 native build에서 N회 재생하고 `CLOCK_MONOTONIC`으로 순서를 확인한다. **[해석]** 이 결과도 RTOS 비행 build의 증거가 아니다.

## 9. 평가 계획 핵심
모두 **[설계 제안]**이다. 검출률이나 분석 시간 결과는 없다.

- 평가 단위는 경고가 아니라 결함 사례다. 사례는 범주, 순서 쌍, 상태 field·자원, consumer 위치, producer MID·API로 정한다. 경고는 `dedup_key`로 대응한다.
- 증거 수준은 따로 센다. L1은 분석기 작성자가 아닌 label 담당자가 witness를 source에서 확인해야 한다. L2는 native 빌드에서 잘못된 상태·동작을 관측해야 한다.
- **[해석]** L1을 L2로 보고하면 "HB를 증명하지 못한 것과 race는 다르다"는 원칙을 어긴다.
- 필요 순서의 출처는 넷 중 하나다. API 문서·구현, 앱 주석·설정, 공개 이슈 원인, 분석기 실행 전에 별도 작성자가 동결한 계약이다. 출처가 없으면 label이 없다.

| 층 | 내용 | 기대 판정 |
|---|---|---|
| (a) 합성 앱 | SENSOR, NAV, CONTROL, GAINTBL. 사례 13개, 빌드 단위 33개 | `faulty` warn, `correct` no_warn, `benign` 허용, `conditional` 가정 명시 |
| (b) 공개 앱 결함 주입 | sample_app, HK, LC, SCH, TO_LAB, Ogma에 INJ-* 한 위치 주입. harness로 HK combined·LC sample을 켠다 | 원본 함수가 정상 대조 |
| (b′) 수정 없는 bundle | 정답 없음, recall 계산 안 함 | 경고를 "설계상 허용", "불가능", "판단 불가"로 분류 |
| (c) 역사적 결함 | H-73-derived, #198, CF #184, #2663, HS #148, MD #79, sample_app #28→#101 등 | 수정 전 warn, 수정 후 no_warn 또는 conditional |

- 모델 적합성 시험을 benchmark보다 먼저 한다. 이 시험은 이 요약본 §8의 실측값(MsgLim, depth, FIFO, 선점, OPERATIONAL 대기, TBL 잠금, owner 재시작)을 다시 잰다. 실패한 행의 범주는 benchmark를 보류한다.
- HS #148, MD #79, sample_app #101은 `order_dependent: false`로 따로 보고한다. #1073과 Swift/BAT(C22)는 제외한다.
- 정답은 사례당 YAML로 분석기 실행 전에 동결한다. 핵심 필드는 `required_order_source`와 `confirm_env`다. label은 labeler B와 reviewer C가 정한다.
- **[실측]** 환경이 결과를 바꾸므로 다른 방식의 결과는 합산하지 않는다. depth·MsgLim 의존 사례는 `unshare --ipc`에서만 돌린다.
- L2 기준은 세 가지다. `CLOCK_MONOTONIC`으로 위반 순서를 관측하고, 잘못된 상태를 한 번 이상 보고, `correct` 변형에서 증상이 0회여야 한다. 0회는 "관측되지 않음"이지 불가능이 아니다.
- 지표: TP·FP·FN 계수 규칙을 정했다. 범주 × 층 단위로 원 개수와 Clopper–Pearson 구간을 쓴다. precision은 `P_L1`과 `P_L2` 두 번 낸다. 비용은 단계별 wall time과 peak RSS의 5회 중앙값을 잰다. 의미 coverage(정답 23 site, 상태 갱신 83곳 등)와 수작업 LOC도 잰다.
- 기준선 B0–B8: B0 직접 호출 그래프, B1 MID·pipe topology, B2 CodeQL+SB 모델(미설치), B3 CSA custom checker, B4 ROSInfer식 휴리스틱, B5 model-based testing, B6 Ogma monitor, B7 TSan, B8 Goblint.
- ablation: 도메인 AB1–AB10은 판정이 바뀐 사례 목록으로 보고한다. 구현 기반은 E-dialect, E-llvm, E-ql, E-ast(3일 제한)로 비교한다. 판정이 같으면 MLIR 기여는 LOC, API 추가 비용, 진단 위치, 분석 시간, 출처 정밀도로만 주장한다.
- MLIR 내부 요소 I1–I7 중 I3–I5는 기존 pass로 풀린다. I1·I2(메모리 모델)와 I6(MID 이름)은 직접 만든다. I7은 CIR 빌드가 있을 때만 판단한다.
- 타당성 위협: 같은 연구자의 주입과 계약 순환, 결함과 허용의 경계, cFE 버전 차이, native Linux 일반화, EVS filter, 역사 사례 부족, 기준선 공정성, snippet 수준의 새로움 판단.
- 주장하지 않는 것: precision·recall·분석 시간, B2–B8 동작, 역사 사례 원 환경 재현. 합성 앱 성공은 비행 결함 검출 성능을 뜻하지 않는다.

## 10. 16주 계획과 관문

일정, 산출물, 기준, 관문, 임계값은 모두 **[설계 제안]**이다. 순서는 원노트 §66을 따른다. 고정·인벤토리 → SB MVP → startup → 다중 stream → Table Services 순이다.

### 10.1 전제
- 고정 입력은 cFS bundle `5a9b075c`와 submodule 전부다. OSAL·PSP는 bundle 값으로 통일한다. 그래서 전체 노트 §3 probe의 ES·TBL 적합성 시험은 단계 2·4에서 다시 돌린다.
- 인력은 연구자 1명이다. 독립 작성자 B(주당 약 1일)가 주입 diff, 계약, 정답 label을 쓰고 동결한다. B는 L1 witness도 확인한다. reviewer가 없으면 `reviewer: none`으로 적는다.
- **[실측]** 디스크 여유는 2.9G(사용률 93%)다. ODS dialect out-of-tree build는 성공했다(configure 2.4 s, build 8.2 s).
- **[실측]** dense 분석 골격(`setInterprocedural(false)` + `ExternalCallee` hook)이 rc 0으로 돌았다. hook 호출은 noinline 68회, inline 243회였다. 로컬에는 `isAddressable`이 없다.
- **[해석]** 그래서 live build tree는 하나만 둔다. summary-at-hook 설계는 구현 가능하다. SB·TBL effect는 분석기가 직접 해석한다.
- 원칙: 추출이 판정보다 먼저다. 23개 site 재현 전에는 race를 판정하지 않는다. 관문은 GO/PIVOT/STOP으로 닫는다. 어느 조건에도 맞지 않으면 PIVOT이다. unknown 수도 산출물이다.

### 10.4 위험과 축소안
- 주요 위험: RK-1 디스크(**[실측]** 2.9 GB), RK-2 MLIR API 차이, RK-3 data 유래 MID(47곳 중 8곳), RK-5 간접 호출 73곳, RK-7 비결정성, RK-8 옛 버전 build(**[미확인]**), RK-10 정답 순환, RK-13 선행연구 미확인, RK-15 1인 지연.

- **[해석]** 축소안에는 F3·F7·F8 결과와 수정 없는 bundle 분류가 없다. 범주가 F1, F2, F4, F5, F6로 줄고, 이를 결과 절에 밝혀야 한다.
- 병행 작업으로 문헌을 닫는다. HLDR 등은 GO-6, typestate는 GO-7, R03·SPLC 2009·WCRE 2010·ROSInfer·IV&V 2020은 GO-8 전에 읽는다.
