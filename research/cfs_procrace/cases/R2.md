## 4. Resource and its publication site

**Resource:** `CFE_SB_Global.AppId`, the ES application ID of the SB core app.
- It is used as the *event source* ID by every SB API path that emits an event.
- It is defined in [B cfe_sb_task.c L40](https://github.com/nasa/cFE/blob/fc8c48ad09460ce0277ad2bfcd81d376634aa2c6/modules/sb/fsw/src/cfe_sb_task.c#L40).

**Lifecycle at B (fact from code):**

1. **Pre-publication value.**
   - `CFE_SB_EarlyInit` runs `memset(&CFE_SB_Global, 0, sizeof(CFE_SB_Global));` ([cfe_sb_init.c L55-L61](https://github.com/nasa/cFE/blob/fc8c48ad09460ce0277ad2bfcd81d376634aa2c6/modules/sb/fsw/src/cfe_sb_init.c#L55-L61)).
   - ES calls it as an object-table function entry before any core task is created ([cfe_es_objtab.c L75-L77](https://github.com/nasa/cFE/blob/fc8c48ad09460ce0277ad2bfcd81d376634aa2c6/modules/es/fsw/src/cfe_es_objtab.c#L75-L77)).

- With the default object table and a startup that does not time out, the start of S1 is a single control flow in the ES startup thread. It forces EVS's (B) or ES's and EVS's (M, D) `*_TaskInit` to complete before the SB task is created.

## 7. Required order and its provenance

**Statement.**
- `CFE_SB_AppInit` must store a valid SB AppId (`cfe_sb_task.c` L126 at B) before any task runs an SB API path that emits an event with `CFE_SB_Global.AppId`. For the event to be generated rather than handled as unregistered, SB must also be registered with EVS (L193) first.
- For R2's callers, this means U1 (EVS init) and, at M and D, U2 (ES init) would have to run after SB's AppInit. They do not (§6.1).

**Provenance:**
1. API documentation (fact). The public header for `CFE_EVS_SendEventWithAppID` says:
   - "The Application ID must correspond to a registered application or core service." ([B cfe_evs.h L168-L172](https://github.com/nasa/cFE/blob/fc8c48ad09460ce0277ad2bfcd81d376634aa2c6/modules/core_api/fsw/inc/cfe_evs.h#L168-L172); the same text is at L169 in M and D);
   - and it lists `CFE_EVS_APP_ILLEGAL_APP_ID` as a return (L196-L200).
2. Code (fact):
   - an undefined ID gives NULL and then `ILLEGAL_APP_ID` (§4);
   - SB's AppId is undefined until L126 (§4).
3. The issue (fact, with the reporter's hedged cause): "presumably because CFE_SB has not been registered with event services".
   - Inference: code points to the **AppId publication** (L126), not the EVS registration (L193), as what selects `ILLEGAL_APP_ID`.
   - Registration alone would select `EVS_NotRegistered` (L187-L191).
   - The `CFE_EVS_APP_ILLEGAL_APP_ID` comment in `cfe_error.h` ("Application ID returned by #CFE_ES_GetAppIDByName is greater than #CFE_PLATFORM_ES_MAX_APPLICATIONS", [L260-L267](https://github.com/nasa/cFE/blob/fc8c48ad09460ce0277ad2bfcd81d376634aa2c6/modules/core_api/fsw/inc/cfe_error.h#L260-L267)) is outdated relative to the resource-ID code.
4. [R2-analysis] (`issuecomment-5588955819`): the content is not retrieved (D3). Probe terms suggest it discusses `CFE_SB_EarlyInit`/`CFE_SB_AppInit`, `CFE_SB_Global.AppId`, `EVS_GetAppDataByID` and "deterministic", but this is not evidence of what it claims.

## 11. What a derived experiment would have to assume (assumptions, not chosen)

- **A1 (revision).** cFE = B (or the bundle `9c786d25` with cfe `18651ef6`, osal `3bcb1377`, psp `9173cba3`) stands for the reporter's "cFE v6.7" on `main`. This needs D1.
- **A2 (setup).** The bundle README setup was used with unmodified `sample_defs` (default object table and platform config).
- **A3 (build options).** `OMIT_DEPRECATED` and `ENABLE_UNIT_TESTS` are unset. This is the README's "debug, permissive mode". By §4 the outcome should not depend on `OMIT_DEPRECATED`.
- **A4 (toolchain).** Ubuntu 22.04 distribution GCC and gdb. Versions are unknown, and a container image may differ from 22.04.5 (to be recorded as a `deviation` if so).
- **A5 (privileges and CPUs).** Normal user, as in the README quick-start, and the host's CPU count. Under S1 this should not change the R2 order (inference), but it changes OSAL RT priority use and timing.
- **A6 (observation).** The outcome is recorded at U0 by a recorder that does not use EVS, SB, TIME or ES `GetAppID` (roadmap §6.3 rule 5). The recorder logs task identity, the AppID passed and the status returned. A gdb breakpoint is the issue's method; it is all-stop by default, which pauses all threads but does not change S1's order (inference).
- **A7 (no startup timeout).** `CFE_ES_MainTaskSyncDelay` succeeds. Otherwise ES panics, which is a different outcome.
- **A8 (current-code arm).** M or D with the default `MISSION_CORE_MODULES` order (D4).
- **A9 (only for the D5 variant).** A role-derived arm needs the ES startup thread to be held, by event rather than by a fixed delay, after `CFE_ES_StartAppTask` returns and before the app record is finalized, until SB's `CFE_ES_GetAppID` is observed. The code allows this execution, but no reference reports it. It must be labeled role-derived and kept out of R2's original-case results.
- **A10 (contrast arm).** A "publish-first" control, e.g. reordering `MISSION_CORE_MODULES` so sb precedes es and evs at M or D, would be a **constructed configuration**. Roadmap §6.4 forbids presenting such a forced order as evidence that the original configuration races ("R2에서 SB를 임의로 먼저 실행시킨 결과만으로 원 구성에 race가 있다고 판정하지 않는다"). If used, label it a configuration variant.

## 12. Open questions

1. **Q1. ES at B.** At B the object table creates ES after SB, and S1 serializes init. Why does the report say "the ES and the EVS tasks"? Candidate explanations:
   - (a) a misattribution, since EVS-task backtraces show `CFE_ES_TaskEntryPoint` (inference);
   - (b) a locally modified object table or a different branch;
   - (c) the S7 window (D5).

   This needs the reporter's trace, the [R2-analysis] text, or an execution at B.
2. **Q2. [R2-analysis] content.** What does `issuecomment-5588955819` state: its author, its exact claims, and whether it calls the defect deterministic? What does dzbaker's comment say, and when was it posted (D3)?
3. **Q3. Execution check.** Do runs at B show exactly 3 hits, all in `CFE_EVS`, and runs at D or M exactly 6 (ES 3, EVS 3) on every boot, as §5 predicts? Is any boot different, which would be a race signal?
4. **Q4. Exact reporter environment.** Which commits, root or user, `OMIT_DEPRECATED`, compiler and gdb versions? None is stated.
5. **Q5. Intended fix semantics.** Should SB events emitted on behalf of a caller before SB is ready be attributed to SB? That would need SB's AppId before SB runs, e.g. assigned at app-record reservation, which is an order guarantee. Or should they be dropped silently (current behaviour), queued, or logged to syslog? No reference decides this.
6. **Q6. Mission reordering.** At M and D the order is a mission-level CMake list. Does any reference require es and evs before sb? The cFE comment says only that the list order is the init order.
7. **Q7. Relation to C3.** In C3's fixed 6.4.2 code the same residual path affects EVS (C3.md §8.3). Should R2 and C3 share one "SB AppId before publication" pattern in the paper's counting, or not (roadmap §9.3: C3 and R2 share the SB-readiness dependency and are "not treated as fully independent generalization cases")?
8. **Q8. Comment-date precision.** The date `2026-09-08` for `issuecomment-5588955819` rests on the comment-ID adjacency to `issuecomment-5588956244` and on the issue's last update. Exact timestamps need the API or the page.
