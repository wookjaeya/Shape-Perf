모든 실행은 한 번씩이고 모두 정상 종료했다. C1은 tx·rx를 따로 실행했다.

| 사례 | 실행 | 결과 |
|---|---|---|
| R2 | F0 1, G-I 1 | 둘 다 `Reset Type: PO` → POWER ON reset(Power Cycle)이고 EEPROM 해시가 같다. AppID 0 전달 24는 `OBSERVED_VIOLATION`(직접 포획, 반환 코드 없이 섬)이고 관계는 코어–앱이다. SB 자기 전송 5는 위반 없음(관측 상태 + A-OWNER). task–앱 귀속 24개가 같다. 보존 기록과 새 기록 네 개의 발생별 판정·근거 차이는 0이다 |

**호출 수** [M][U]

- 새 F0에서는 명령 재시작이 TO_LAB 구독보다 먼저 왔다. 원인은 미확인이다.

### 3.4 C5 준비 (`plan/c5_execution_basis_20261028.md`) [M][F]

- cFE 6.4.1(수정 전)·6.4.2(수정 후)와 OSAL 4.1.1을 기록된 URL에서 다시 받았다. 해시가 기록과 같다.
- 두 판 모두 릴리스 readme대로 빌드됐다. 소스는 고치지 않았고, 빌드 host 차이는 이탈 DV-H로 기록했다.
- build-smoke는 두 판 모두 POWER ON으로 떴다.
  - EVS 파이프 깊이 32가 `msg_max` 10을 넘어 큐 생성이 실패한다. 그래서 cFE가 1초 안에 멈추고, 사례 경로(`CFE_ES_AppCreate`)에 이르지 못한다.
  - readme의 다른 해법인 root 실행은 이 컨테이너에서 성립하지 않는다(`CAP_SYS_RESOURCE` 없음).
- A8 소스 읽기: OSAL 4.1.1은 task 표 칸 자체를 `pthread_create`의 출력 인자로 넘긴다(`osapi.c` L645). glibc 원 소스(2.12·2.17·2.39)는 그 값을 새 thread 시작 전에 쓴다.
  - 그러면 창 안의 결과는 잘못된 AppID가 아니라 `CFE_ES_ERR_APPID` 실패로 예측된다.
  - 실제 libc 바이너리의 동작과 창에 실제로 들어가는지는 실행으로만 확인된다.
- `kzgcc`는 `-m32`로 6.4.x를 계측할 수 있다. 초안 site 32/32, 30/30이 결합됐다.
- 남은 일:
  - F0 관측기는 지금 ELF64 파일만 받는다.
  - 32비트 `kz-rt-dump`는 32비트 C++ 라이브러리가 없어 링크되지 않는다.
  - 생성 뒤에 정해지는 소유 앱을 위해 정체성 결합을 넓혀야 한다.

  - H3·H4, 다른 사례
  - 수는 사례 2, 순서 구조 2, 계획, 실행 기록(R2 4, C1 176), 호출로 따로 적었다.
