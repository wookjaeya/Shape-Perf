## 0. 요약

- **외부 검토를 항목별로 검증했고, 대부분 타당했다.**
  - P0 두 건은 맞았고, 실제 문제는 검토가 지적한 것보다 넓었다.
  - R2 trace 재집계 수치는 우리가 다시 세어도 같았다: 223/229/229, 발행 전 사용 24, 호출 함수별 2/4/18.
  - 반박한 항목은 없다. 일부는 범위를 좁혀 받아들였다(§1).
- **설계를 고쳤다. SPEC은 rev 1.1이 되었다(약 2,400줄 → 3,300줄 이상).**
  - 안전성과 진행성을 분리했다.
  - 포함 관계를 유한 실행(prefix)으로 다시 세웠다.
  - 인증서에 신뢰 원장을 붙였다.
  - 준비되지 않은 사용을 세 층(프레임워크 / 호출자 / 관측)으로 따로 판정한다.
  - 평가 설계를 바로잡았다.
  - 한국어 문서 01–10, 그림, PI 결정 문서에도 반영했다. 실제 반영 결과는 §6.
- **R2 편중 지적을 반영했다(§3).**
  - 다섯 사례마다 검증 경로와 대조군을 SPEC §9.3에 규범으로 넣었다.
  - R2만으로는 Kairos 기능 22가지 중 상당수가 검증되지 않는다. 예측, 탐색기, 재시도·barrier 의미, σ_R1, hold 확인, 진행성 축, PROTECTED 인증서, 수정 전후 대조가 그렇다. 이것을 표로 정리했다.
- **바뀌지 않은 사실도 있다.**
  - 구현과 실행은 하지 않았다.
  - 실행 증거가 있는 사례는 여전히 R2뿐이다.
  - C1·C2·C3·C5의 도구 수준 증거는 분석 기준(basis) 결정이 있어야 생긴다: D22(C1), P-C2(C2), D13(C3·C5).
  - 이 결정이 없으면 논문 결과는 "단일 사례 결과"로 보고해야 한다.
- **결정 항목이 많이 늘었다.** §4에서 "지금 필요한 것", "다른 사례를 열기 위해 지금 필요한 것", "나중에 해도 되는 것"으로 묶었다.

## 2. 형식 모델에서 바뀐 것

### 2.1 안전성과 진행성의 분리 (검토 §4.1, ADR-039)

| | rev 1.0 | rev 1.1 |
|---|---|---|
| `protected`의 뜻 | 사용에 도달하는 실행이 있고, 나쁜 실행이 없고, **영구 대기도 없다** | **도달한 사용은 언제나 준비 상태(또는 허용 결과)다.** 도달하는지, 그 전에 교착되는지는 따로 판정한다 |
| 인증서가 보이는 것 | (정의와 불일치) 도달 시 준비 상태만 | 안전성만. 진행성은 `unknown(not_checked)`로 남긴다 |
| 진행성 | 판정 class 안에 섞여 있었다(good + stall이면 schedule-dependent) | **칸(σ, M)마다 따로 두는 진행성 결과.** 정하는 방법은 제한된 전수 탐색(`exh`, 경계 b 안), 또는 wait-for 사실이 있는 실제 hang뿐이다. 그 밖에는 `unknown` |
| schedule-dependent | 좋은 실행과 나쁜 실행(또는 stall)이 있음 | **같은 발생 순번에서** 좋은 witness와 나쁜 witness가 모두 있어야 한다. 순번이 다르면 `ordinal-split`이다 |

- 검토가 낸 반례(사용 전에 mutex 두 개를 엇갈린 순서로 잡는 경우)를 litmus LP-DL로 적었다.
  - 기대 결과: 안전성은 protected, 진행성은 `exh`가 stall witness를 찾음(종류 `deadlock-cycle`), 인증서만 있으면 진행성 `unknown(not_checked)`이다.
  - 표시 규칙으로 `protected`는 언제나 진행성 값과 함께 쓴다. 그래서 "무조건적인 protected"는 더 이상 나오지 않는다. 검토의 완료 조건이 이것이다.
- 결정 **D20**은 이 방식(A)을 쓸지, 아니면 인증서에 진행성 증명 의무를 더할지(B)를 묻는다. **권고는 A**다.

### 2.2 유한 실행(prefix)으로 다시 세운 포함 관계 (검토 §4.2, ADR-040)

- **문제.** timeout이 끝내 만족되지 않는 timed wait를 생각한다.
  - σ_U에서는 timeout 전이로 실행이 이어진다.
  - σ_U∞에서는 그 자리에서 멈춘 실행이 maximal이 된다.
  - 그래서 "σ_U∞의 maximal 실행 ⊆ σ_U의 maximal 실행"은 거짓이다. litmus LP-TW로 적었다.
- **고친 것.**
  - 유한 prefix 집합 Pref와 maximal 실행 Max를 따로 정의했다.
  - 포함 관계는 Pref에 대해서만 주장한다.
  - **안전성 진술**("도달한 사용은 모두 준비됨", "모두 나쁨")은 prefix 포함을 따라 옮겨 간다.
  - **존재 진술**(도달 여부, witness)과 **진행성 결과**는 σ마다, 경계 b마다 따로 계산한다.
  - σ_R1은 projection으로 비교하는 별개 시스템으로 다룬다.
  - σ_E(실제 실행)는 prefix로만 연결한다.
- `exh`의 witness와 인증서가 어긋나면 새 obligation O10으로 보고한다.

### 2.3 신뢰 원장 (검토 §4.3, ADR-041)

판정과 인증서마다 다음 네 부분을 기록한다.

| 부분 | R2 인증서의 예 |
|---|---|
| (i) `kz proofcheck`가 다시 확인한 추론 단계 | MustBefore 유도, frontier의 경로 없음, once 사실, writer 제외 규칙 |
| (ii) 추출기에 의존하는 사실 | `facts.kz`의 writer 집합, 추출한 predicate, skeleton 그래프(call graph, loop 처리) |
| (iii) 신뢰한 프로파일 항목과 가정 | 프레임워크 규칙 R19(core 직렬화), `DECLARED_TRUSTED` 항목, 가정 A-* |
| (iv) 관측으로 반박할 수 있지만 증명하지 않은 것 | obligation O1–O9 검사와 그 상태 |

문서의 "독립 검증"은 이제 "추출된 사실 위에서 추론 단계를 독립적으로 다시 확인"이라고 표현한다.

## 3. 다섯 사례 검증 경로 (R2 편중 지적에 대한 답)

### 3.1 R2만으로 검증되지 않는 것

R2는 "모든 실행에서 이미 보이는 잘못된 순서를 증명할 수 있는가"만 시험한다. 다음은 시험하지 못한다.

- **잘못된 증명을 삼가는가.** 성립하지 않는 순서를 증명하지 않는지 보려면 다른 사례의 '인증서 보류' 행이 필요하다.
- **실행에 안 보이는 순서를 찾는가.** lock을 뒤집는 예측, 탐색기, schedule-dependent 판정, hold 확인 실행이 해당한다.
- **허용 결과·σ·진행성 의미가 맞는가.** 재시도(C1), barrier(C2), σ_R1 우선순위(C3), lock 구간 틈(C5), `timeout-dependent` 같은 refinement, 진행성 축이 해당한다.
- **PROTECTED 인증서와 수정 전후 대조.** R2는 upstream 수정이 없다.

전체 22개 항목의 대조표는 `Architecture/08_roadmap.md`의 사례 행렬과 SPEC §9.3에 있다.

## 5. 아직 하면 안 되는 주장 (추가분)

- Kairos가 R2 외의 사례에서 무엇을 보였다. 다른 사례는 기준 결정 전이고, v7.0.1 대응물에서 나온 결과는 그 사례의 증거가 아니다.
- protected 인증서가 사용 지점에 도달한다거나 교착이 없다고 보장한다. 인증서는 안전성만 말한다.
- σ_U에서 증명한 결과의 존재 부분이나 진행성이 다른 σ나 실제 실행에서도 성립한다.
- 인증서를 "독립적으로 검증했다". 정확히는 신뢰 원장에 적힌 기반 위에서 추론 단계를 다시 확인한 것이다.
- recall mutant 결과가 맹검이다. 노출·동결 기록이 생긴 뒤에만 주장할 수 있다.
- 단순 감시기가 R2를 못 잡는다. 같은 조건을 받으면 잡는다. Kairos의 추가 가치는 분류와 증거에서만 주장한다.
- 이전 STATUS들의 주장 금지 목록도 그대로 유효하다.

## 7. 제 판단과 위험

- **형식 수정은 꼭 필요했다.** P0 두 건은 논문의 보장 문장(G2)을 거짓으로 만드는 결함이었다. 이제 정의, 인증서, 결과 표시가 맞는다. 다만 lemma 증명 의무는 아직 "써야 할 목록"이다(V0-P).
- **복잡도가 늘었다.** SPEC이 38% 커졌고 결정 항목도 늘었다. 검토자가 경고한 "범위 과대"가 설계 문서 쪽에서 다시 커질 위험이 있다. 그래서 권고한다:
  - §4.1의 결정이 나면 형식 코어를 동결한다.
  - 바로 V1(R2 끝까지) 구현으로 넘어간다.
  - 다른 사례는 §4.2의 기준 결정만 먼저 받고, 코드 읽기와 기대 판정표 동결(결정 불필요)을 V1과 병렬로 진행한다.
- **R2 편중은 구조적이다.** v7.0.1에서 결함 코드가 실행되는 사례가 R2뿐이기 때문이다. 이것은 숨기지 않고 사례별 경로와 F1 조건(P-F1GATE)으로 관리한다. 대신 C1·C3·C5에는 R2에 없는 수정 전후 쌍이 있어서, 기준 결정이 나면 오히려 더 강한 대조 검증을 할 수 있다.
