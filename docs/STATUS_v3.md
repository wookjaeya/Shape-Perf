# v3 게이트 현황 (계획서 `docs/research_plan_v3.md` §10, §15)

범례: **완료** = 실행하고 증거 파일로 확인함 · **부분** = 일부만 실행 · **불가** = 이 환경에서 할 수 없음 · **미실행**

**모든 시간 수치는 개발 컨테이너(4 vCPU KVM, 호스트 공유 여부와 이웃 부하를 확인할 수 없음)에서 얻었다. 계획서 §9.1에 따라
이 컨테이너의 timing은 본 결과가 아니며, 아래 수치는 (a) 타당성 점검, (b) 다음 실험(측정 VM)의 설계 입력으로만 쓴다.**
계획서와 다르게 한 일·못 한 일은 [`design_amendment.md`](../design_amendment.md) 8절에 모두 적었다.

## G1 pilot

**설계**: 길이는 sig-v3 census의 structural class별 lower median + {41, 256}(timing과 무관, `g1_lengths.json`) = 15개.
길이마다 5블록, 블록마다 3 arm(S8, S1, S8의 byte-identical 복사본 = A/A) × 2프로세스, 프로세스당 warmup 2 + 측정 16회,
길이·arm×프로세스 순서는 seed 무작위, CPU 1개 고정, 통제 입력. 효과는 블록 안 `a = log T_S8 − log T_S1`, 요약은 process 산술 평균(주),
median·min(보조). 추론 단위는 블록.

**컴파일·IR (15/15)**: `u(L)=max({1}∪{k∈2..8: L mod k=0})`로 예측한 IR 차이가 15개 모두 맞았다. `u≥2`인 13개 길이에서 S8의
K형 transpose 13개(12개 `[0,2,3,1]` + 마지막 `[2,0,1]`)가 unroll 루프로 남고 S1에서는 사라진다(정규화 diff 13 hunk).
`u=1`인 41, 149는 S8과 S1의 `.so`가 바이트 동일(예측대로, 음성 대조). Q/V형(`[0,2,1,3]`)은 `blockTranspose` 경로라 패치가 닿지 않고
IR이 동일(음성 대조).

**정확성**: S8과 S1의 출력이 **30/30 쌍(길이 15 × 통제·자연 입력)에서 비트 단위로 동일**. 정적 shape·반복 동일성·유한성 통과.
ORT 대비 유효 위치 최대 절대차 1.47e-5, argmax 전부 일치(허용치는 정하지 않음, 기술 통계).

**시간 (개발 컨테이너, 결과 아님)**

| 항목 | 값 |
|---|---|
| 측정 기록 | 450 프로세스, 실패 0 |
| 반복(iteration) sd / 프로세스 sd | 4.3% / 2.5% (log 스케일) |
| 블록 sd (S8/S1, A/A) | 2.95% / 2.26% |
| 길이 15개에서 `a`의 평균 | −0.12% (길이 간 sd 1.0%), A/A: −0.60% (길이 간 sd 1.2%) |
| 평균 95% 구간이 0을 제외한 길이 | S8/S1 1개(L=147, +1.6%), **A/A 3개** — 같은 실행물끼리도 15개 중 3개가 "유의" |
| 후보 (사전에 정한 선별 규칙) | **0개** |

- A/A의 구간이 15개 중 3개에서 0을 제외했다는 것은 이 환경의 구간이 반보수적(실제보다 좁음)이라는 뜻이다. 그래서 L=147의 +1.6%도
  효과로 읽지 않는다. (선별 규칙은 위 표를 본 뒤에 적었다 — `analysis/g1_pilot_report.py`의 docstring에 명시.)
- **판단 불가와 부재의 구분**: 이 pilot은 "블록 5개로 |효과| ≳ 4.5%(A/A 블록 sd의 2배)를 넘는 길이는 없다"는 것까지만 말한다.
  1% 미만의 효과는 이 환경에서 볼 수 없다(블록 sd 2.95% 기준 검출력 80%에 1%는 길이당 약 69블록, 0.3%는 757블록 필요).
  "모든 길이에서 손해가 없다"는 결론이 아니다(계획서 G1).
- **비용 추정(이 컨테이너)**: 블록 1개(3 arm × 2프로세스) 평균 58.5초(L=41: 20초, L=256: 114초, 선형 근사 ≈ 0.44·L초).
  216개 길이 × 5블록 ≈ 19시간, 69블록이면 ≈ 263시간. 컴파일은 길이·arm당 ≈ 83초(3 병렬), 216 × 2 ≈ 3.3시간. 저장은 길이·arm당 약 0.42 GB.
  → 전 범위 정밀 측정은 이 방식으로는 예산 문제가 크다. 측정 VM에서 잡음이 줄지 않으면 "예산 내 정밀도 부족 → 판단 불가"(계획서 §15).

**G1 판정**: 계획서의 진행 조건(재현 가능한 역전 후보 + 조사할 구조적 결정 + 예산 내 정밀도)을 이 pilot에서 **충족하지 못했다**.
정확성 실패는 없다. 중단 사유 중 "통제 불가능한 잡음"과 "후보 없음"이 이 환경에서 해당한다. 아래 G2는 G1 결과에 따르지 않고,
낮은 비용으로 얻을 수 있는 원인 진단(모델 전체의 잡음을 피한 단일 op 측정)을 추가로 실행한 것이다.

## G2 (진단으로 대체한 부분)

**단일 op 실험**: 실제 ORT 활성값으로 K형·Q형 transpose를 한 op씩 컴파일해 S8/S1을 프로세스 분리로 측정했다(길이 K 15개 + 보충
6개, Q 5개). 출력이 입력의 정확한 순열임을 측정 프로세스 675 + 432 + 225개 모두에서 확인(실패 0).

**1. 낮은 길이의 큰 효과는 측정 장치 artifact다 (철회)**

| 길이 | 프로세스당 arm 하나(fresh) 결과: S8이 S1보다 | A/A |
|---|---|---|
| L=63 / 64 / 65 | +45% / +38·41% / +25% (절대 +6~10 µs) | ≈ 0 |
| L=96 | +12.5% (절대 +8 µs) | ≈ 0 |
| 그 외(L=41, 100–256, 128, 192) | 점 추정 −1.4~+1.6%, 구간은 모두 0 포함(L=150만 [+0.1,+2.6]%, 16개 조건 중 1개) | ≈ 0 |

처음에는 이것이 "unroll이 낮은 L에서 손해를 만든다"는 후보처럼 보였다. 같은 산출물을 프로세스 안에서 로드 순서를 바꿔 측정하자(요인 설계,
L=63/64/96) 결과가 뒤집혔다.

- **한 프로세스에서 먼저 로드한 `.so`가 그 프로세스의 타이밍 수준을 정한다.** S8을 먼저 로드하면 두 arm 모두 ≈ 28–30 µs,
  S1을 먼저 로드하면 두 arm 모두 ≈ 18–20 µs(L=63/64; L=96은 ≈ 64 대 70 µs). 어느 arm의 코드를 재느냐는 수준을 바꾸지 않는다.
- 즉 "S8이 느리다"는 관측은 arm 코드의 성질이 아니라 **로드 순서/프로세스 상태와 arm이 교락**된 결과다. 같은 파일 복사본(A/A)은
  파일 배치가 같아 이 교락을 잡지 못한다(A/A ≈ 0이었음).
- 원인(메모리 배치·힙 상태 등)은 **규명하지 못했다**. `MALLOC_MMAP_THRESHOLD_`/`MALLOC_TOP_PAD_` 조정으로는 간격이 사라지지 않았다
  (`results/v3/g2/diagnostics/context_L64_*`).
- 로드 순서를 고정한 채 S8과 S1을 비교하면(L=63/64/96 × 2개 순서, 블록 5–6개) 여섯 조건 모두 점 추정이 +1~+7%(절대 +0.2~+3.2 µs,
  S8이 느린 방향)이지만 **모든 95% 구간이 0을 포함**한다(구간 폭 ≈ ±10%). 방향은 가설과 같으나 이 정밀도에서는 잡음과 구분되지 않는다.
- **방법론 결과(측정 VM용)**: 같은 프로세스 안에서 arm을 짝지어 로드 순서를 무작위화하거나, 프로세스당 arm 하나를 쓰되 로드 순서를 통제해야 한다.
  파일 복사본 A/A만으로는 이런 파일 의존 상태를 검출할 수 없다.

**2. 최종 코드 확인 (objdump, K_L64/96/128/147/192/256)**: 두 arm의 최종 코드는 크게 다르다. S1의 계산 함수는 S8보다 명령이 1.9–5.0배 많고
(L=147: 602 → 1897), 후방 분기가 6–10개에서 38–50개로 늘며, `vgatherdps`가 크게 늘고(L=64/96: 0 → 96/144, L=147: 28 → 216,
L=256: 64 → 384), S1은 zmm 명령을 쓰지 않는다(ymm/xmm만). S8은 L=96을 뺀 5개 길이에서 zmm 명령이 84–224개다(L=96의 S8은 0개). scatter 명령은 어느 쪽에도 없다. 즉 **IR 차이는 최종 코드에서도
유지되어 LLVM이 지우지 않았다**. 그러나 이 코드 차이가 실행 시간 차이로 이어진다는 증거는, 로드 순서를 통제한 뒤에는 이 정밀도에서 얻지 못했다.

**3. 전체 모델과의 연결 (산술 상한)**: 12개 K형 transpose × 1개당 시간 차이 ÷ 모델 지연(L=64에서 ≈249 ms, L=256에서 ≈1045 ms).
artifact가 부풀린 fresh-process 차이(+9 µs)를 그대로 넣어도 **≈ 0.04–0.05%**(L=64), 로드 순서를 통제한 효과로는 ≲ 0.01–0.02%.
G1의 모델 전체 `a`(−0.12 ± 1.0%)와 모순 없고, 이 pilot으로는 모델 전체에서 직접 관측할 수 없는 크기다(잡음 ≳ 3%).

**4. 못 한 것**: D8/D1(정적 대 동적 L)은 만들지 않았다. 다른 VM 할당에서의 재측정은 측정 VM이 없어 **불가**. 전 범위 커널 스캔은 그 장치가
로드 순서에 교락돼 있어 **중단**했다(규모 시험 기록 27개가 `results/v3/g2/timing/interleaved_in_process_test.jsonl`에 남아 있으며 분석에 쓰지 않았다).

## 계획서 §15에 따른 결정 (이 컨테이너 기준, 잠정)

| 관측 | 결정 |
|---|---|
| 최대 16개 길이 pilot에서 후보 없음 | 전 범위 부재를 주장하지 않는다. 확장은 별도의 비용 근거가 있을 때만 |
| MLIR 구조 차이가 runtime 차이를 설명하지 못함 | IR·최종 코드 차이는 확인됐으나, runtime 차이는 관측되지 않았거나 이 환경의 정밀도(커널 ±10%, 모델 ±3% 이상) 아래다. **이 환경에서 가설은 지지되지 않았지만**, 정밀도가 부족하므로 기각도 선언하지 않는다. 공식 판단은 측정 VM에서의 재확인이 있어야 한다 |
| 약수·remainder만으로 예측 충분 | 이번 실험은 IR 차이가 `u(L)`(약수 산술)로 정확히 예측됨을 확인했으나, 그 차이의 runtime 비용은 미확인. 따라서 컴파일 정보의 추가 예측력을 주장할 근거가 없다 |
| 예산 내 정밀도 부족 | 판단 불가. 유의해질 때까지 측정하지 않는다 |

**G3 이후는 진행하지 않는다**: 사전등록할 후보가 없고 측정 VM이 없다. `protocol_v3.json`은 초안이며 `null` 항목은 채우지 않았다.

## 다음에 할 수 있는 일 (실행하지 않음)

1. 측정 VM(CPU 모델·ISA·vCPU·SMT·NUMA·allocation ID 기록 가능)에서 같은 pilot을 반복하여 잡음 수준을 확인한다. 이때 로드 순서를 통제한
   인-프로세스 짝짓기 측정을 사용한다.
2. 잡음이 충분히 낮고 후보가 생길 때만 G2의 다른 VM 할당 재측정과 D8/D1을 진행한다.
3. 잡음이 그대로면 이 컴파일러 결정의 모델 수준 효과는 이 방식으로는 판단 불가로 보고한다(상한 ≲ 0.05%는 커널 측정×12의 산술 추정이며 직접 관측이 아님).
