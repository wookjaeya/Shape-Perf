### 1.2 Buggy-side cFE behavior (single readiness barrier)

All of the following is identical in cFE 6.4.2 (tarball) and v6.5.0a (git). Permalinks use tag `v6.5.0a` = `b2765d9f905aa11f0c3b419b62233597366a7db9`, whose `cfe/` tree is byte-identical to the import commit 792f5e35 (`git diff --stat` empty).

- **System states defined.** UNDEFINED, EARLY_INIT, CORE_STARTUP, CORE_READY, OPERATIONAL ("normal operation mode"), SHUTTING_DOWN. There is no intermediate app-init state. https://github.com/nasa/cFE/blob/b2765d9f905aa11f0c3b419b62233597366a7db9/cfe/fsw/cfe-core/src/es/cfe_es_apps.h#L90-L95
- **`CFE_ES_WaitForStartupSync` declares the caller ready, then waits for OPERATIONAL.** https://github.com/nasa/cFE/blob/b2765d9f905aa11f0c3b419b62233597366a7db9/cfe/fsw/cfe-core/src/es/cfe_es_api.c#L642-L694
  - L660-L663: "An application calling CFE_ES_WaitForStartupSync() is assumed to have completed its initialization and is ready to run. This is required, or else the sync delay will end up waiting for itself, or could deadlock by two apps waiting for each other, etc."

  - L681/L685: core apps wait for `CORE_READY`; all other apps wait for `CFE_ES_SYSTEM_STATE_OPERATIONAL`.
  - L692: `CFE_ES_ApplicationSyncDelay(MinSystemState, TimeOutMilliseconds);`
- **`CFE_ES_RunLoop` also marks the app RUNNING on its first call.** It says "The first time an App calls this function, change the state from INITIALIZING to RUNNING. This is for the startup syncronization code below". https://github.com/nasa/cFE/blob/b2765d9f905aa11f0c3b419b62233597366a7db9/cfe/fsw/cfe-core/src/es/cfe_es_api.c#L576-L587

**Inference.** At this revision, one call to `CFE_ES_WaitForStartupSync` both publishes "I am fully initialized" (RUNNING) and subscribes to "everyone is RUNNING" (OPERATIONAL). P needs the barrier *before* its late init, because it needs the other apps loaded. P therefore publishes RUNNING before its late init, contrary to the documented assumption (L660-L663; header "last item of an Apps initialization"). ES then enters OPERATIONAL and releases R while P is still in late init. The single-state API cannot express both directions of the dependency. This matches issue sentences 5-7.

## 7. Required order and its provenance

**Statement.** P's late-phase initialization must complete before other applications make requests to P. Equivalently, an app is "completely up and running", and may be the target of requests, only after its late init.

**Provenance.**
- Issue #198 sentences 4 ("An application would need to also complete this "late" initialization in order to be considered completely up and running"), 5b-5c ("requests can be made to an application that has not been fully initialized" is called "a race condition") and 7 (the observed violation).
- Corroborated by the fixed cFE definitions: OPERATIONAL = "normal operation mode; all apps are RUNNING"; RUNNING = "All initialization is complete. Second sync point." (https://github.com/nasa/cFE/blob/8811c92094512975e14fd545df355705141560b2/fsw/cfe-core/src/inc/cfe_es_extern_typedefs.h#L178-L215).

Kind of provenance: original report (issue text) plus API semantics in the fix. It is not derived from P's code, which is private.

A secondary order from the same text: P's late init needs the other apps "fully loaded" first (sentence 6a). That is P's reason for calling the sync before late init.

  - Release tag: `v6.6.0a` = `8811c92094512975e14fd545df355705141560b2`.
  - Linkage to #198 is an inference (D1).
- **What changed** (6.5.0a → 6.6.0a, read from code):
  1. New system state `CFE_ES_SystemState_APPS_INIT = 4`: "startup apps have all completed their early init, but not necessarily operational yet". OPERATIONAL moves to 5. https://github.com/nasa/cFE/blob/8811c92094512975e14fd545df355705141560b2/fsw/cfe-core/src/inc/cfe_es_extern_typedefs.h#L178-L215
  2. New app states `EARLY_INIT`, `LATE_INIT`, `RUNNING`, … with documented order "UNDEFINED -> EARLY_INIT -> LATE_INIT -> RUNNING -> WAITING -> STOPPED". `AppStartedCount`/`AppReadyCount` are replaced by per-app state. …/cfe_es_extern_typedefs.h#L260-L310
  3. New public API `int32 CFE_ES_WaitForSystemState(uint32 MinSystemState, uint32 TimeOutMilliseconds)`. Doc: "allows an app to wait for the rest of the apps to complete a given stage of initialization before continuing… This API assumes that the caller has also been initialized sufficiently to satisfy the global system state it is waiting for, and the apps own state will be updated accordingly." https://github.com/nasa/cFE/blob/8811c92094512975e14fd545df355705141560b2/fsw/cfe-core/src/inc/cfe_es.h#L616-L645
     - Implementation: waiting for APPS_INIT sets the caller to `LATE_INIT`; waiting for OPERATIONAL sets it to `RUNNING`. Returns `CFE_ES_OPERATION_TIMED_OUT` on timeout. https://github.com/nasa/cFE/blob/8811c92094512975e14fd545df355705141560b2/fsw/cfe-core/src/es/cfe_es_api.c#L584-L673
  4. `CFE_ES_WaitForStartupSync` becomes a wrapper `CFE_ES_WaitForSystemState(CFE_ES_SystemState_OPERATIONAL, …)` (…/cfe_es_api.c#L676-L689). Its return value is discarded; it returns `void`.
  5. ES main task becomes two-phase. https://github.com/nasa/cFE/blob/8811c92094512975e14fd545df355705141560b2/fsw/cfe-core/src/es/cfe_es_start.c#L198-L233
     1. Start apps.
     2. `CFE_ES_MainTaskSyncDelay(CFE_ES_AppState_LATE_INIT, CFE_PLATFORM_ES_STARTUP_SCRIPT_TIMEOUT_MSEC)`.
     3. Set `APPS_INIT`.
     4. `CFE_ES_MainTaskSyncDelay(CFE_ES_AppState_RUNNING, CFE_PLATFORM_ES_STARTUP_SCRIPT_TIMEOUT_MSEC)`.
     5. Set `OPERATIONAL`.

     On each timeout it only logs and continues. `MainTaskSyncDelay`: …/cfe_es_start.c#L949-L1005.
  6. `CFE_ES_RunLoop` calls `CFE_ES_SetAppState(AppID, CFE_ES_AppState_RUNNING)` (…/cfe_es_api.c#L520).
- **Kind.** Order guarantee: a new startup barrier phase. It is opt-in and bounded by soft timeouts. It is not a retry and not a guard at the use site.
- **What it guarantees** (code reading; the conditions are inference from the cited lines):
  - G1. Suppose P calls `CFE_ES_WaitForSystemState(CFE_ES_SystemState_APPS_INIT, T)` after early init, then does late init, then becomes RUNNING (first `CFE_ES_RunLoop` or `CFE_ES_WaitForStartupSync`). Then ES does not set OPERATIONAL until P is RUNNING, so any R blocked in `CFE_ES_WaitForStartupSync` / `WaitForSystemState(OPERATIONAL)` is released only after P's late init. **Unless** the ES phase-2 wait times out (`CFE_PLATFORM_ES_STARTUP_SCRIPT_TIMEOUT_MSEC`, sample 1000 ms at 6.6.0a; soft limit, "continue anyway"), or R's own wait times out.
  - G2. When `APPS_INIT` is entered, every started app has at least reached LATE_INIT (early init done), so P's late init may talk to them. Same timeout caveat.
  - Not guaranteed:
    - ordering among the late-init phases of two apps that both wait for APPS_INIT;
    - requests from apps that do not wait on OPERATIONAL (e.g., call `RunLoop` directly);
    - apps started after startup (the doc limits `WaitForStartupSync` to startup-script apps);
    - any notification to R that a timeout happened (`WaitForStartupSync` returns void; open #1466/#1467).
  - Backward-compatibility note (fact, …/cfe_es_api.c#L632-L637): "a call to "CFE_ES_WaitForSystemState()" implies that the calling app MUST also be in the requisite state. This is hooked into here to avoid needing to update all existing apps…". An app that keeps the 6.4.2 pattern (calling `WaitForStartupSync` *before* late init) still declares RUNNING early. **Inference: the fix requires P to change its code to use APPS_INIT. It does not repair the original EVA CWS call pattern by itself.**
