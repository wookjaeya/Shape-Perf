## 2. 구성 (SPEC rev 1.4, ADR-059)

분석기 하나에 실행 경로가 둘이고, 두 경로는 같은 사건·제어 의미를 써서 중립 사건 계층에서 만난다.

| 구성 | 내용 |
|---|---|
| 공통 분석 | Φ 프로필, `kz-static`(코어 + 적재 `.so` 결합 닫힘, 계측 빌드용 B′), `kz replay`, `kz predict`(탐색 전 기록–모델 적합성 검사: 모순이면 거부, 가정·정보 부족은 나열) |
| 공통 의미 | `kairos/docs/event_semantics.md`: 사건 정보, 순서 근거 4종(기록 순서는 HB가 아님), 보류 규칙 `kzp-hold 1`, 실현 제어 기록, 보류 가능 문맥 |
| 기록 형식 | 개정 3 중립 사건 계층. 기존 기록은 그대로 읽고, 변환해도 재생 결과가 같음 |
| F0 경로 | 재계측하지 않은 기준 빌드를 밖에서 관측(uprobe·tracefs), 보류는 `kz hold`(ptrace + 디버그 레지스터) |
| 계측 경로 | GCC plugin `kzgcc` 0.2 + 공통 C 런타임 `kzrt` 0.3.0. 관측점 목록 `kzs-sites 2`(정체성 읽기 포함), `kz convert`, `kz rtplan`. 한 바이너리에서 모드로 G-I0(off)·G-I(기록)·G-I-H(기록 + 보류) |
| 계측 경로를 둔 이유 | 코드가 실제로 쓴 값을 직접 포획(호출 인자, 성공 경로의 out 값 store), 관측점을 컴파일 시점에 결합(꼬리 점프·줄 정보 없는 빌드 문제 없음), 디버그 레지스터·ptrace 한도 없는 보류 |
| 시험 | 기본 빌드 179 중 178, LLVM 빌드 201 중 200 통과(각 1개는 tracefs 조건부 건너뜀), plugin 14/14, 런타임 60/60. 구현 품질 확인용이며 사례 표본이 아님 |

컴파일러 연결부는 GCC plugin, Clang 소스 변환 → gcc 빌드, LLVM pass를 같은 C1·R2 관측점에서 비교해 GCC plugin을 주 구현으로 골랐다(`plan/instrumentation_selection_20261026.md`). 나머지 둘은 비교 기록으로 남긴다.

### 3.3 C1 — 계측 경로

| 실행 | 결과 |
|---|---|
| G-I 자연 (네 빌드 × tx·rx, 8회) | 호출별 판정과 앱 관계가 F0와 대응. 이름·id(`0x30002`, `0x30003`) 같음. 수정 후 성공 조회 8건(기록마다 2건)은 후속 근거 규칙 뒤 store 값에 근거하므로 F0와 근거 표시가 다름 |
| 반환 코드 독립 근거 | 그 8건은 `nocode` 읽기(반환 코드를 조건 고정에도, 성공 근거에도 쓰지 않음)에서 섬. 근거는 성공 경로에서만 실행되는 out 값 store(`osapi-idmap.c` L976–978). F0는 같은 읽기에서 불확정. 실패 조회의 미준비 판정은 여전히 반환 코드에 기댐 |
| G-I-H 제어 (confirm2 계획 9개 × 4 인스턴스, 36회) | 보류 52·재개 52·해제 선도달 48이 계획 지점과 호출 번호까지 F0와 같음. 결과 부류 36/36 같음. ptrace 정지 0회 |
| 제어 근거를 판정에 연결한 효과 | P1을 끄면 F0 재생에서 판단을 유보하던 호출이 인스턴스당 86개. G-I-H 재생은 실제 보류·해제 기록을 근거로 그중 83개를 판정한다. 83 = 소진 계획 셋(W1·W10·W6)의 25회씩 75 + 나머지 계획 8. F0의 보류 기록은 아직 판정 입력에 연결하지 않았으므로, 이 차이는 수집 경로의 차이가 아니라 제어 근거를 연결한 효과를 포함한다 |

이 36회는 confirm2가 기준 빌드에서 이미 확인한 계획이라 예측 확인(H3)에 더하지 않고 경로 대조로만 보고한다(권고, 결정 대기 5번).

## 4. 근거 종류로 본 현재 판정

| 근거 | 해당 판정 |
|---|---|
| 직접 포획 값 | R2 AppID 0 전달 24, C1 수정 후 성공 조회 8(계측 store 값) |
| 관측 상태·순서 (+ 신뢰 가정) | R2 SB 자기 전송 5 (A-OWNER) |
| 반환값에서 유도한 순서(RF) 포함 재생 | F0의 C1 성공 조회 |
| 제어 순서 (P11, 제어 실행 전용) | 소진 25회, 보류로 만든 순서 |
| 반환 코드 좁힘 (P1 조건부) | R2 다른 task 240/243, C1 실패 조회의 미준비 |

보고할 때는 호출 수와 함께 사례 수, 순서 구조 수, 계획 수, 실행 수를 따로 적는다. 위 수치는 근거 개선을 보이는 자료이고 정확도 지표가 아니다.

## 5. 보여 준 것과 보여 주지 않은 것

- **보여 줌**:
  - 실제 cFS 기록에서 호출 목적·자원·앱 귀속을 갖춘 판정
  - C1의 순서 의존과 소진 위반을 같은 바이너리·설정의 제어 실행으로 확인
  - 같은 분석기가 두 실행 경로의 기록을 처리하고, 계측 경로가 일부 판정에 반환 코드와 독립인 근거를 더함
- **보여 주지 않음**: 자연 실행에서의 빈도·발생 가능성, 새 실패 기전, 관측 효과의 크기(hook 비용·군 비교 미실시), 기존 방법 대비 기여(H4), 다섯 사례 일반성(H5).
- 주의: E-06의 위반은 채택한 요구·허용 모델의 판정이다. PR #342가 재시도 상한을 의도적으로 두었고, 강제 보류로 만든 소진은 새 운영 결함이나 자연 빈도를 뜻하지 않는다. "재계측하지 않은 기준 빌드에서 관측" 주장은 F0 경로에만 쓴다.
