## 1. Definition

Terms a program can compute:
- Actor: a static thread root (the process root; an entry read from the core object table or the startup script; the entry argument of a resolved spawn call). app(actor) is defined in section 3.
- Publishable element O, three structural kinds: (K-name) a record of a global table found by a key comparison in a search loop, identified by (record type, key field, partition constants, key value); (K-field) a global field that holds one constant c0 at every program point that precedes all spawns, and has at least one later writer, in some actor, of a value other than c0; (K-spawn) fields a creator writes after a spawn call and the spawned actor reads through its own identity.
- w: an operation that moves O from absent (no record with that key; field equals c0) to present. u: an operation whose result depends on O.
- sigma_bot(u): the state in which every publication that is not ordered before u by MHB (section 5) has not happened. Eval(u, sigma): concrete evaluation of u's callee chain and of the caller's code after u, up to the end of the caller actor's once-only region, in state sigma.
- Effect classes: K1 the actor or the process terminates; K2 undefined behaviour of the language (a constant index outside the declared bound of an array, a constant null pointer dereferenced) on an unguarded path; K3 an event of type ERROR or CRITICAL is sent; K4 a status of the framework's error class is produced and a publication or effect of the present-state path is skipped; K0 none of these. Order K1 > K2 > K3 > K4 > K0.

KZ-S reports the triple (O, w, u) as an ORDER VIOLATION iff all four hold:
- V1 (two actors) actor(w) != actor(u).
- V2 (the code distinguishes the orders and labels one as failure) class(Eval(u, sigma_bot)) > class(Eval(u, sigma_bot with O present)): making O present removes a failure-class effect.
- V3 (no healing in the code) the absent branch of u does not publish O itself, does not rejoin the present path with a success-class result, is not an unbounded retry, and u is not in cyclic code whose absent branch returns to the loop head.
- V4 (not enforced) (w before u) is not in MHB.
Sub-verdicts: FIXED-PREMATURE when (u before w) is in MHB; UNENFORCED when neither order is in MHB; TOLERATED(B) when V3 fails only because of a retry with a finite bound B read from the code. Decided negatives: ENFORCED (V4 fails), NO-REQUIREMENT (V2 fails), HEALED (V3 fails otherwise). Not decided: UNDECIDED-KEY, UNDECIDED-EVAL, each with the missing fact named.
A violation is therefore "an order that the consumer's own failure handling requires and that nothing in the system enforces". Each finding carries the pair (app(actor(w)), app(actor(u))): application and application (C1), core service and core service (C3, R2), framework creator and application (C5). Whether the bad order occurs in a given run is a separate, run-time statement (REALIZED / NOT-REALIZED, section 5).

## 3. Candidate discovery

Consume sites. The three structural patterns of step 2a are kept as the generators (static_facts.md §5e): path A (a use of a function whose parameter reaches a key comparison in a search loop over a global table), path B (a shared field passed as an argument, or read in a branch, with a writer in another actor), path C (a field written by a creator after a spawn and read by the spawned actor). What changes is the order of the questions: KZ-S does not grade every (reader, writer) pair. It first asks V2 of each consume site alone (section 4), and only the sites that pass get a publisher search and an order analysis.

Publisher. Path A: creators of the same namespace and partition whose key value equals the consumer's. Path B/C: the writers of the field whose value differs from c0; a writer that stores c0 again (R2: the failure branch of `CFE_ES_GetAppID` stores `CFE_ES_APPID_UNDEFINED`, REL(r2_core) row B65 writer 3 [M]) is a non-publication and is kept as a second absent path. The lead's pattern "one later non-constant writer" is too narrow for the dossier facts: B65 has three writers, and C3's B64 lists two may-writes from string copies (G3 C3 §9).

Identity of the shared object.
- Literal keys and keys in static images: 2a already resolves them (BP: `BP_Throttles[i].Name` = "BP0_tsem", "BP1_tsem", REL(c1_pre_tx) row A20 [M]).
- Keys in tables loaded at run time: resolved statically by T-BIND. For C1 the chain is `CFE_TBL_Register(&CF_AppData.config_handle, "config_table", ..)` cf_app.c:155, `CFE_TBL_Load(.., CFE_TBL_SRC_FILE, "/cf/cf_def_config.tbl")` :164, `CFE_TBL_GetAddress(&CF_AppData.config_table, ..)` :184, and the table unit `bpxfer_defs/tx/tables/cf_def_config.c`: object `CF_config_table` :24, "BP0_tsem" :40, "BP1_tsem" :54, `CFE_TBL_FILEDEF(CF_config_table, CF.config_table, CF config table, cf_def_config.tbl)` :59 [F, all opened]. This removes the "key unresolved" of row A21 without a run. Two targets (tx, rx) ship a unit of that name: the image is chosen by the target whose script is analysed.
- Keys that come from a function parameter, a received message or a command (GO §g: 3 of 11 sites; G1 N8): if the value is in the shipped system the caller chain resolves it; otherwise the row is UNDECIDED-KEY. One passive boot (KZ-R1) logs (partition, key string, status, actor) at the search functions that path A itself found; keys that only an operator command can supply stay out of scope.
- K-field elements are static memory locations; no key is needed. For K-spawn the key equality "the record the creator writes is the record the child reads" follows from the spawn's out argument and the child's self-identity chain; it is a premise [I], and the C5 identity mix-up (G5 §15) shows it can fail at run time. A read of another task's record is a different finding and is not reported as an order violation.
- Numeric IDs are never used to pair or to compare runs (GO §f: they are creation serials).

Actor to application. Static: a script-entry root belongs to the application named on its script line; a spawn-entry root belongs to the application of the actor that calls the spawn; core roots belong to the core service of their table entry; library functions belong to the calling actor, a library init to the process root at its script position (GS E7). At run time (KZ-R) the thread is bound to its root by the creation edge (creator's spawn call instance and entry argument, then the first execution of the child), never by a value the task reports about itself (G5 §15 items 1-4).

## 4. The oracle

O1. Once-only region. For each actor, the code reachable from its root that is not inside a loop without a constant trip bound. A consume there cannot heal by re-execution. Cyclic consumes are evaluated too, but go to a separate TRANSIENT list unless their absent branch leaves the loop for good.
O2. sigma_bot. For the consume u, every K-field read on u's path whose publisher is not MHB-before u takes c0 (c0 = the value stored by the last writer that IS MHB-before u, e.g. an early-init placeholder), and every K-name record whose creator is not MHB-before u is absent. This state is always consistent because publications are monotone [I].
O3. Concrete evaluation. Run u's callee chain on sigma_bot with the constants of the build: return constants, their conditions, nested calls, array subscripts. All ingredients are 2a facts (RETURNS, RET_CONSTS, READS, INIT, WRITERS); the new part is that calls are followed with concrete arguments instead of stopping at "the result of a call". Then follow the caller: which branch the returned status selects, what that branch does until the end of the once-only region (return of the result, return of another constant under a guard on the result, stores of run-status constants, event sends with a constant type argument, terminals from F8, publications skipped).
O4. Classify the effects of the absent path and of the present path with K1..K4 (V0 and generic semantics). V2 holds when the absent path has a higher class. When the published value is symbolic (an ID computed at run time), the present path is the callee's success-class return, provided constants do not refute its condition [I].
O5. Healing (V3), read from the code around u: create-on-miss (2a "probe-create"), fallback, bounded retry (trip bound and delay give B), unbounded retry, cyclic re-check.
O6. Consequence closure. Publications skipped on the absent path are themselves elements; their consumers are evaluated in turn with that element absent. This yields the predicted failure signature (sites, statuses, events) that KZ-R must match.
O7. Minimal required set. With k unordered elements on u's path, evaluate the 2^k presence states; the required publications are those whose presence lowers the class.

Why the inference is legitimate. (i) V2 is a property of the shipped code, not a guess about intent: the same call site has two outcomes; the program itself reacts to one of them with the framework's failure vocabulary or with termination, and (ii) the evaluation shows that this outcome is selected exactly by the absence of another actor's publication. From (i) and (ii), "w before u" is the order under which the consumer's code does not take its own failure path. No sentence about what the application "should" do is used. The consumer's error handling is the specification, and the framework's vocabulary says which branch is the error.
What the inference does not give: that the designers regard the failure as a defect (CF documents its exit as intended behaviour, cfs_cf.dox:212-214, G1 §4 item 10), and any requirement whose violation the code does not label (section 7).

How this avoids ending where step 2a ended. In 2a every dependent pair is a row and every row needs a feasibility grade, which is mostly undecidable. Here most rows are DECIDED by V2: no failure-class effect on the absent path means NO-REQUIREMENT. Measured on existing facts: in REL(c1_pre_tx) only 6 of 127 path A rows have a terminal on the handling chain, and only one of the six has a creator in another actor: A21, the C1 row [M2]. In REL(r2_core) 24 of 155 path B rows have a callee that returns an error-class constant depending on the argument, 5 of those carry creation-order facts, and exactly one has a reader actor created before the writer: B65, the R2 row; the look-alike B97 has "none" [M3]. And "no MHB edge in either direction" is a verdict (UNENFORCED), not "undecidable", because the definition asks whether the order is enforced, not whether a schedule exists.
Two gaps of the present handling facts must be closed for this to work, both seen on a control: row A24 (SCH_LAB's lookup of "cFS-Master") says "result tested; no return of it and no terminal operation under it found" and "feasibility: undecidable" [M4], although the code returns `CFE_STATUS_EXTERNAL_RESOURCE_FAIL` under the test (sch_lab_app.c:176-181 [F]), the caller then sets `RunStatus = CFE_ES_RunStatus_APP_ERROR` (:87-91 [F]), and the creator runs in the process root before any task exists (G1 N2). O3 needs "returns constant c under a guard on the result"; section 5 needs HB-spawn for creators in the process root.

When KZ-S cannot decide it says which fact is missing: UNDECIDED-KEY (key from outside the shipped data), UNDECIDED-EVAL (a branch depends on a value that is neither a constant nor a placeholder; evaluator limit), or a premise note on a verdict (writer-set completeness, P0 entry not checked against its source).

## 5. Enforcement and feasibility

MHB (must-happen-before), the transitive closure of four generic rules over the shipped code:
- HB-seq: inside one actor, p before q when p dominates q on the path where every tested status takes its non-error side.
- HB-spawn: a point of the creator that dominates the spawn call precedes every point of the spawned actor. With L0 this orders the process root's work, library inits and earlier script lines before a later script actor.
- HB-await: after the spawn the creator runs a wait loop whose only non-terminal exit needs a field value that the child writes at point p. Then everything of the child that dominates p precedes everything of the creator after the loop, hence every actor spawned later. If the timeout exit is a terminal (panic), the edge is hard. If the timeout exit continues, the edge is soft and carries the bound from the build's configuration.
- HB-lock: the creator holds lock L from before the spawn through the publication and the reader takes L before u (the 2a rule behind "proven-impossible", revision 5).
The framework orders E1-E10 of GS §B are instances of these rules on the ES source (E2 = HB-await with a panic exit, cfe_es_start.c:810, :835-846; E7, E8 = HB-seq + HB-spawn with L0). They are derived, not listed by hand. Code of an actor after its ready-declaring write p is NOT covered by HB-await: this is the C2 mechanism, obtained for free.

| Statement | Status |
|---|---|
| ENFORCED by HB-seq, HB-spawn, HB-lock; V2 when the evaluation uses constants only | proven, under the listed premises (complete writer set, P0 semantics) |
| FIXED-PREMATURE by a hard HB-await edge | proven if the awaited field's writer set is complete; otherwise strongly inferred, and one passive boot must show the predicted status at the predicted sites |
| UNENFORCED | strongly inferred: absence of an edge under four rules; an ordering mechanism outside the rules makes it a false positive |
| Retry bound B | read from code; the real delay per trip is not proven |
| The bad order occurs in this build; what K2 does; whether lateness can exceed B | needs a run |

Minimal run-time addition KZ-R.
- R1, one passive boot per build. Observation points are generated from the surviving rows only: entry and return of each u and w, with key string and status, and the terminals and event sends of the predicted signature. It confirms FIXED-PREMATURE rows, resolves UNDECIDED-KEY rows, and marks an UNENFORCED row REALIZED when the natural order is the bad one and the trace equals the predicted signature.
- R2, one directed boot per UNENFORCED row not realized by R1, and per TOLERATED(B) row if the residual is wanted: delay the publisher at the entry of w's API call (or at the publisher actor's entry when w is not an API call), release when u has returned. Only the entry is used: a publisher stopped inside a create exposes a third object state (G1 §1.5, §4 item 7). The plan is refused when the static lock set at the hold point is not empty or when w and the spawn share one critical section (then the order is ENFORCED).
Artifacts of the intervention are recognized by prediction: (1) a run counts only if its trace equals the statically predicted signature (u returns the predicted status at the predicted site, then the predicted chain); (2) before the run, KZ-S lists every wait loop whose predicate depends on the held actor; a timeout line or status of such a loop, and any effect reachable only through its timeout exit, is attributed to the hold; (3) a hold must be shorter than every hard wait bound on the held actor, otherwise the plan is refused (delaying a core task drives the creator toward its 30000 ms panic, G3 observation 6); (4) a failure obtained only by a hold longer than B on a TOLERATED(B) row is reported as "bound exceeded under forced delay", not as a natural violation. For FIXED-PREMATURE rows the other order cannot be executed in the shipped configuration and is not needed: the harmful order is the one every boot takes.

## 7. False positives and false negatives

False positives.
- Designed exits. C1 itself is "intended behaviour" in CF's documentation (G1 §4 item 10). KZ-S cannot separate "intended but unenforced" from "defect"; it reports both with the evidence.
- UNENFORCED where an unmodelled mechanism orders the actors: the 6.4.1 startup semaphore released by `OS_BinSemFlush` (GS §G "Startup sync"), a consume that is only reached after a message another actor sends, a soft barrier that in practice always holds.
- Instances beyond the reported case with no ground truth: C3 L7, the R2 "nearby" window, further (caller, site) instances (G3 C3 L8).
- Cyclic consumes with an ERROR event on a miss, e.g. HS monitoring an application by name (GO §g A4-A6): they are put on the TRANSIENT list; if that list were counted they would be false positives.
- Statuses of error severity with a routine meaning (`CFE_SB_TIME_OUT`, `CFE_SB_NO_MESSAGE`, GS §C): only a risk when such a status is the absent outcome of a keyed or placeholder consume.
- States the two-valued abstraction over-approximates: sigma_bot may combine absences that scheduling never produces together.
False negatives.
- C2: no pair in shipped code; a barrier that does not cover a dependency is visible only as an uncovered publication.
- Absence that returns success: a message sent before the receiver subscribed (GO §d row 2; the count of that event differs with start order in the recordings, G3 R2 L6); C3's sub-order "SB ID unpublished, EVS registered" (G3 C3 field 5 table row 3); the 6.4.2 residue; a library used before its init (GO §d "Library state") unless a placeholder pointer gives K2.
- A third object state (a lookup racing a create between allocation and finalization, G1 §1.5 "third outcome") is outside the absent/present model.
- Keys supplied only at run time from outside the shipped data; evaluator limits; actors the facts do not have (script actors are missing from the r2_core facts, G3 R2 L2 caveat).
- Identity confusion (G5 §15) is not an order violation and is not looked for.

## 8. Cost and construction

Static cost: one extraction per build (as step 2a) plus one concrete evaluation per consume site and presence state: O(sites x 2^k), k = unordered elements on the site's path (3 for C3, 1 elsewhere in the five cases). Runs: 1 passive boot per build and target; plus at most 1 directed boot per UNENFORCED row that the passive boot did not realize, and 1 per TOLERATED row if the residual is wanted. The number of boots grows with the number of surviving rows, not with the number of application pairs; on the development builds the two filters of section 4, which are cruder than the full method, leave 1 of 127 rows (path A, c1) and 1 of 155 rows (path B, r2_core) [M2, M3]; the count for the full method is the first thing to measure [U].
Instrumentation: none for KZ-S. KZ-R1 needs entry/return observation with arguments at the row's sites; KZ-R2 needs a hold at an API entry or actor entry and, for K2 rows, the value of one subscript at one site.

## 10. The weakest point

The oracle is exactly as strong as the consumer's own error handling, and the verdict UNENFORCED is the absence of a proof. KZ-S sees a required order only where the shipped code labels the absent outcome as failure (termination, ERROR event, error-class status) or where a placeholder constant provably reaches an unguarded subscript. A dependency whose violation returns success is invisible: C2 is not detected at all, the software bus (the largest cross-application channel, GO observation 2) yields nothing, and C3 is caught through one memory-safety pattern rather than through any framework signal. In the other direction, every labelled absent branch with an unordered publisher is reported, although the label may document intended behaviour and although the bad order may never occur: of the five cases only C1 and R2 have a recorded run that shows the reported order (G1 §1.10, G3 R2 field 9); C5 and C3 would stand as static verdicts with no observation behind them, and their confirmation depends on a directed delay that was never executed in this project for the new path. The static tier also rests on engineering that does not exist yet (the concrete evaluator, T-BIND, the MHB closure, two actor-resolution fixes); until it is built, predictions P3-P9 are claims, and only P1 and P2 are measured.
