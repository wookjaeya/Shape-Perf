## 1. R2: 실제 실행에서 순서위반을 관측했다 (첫 사례 결과)

- **조건.**
  - 빌드는 ENV 빌드(cFS v7.0.1, cFE `c5fb2b4d`)를 **수정하지 않고** 그대로 썼다. 기본 구성, 일반 사용자.
  - 관측은 보고자가 쓴 방법인 gdb breakpoint로 했다. 보고자가 찍은 행 `main#L185`는 이 판에서 내용이 같은 `cfe_evs.c` L188로 옮겨 찍었다.
  - gdb 운용 방식과 실행 횟수(3회)는 레퍼런스가 없어 가정으로 기록했다.
- **결과.** 3회 모두 똑같았다.
  - SB task가 자기 AppId를 기록하는 지점(`cfe_sb_task.c` L138)은 부팅마다 한 번 실행됐다.
  - **그보다 먼저** ES task와 EVS task가 SB API를 통해 SB AppId(아직 0)로 이벤트 24건을 보냈다. ES가 20건, EVS가 4건이다.
  - 24건 모두 EVS에서 `ILLEGAL_APP_ID`로 거부되어 **조용히 사라졌다.** 콘솔 출력도, counter 변화도, syscall도 없었다.
  - SB가 AppId를 기록하고 EVS에 등록한 뒤에 나온 사용 199–205건은 모두 정상 순서였다.
- **사례 기록과의 비교.** 코드 해석에서는 "최소 9건"으로 예측했다. 실제로는 24건이다. 영향받는 task는 ES와 EVS로, 원 보고의 "the ES and the EVS tasks"와 맞다.
- **검토 §8.1 상태표 기준.** 경로 실행 ○, 사건 기록 ○, 판정 ○, 순서위반 관측 ○. 판정 기준은 P4 (a)이고 아직 결정 전이다.
- **아직 말할 수 없는 것.**
  - gdb 없이 실행했을 때의 결과. breakpoint마다 모든 thread가 잠깐 멈춘다. 그래서 OPERATIONAL 도달이 약 1.6초에서 2.2–2.7초로 늦어졌다.
  - 결정적이라는 주장. 3회 실행이고, 모두 gdb 아래에서, 같은 유지 상태로 시작했다.
  - 기존 도구가 이것을 놓친다는 주장. 실행하지 않았다.
- **논문에 주는 뜻(분석).**
  - 이 위반은 콘솔, counter, syscall 어디에도 흔적을 남기지 않는다. 프로세스 안을 관측해야만 보인다.
  - syscall 수준 관측 모델(RacePro, DESCRY, SysPro류)이 이 사건을 볼 수 없다는 주장을 뒷받침하는 실행 근거가 된다. 다만 도구 자체를 실행한 결과는 아니다(P3).

## 2. 기준 조건 측정(M1) 결과

빌드와 설정은 하나도 바꾸지 않았다. 30초 고정 구간 실행을 6회 했다(probe만 붙인 실행 3회, SB pipe 정보 명령을 쓴 실행 3회). 측정 시점은 사건 기반이다.

| 항목 | 측정 결과 | 이전 기록에 대한 영향 |
|---|---|---|
| **큐 용량** | 큐 26개는 모두 SB pipe다. kernel의 실제 깊이는 min(요청, 10)이다. **22개가 잘렸고**, 전체 용량은 요청한 584칸 중 247칸이다. 12번 측정이 모두 같았다. | E5 확인 |
| **손실** | 큐가 가득 차서 버려진 메시지(SB `PipeOverflowErrorCounter`)가 **실행마다 33, 37, 4, 49, 45, 41건**이다. 모두 시작 직후에 일어났고, 이후 약 28초 동안은 0건이다. 콘솔 표시는 16건에서 멈춘다. 그래서 run01–07은 모두 상한에 걸렸고 실제 값은 모른다. pipe별 손실 counter는 cFE에 없다. pipe 정보 파일의 `SendErrors`는 다른 원인(MsgId별 한도 초과)만 센다. | E5의 "8–16건"은 하한값이었다. 정정한다. |

## 3. 결정 요청

### D2. 큐 깊이 (측정값 반영)

레퍼런스부터 확인했다. bundle CI(`actions/start-cfs-container/action.yml` L29-34)는 실행할 때마다 **새 docker container**를 띄우고, 그 container에 `--sysctl fs.mqueue.msg_max=64`를 준다. docker container는 자기 IPC namespace와 자기 `/dev/shm`을 갖는다. 즉 CI의 64는 **cFS 전용 IPC namespace 안에서만 적용되는 값**이다.

| 선택지 | 레퍼런스 | 영향 |
|---|---|---|
| (가) README 모드 유지(`msg_max` 10) | README L102 | pipe 22개가 잘리고, 실행마다 시작 직후 4–49건이 손실된다. 손실 수가 실행마다 달라 사건 순서 연구에 변수가 된다. 결과마다 "제한된 큐 조건"이라고 표시해야 한다. |
| **(나) CI와 같은 방식: cFS 전용 IPC namespace를 만들고 그 안에서만 `msg_max`=64** | CI action L29-34 | 잘림이 없을 것으로 예상된다(요청 최대 50). 손실은 다시 측정해야 한다. **deviation이 둘 있다.** 첫째, docker 대신 `unshare --ipc`를 쓴다. 둘째, CI 이미지(`cfsexec-linux`)의 사용자 공간과 실행 사용자는 확인할 수 없다. 다른 프로세스에는 영향이 없다. |
| (다) VM 전체의 `msg_max`를 64로 | 같은 CI 값 | VM 안의 모든 프로세스에 적용되어 다른 작업에 영향을 줄 수 있다. 권하지 않는다. |

**권고: (나).** 승인하시면 M1과 같은 방법으로 큐 용량과 손실을 다시 측정한다. 측정 전에는 "잘림이 없다"고 쓰지 않는다.

### D3. 종료 방법, reset 종류, 유지 데이터 (세 조건으로 나눔)

| 조건 | 측정 사실 | 선택지 | 권고 |
|---|---|---|---|
| 종료 방법 | CI의 ES Restart(POWERON)로 종료하면 SysV segment가 지워진다. 그래서 다음 부팅은 항상 POWER ON이다(6/6). SIGINT로 종료하면 PO → PR → PR → PO 순서로 돈다(이전 기록). | (가) CI 명령 (나) SIGINT | **(가)**. bundle CI의 방법이고, 부팅 종류가 고정된다. |
| 유지 데이터 | 실행 사이에 남는 것은 `/ram`(`/dev/shm/osal:RAM`)의 파일, `EEPROM.DAT`(모두 0), key file이다. M1이 남긴 `/ram/cfe_sb_pipe.dat`가 지금 있다. | (가) 지금처럼 host 상태를 그대로 두고, 실행 전후를 기록한다. (나) **CI 방식: 실행마다 새 상태로 시작.** D2 (나)의 namespace에 전용 `/dev/shm`을 함께 쓰고, run 디렉터리는 빌드 산출물에서 새로 복사한다. CI는 job마다 새 container와 새로 푼 바이너리로 시작하기 때문이다. (다) 남은 파일만 지운다. | **(나)**. D2 (나)와 한 번에 적용할 수 있다. 레퍼런스(CI)의 "매번 새 상태"에 가장 가깝다. (다)는 레퍼런스가 없어 권하지 않는다. |
| 재부팅 직후 첫 실행 | 시작 순서가 달라진다(앱 적재가 849 ms). | (가) 그대로 포함하되, 모든 실행에 "재부팅 후 첫 실행" 표시를 붙여 따로 분석한다. (나) 재부팅 후 첫 실행은 결과에서 뺀다. | **(가)**. 빼는 기준에는 레퍼런스가 없다. 표시해서 따로 분석하면 정보를 잃지 않는다. |

### 이의가 없으면 진행할 작업

| 작업 | 내용 | 레퍼런스와 표시 |
|---|---|---|
| R2를 gdb 없이 관측 | CORD 기록기를 cFE에 넣은 **별도의 계측 빌드**로 R2를 관측한다. ENV 빌드는 그대로 둔다. gdb 결과(24건)와 같은지 비교하고, 계측이 실행에 주는 영향도 잰다. | 계측 빌드는 연구 도구의 빌드다. 기준 환경과 구분해 "계측 빌드"로 표시한다. 빌드 조건(소스, 옵션)은 ENV와 같게 하고, 차이는 계측 코드뿐이다. 디스크 여유는 1.7 GB이고, 빌드 하나는 400 MB 안팎으로 예상한다. |

## 4. 아직 하면 안 되는 주장 (2차 목록에 추가)

- gdb 없이도 R2 위반이 24건이다.
- R2는 결정적이다.
- `msg_max`=64이면 손실이 없다. (D2 (나)를 적용한 뒤 측정 전까지는 말할 수 없다.)
- 실행마다 초기 상태가 같다. (`/ram` 파일과 재부팅 직후 차이가 있다.)
- HS를 빼면 결과가 같다. (영향이 작다는 측정은 기본 table 조건에서만 한 것이다.)
