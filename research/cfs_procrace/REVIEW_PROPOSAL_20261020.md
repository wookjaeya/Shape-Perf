## 1. 종합 판단

**제안이 하는 일을 한 문장으로.** 연구의 중심 주장을 "σ·M 한정 must-order 인증서로 관측된 wrong-way 위반을 보편 클래스 `fixed-order`로 올린다"(SPEC §1.11)에서 **"불완전 관측 아래의 관측 판정(§9) + 제약 기반 한정 예측(§10) + 실행 확인(§11)"**으로 옮기고, 최대 고정점·인증서·독립 검사기를 "추가 주장을 위한 보존 경로"로 내린다(제안 §3.2, §14.3).

**판단 [검토].**

1. **방향은 타당하다.** 10-19 검토 §2.3·§4가 보인 문제(인증서 경로는 R2에서만 검증되고 나머지 네 사례는 예측·확인 경로가 필요하다)에 대한 일관된 답이다. 다섯 사례를 단계 A부터 모두 올리는 것(§15.2), 관측 불확실성을 판정 의미에 넣는 것(§9.2, IN-03, OB-01), 시험 T-01–T-16은 10-19 검토의 D-2·D-3·Q2·Q3를 그대로 요구로 바꾼 것이다.
2. **그러나 이 안은 채택 여부를 PI가 결정해야 하는 "연구 주장 변경"이다.** 10-15 결정 가운데 적어도 네 건(P-LADDER, D20의 인증서 완료 조건, P-Z3, ADR-046/P-ABL-ALLOWED)과 용어 결정 T1을 다시 정해야 하고, 외부 검토(10-12)와 PI가 받아들인 "방어 가능한 기여"(SPEC §1.11)가 바뀐다(§4 P1, P2).
3. **가장 큰 공백은 기여(novelty)다.** 인증서를 빼면 R2에 남는 것은 "관측 판정"이고, SPEC §6.4 항목 38이 스스로 말하듯 단순 상태 검사도 R2의 실현된 발생을 모두 찾는다. 제안의 RQ2("기존 기법의 어떤 부족분을 해결하는가")는 질문만 있고 답이 없다. GPredict 원리를 cFS 사건에 적용한 것과의 차별점을 제안 자체가 정의해야 한다(§4 P1).
4. **의미의 정밀도가 SPEC보다 낮아진 곳이 있다.** §9.2의 설명 공간 `Cobs`가 정의되지 않았고, 상태 6종·세 판정·QT-4 엄격 규칙이 결과 4값으로 접히며, σ_U/σ_U∞/σ_R1과 M_api/M_impl 축이 "실행 모델 M"으로 뭉개진다. C1(재시도의 timeout 의존)과 C3(우선순위)은 이 축이 없으면 분류할 수 없다(§4 P3, P4).
5. **거버넌스가 비어 있다.** 3,702줄의 SPEC rev 1.2와 이 0.1 문서 중 어느 것이 규범인지, 결과 어휘를 어느 쪽으로 통일하는지 정하지 않았다(§4 P6).

권고 요약: **채택하되 "대체"가 아니라 "SPEC rev 1.3의 우선순위·완료 조건 개정"으로 받아들이고**, §6의 결정 8개를 먼저 내린 뒤 구현 순서를 바꾸는 것이 안전하다.

## 3. 유지할 장점

- **§2.1 세 정보의 분리(요구 순서 / 실행 제약 / 관측 순서)와 "요구 순서를 실행 제약에 넣지 않는다".** SPEC도 같은 원칙(MB는 코드의 S-규칙만)을 따르지만 제안이 더 명료하게 적었다.
- **IN-03, OB-01, OB-02, T-05.** 10-19 검토 D-2의 두 시나리오(247건 `NOT_EVALUATED` 또는 247건 VIOLATING)를 정확히 막는 요구다. 재생 엔진의 추상 domain은 "나열되지 않은 자원은 초기 상태"를 구체화 규칙으로 쓰므로(`phi_reference.md` §6 규칙 (2)) [F], 미관측 자원을 **전체 상태 집합으로 나열**하면 기존 평가기로 구현할 수 있다 [I]. 제안 §9.2의 "상태 집합으로 불확실성을 처리할 수도 있다"가 이것이다.
- **EV-03(C5의 순환 회피), EX-02(장벽은 회차·참여자별), §7.1의 "부모 반환 뒤에만 자식 실행" 금지.** 모두 SPEC §5.7, K-PHASE, spawn 규칙과 일치하고 더 읽기 쉽다.
- **OUT-01/OUT-02.** 발생 수와 결함 수의 분리, 고정 순서 결과를 스케줄 의존 탐지 실적에 합산하지 않음. SPEC §6.4 항목 12·40과 같다.
- **§15.1 시험 T-01–T-16.** 구현의 실패 위험을 시험으로 바꾼 좋은 목록이다. T-06(timestamp로 결정하지 않음), T-09(순서 변경 뒤 후속 경로 재사용 금지), T-13(작은 모델 전수 대조)은 SPEC의 litmus·exh 차등 시험에 대응한다.
- **§15.2 단계 A에서 다섯 사례 모두 등장.** 10-19 검토의 M-2(경로×사례 일대일)에 대한 직접적 답이다.
- **§17 "미확인 항목 하나로 전체를 멈추지 않고, 그에 의존하는 주장만 제한한다".** 10-19 검토 §2.5의 결정 대기 문제를 푸는 원칙이다.
- **§1.2 "같은 앱 내부 task 사이만의 문제는 앱 간 실적으로 합산하지 않음", "귀속 미확정은 별도 보고".** 평가 단위의 정직한 구분이다.

## 4. 문제점과 빈틈 (심각도 순)

### P1. 기여 공백: 인증서를 빼면 R2에서 "단순 상태 검사와 다른 것"이 없다

- SPEC §6.4 항목 38 [F]: "탐지(알람 유무)만으로는 인증서와 예측이 더해 주는 것을 보일 수 없다. 같은 준비 조건을 주면 단순 상태 검사가 R2의 모든 실현된 발생을 찾는다." 제안은 인증서를 필수 경로에서 빼고(§3.2) R2를 "기존 관측 자산을 연결하는 첫 실험"(§12.5)으로 둔다. 그러면 R2의 결과는 `OBSERVED_VIOLATION` 24건이며, 이것은 gdb 기록 재집계와 같은 정보량이다.
- OUT-02는 "고정된 잘못된 순서의 사례와 순서 변화에 따라 발생하는 사례를 구별한다"고 하지만, **구별할 수단을 제안은 제공하지 않는다.** 고정 순서는 보편 진술(모든 실행에서 wrong-way)이고, 그것은 인증서(b = ∞) 또는 전수 탐색(b 한정)으로만 나온다(SPEC §1.10 `fixed-order` 행, §6.4 항목 4 "반복 실패 실행으로부터는 절대 아님") [F]. 제안의 예측(§10)은 존재 질문(∃p)만 묻는다. "다른 순서가 UNSAT"(`NONE_IN_SCOPE`)는 PR-03이 말하듯 범위 한정 진술이라 고정 순서의 근거로 쓸 수 없다.
- GPredict와의 차별점: 제안 §2.2는 GPredict 원리를 "우선 검증할 판정·예측 원리"로 삼는다. 그러면 Kairos = GPredict의 제약 틀 + cFS 사건 모델 + 불확실성 보존 + 실행 확인이 된다. 이 가운데 새로운 후보는 (a) cFS 자원 동일성·앱 귀속·장벽 의미의 프로필 Φ, (b) §9.2의 "모든 허용 설명에서 위반"이라는 판정 기준이다. (a)는 SPEC도 가진 것이고 (b)는 불완전·손실 trace 위의 runtime verification 문헌(예: 누락 사건이 있는 로그의 감시)에 선행 연구가 있을 가능성이 높다 [U: 이 검토에서 문헌을 확인하지 않음]. **제안은 RQ2의 답을 자신이 써야 한다.** 그렇지 않으면 논문은 "GPredict를 cFS에 적용한 사례 연구"로 읽힌다.
- [검토] 가능한 해결: 인증서 경로를 "필수 경로에서 제외"가 아니라 **"R2 track에서만 필수"**로 두는 절충. 10-19 검토 B-1·B-2는 R2 인증서의 논증이 닫힌다는 것을 보였고, K4a가 R2의 사실(writer 3, derives 39, await 1)을 이미 냈으므로 K4b의 R2 부분은 다른 사례보다 싸다. 그러면 R2는 "관측 판정 + 고정 순서 인증서", C1·C5는 "관측 판정 + 예측 + 확인"으로 두 종류의 결과가 생기고 OUT-02의 구별 수단이 생긴다.

### P3. §9.2 관측 판정 의미의 정밀성

- **설명 공간 `Cobs`가 정의되지 않았다.** "관측 기록·초기 상태·누락 정보와 양립 가능한 설명"이 무엇을 허용하는지가 판정을 결정한다. 미관측 쓰기를 임의로 허용하면 거의 모든 인스턴스가 `INCONCLUSIVE`가 되고, 전혀 허용하지 않으면 지금 재생 엔진의 초기 상태 규약과 같아진다. 제안은 "필요한 누락 사건을 유한하게 표현할 수 없으면 보류"라고만 한다. **최소한 종류별로 "계획이 writer LP를 덮으면 관측된 쓰기만, 덮지 않으면 전체 상태 집합"이라는 규칙이 필요하다**(10-19 검토 Q2의 (a)+(b)).
- **상태 어휘의 손실.** SPEC의 `NOT_EVALUATED`(조기 반환), `PENDING`(horizon 열림), `NOT_READY_UNJUDGED`(출처 없음), `TOLERATED`(허용 처리 ACCEPT)가 제안의 4값에 어떻게 대응되는지 없다. OB-02가 `NOT_EVALUATED`를, §6.3이 허용 처리를 문장으로 다루지만 결과 구조(§8.2)에는 없다. 세 판정(프레임워크/호출자/관측 결과)과 인용 등급도 없다. 이것들은 10-12 외부 검토와 10-15 결정(QT-2·QT-3·QT-4·QT-9)이 만든 것이고, 없애면 R2의 "이벤트 요청 거부 vs 패킷 손실", C1의 "재시도 허용 vs 미허용" 구분이 결과에서 사라진다.
- **SAT 의미의 범위.** `Qv`·`Qn`은 하나의 프레임이고 "실행마다 두 번 풀이를 강제하지 않는다"는 단서가 있다. 좋다. 그러나 "구현이 배제한 설명 때문에 위반이 확정되는 일이 없도록 보존 성질을 검증"이 유일한 건전성 조건인데, 그 검증 방법(어떤 시험, 어떤 기준 모델)이 없다. 기존 추상 평가기의 포함 성질 시험(`test_property_eval_agreement`, 90,000 평가) [F]이 이 역할을 할 수 있다 [I].
- **선행 연구 확인 [U].** 불완전·손실 trace에서 "모든 양립 설명에서 성립할 때만 확정"하는 기준은 runtime verification에서 다뤄진 형태다. 제안 §2.2에는 없다. P-PAPERS 수준의 문헌 확인을 추가해야 한다.

### P4. σ·M 축의 소실 — C1과 C3가 분류 불능이 된다

- **C1**: CF의 조회 실패는 재시도(count-bounded, delay-paced)로 복구된다. 위반 witness는 "모든 재시도가 실패"인데 그 마지막 실패는 시간 기반 전이다(SPEC §1.8 TB). σ_U∞ 축이 없으면 "순서 논리의 위반"과 "시간 초과로만 생기는 위반"을 구별하지 못한다. 제안 §6.2 셋째 문단("재시도 구간을 자를 때 잘린 이후를 확정하지 않음", "시간 한도가 요구의 일부면 출처 필요")은 이 문제를 **알고 있으나 축으로 만들지 않았다.**
- **C3**: 우선순위에 의해서만 순서가 정해진다. SPEC은 σ_R1[P_sched]를 모델 전용 축으로 두었다(D4). 제안 §7.1 "플랫폼 실행 제약" 행과 §11.1 마지막 문단이 언급하지만, 결과가 "어느 스케줄 의미 아래의 후보"인지 표시하는 필드가 §8.2에 없다. IN-05가 가정 명시를 요구하므로 **결과 레코드에 `M`의 식별자를 넣으면 최소한은 된다** [검토].
- **M_api/M_impl**: C1·C5는 OSAL 내부(idmap RESERVED 창, 형 잠금 누출)가 관여하는 M_impl 사례다. 제안 §1.3이 OSAL 경로를 입력에 넣지만 모델 수준 구분은 없다.

### P5. 예측(§10)의 의미 공백

- §10.3 값·후속 경로 보존은 SPEC §4.9의 A-COMM(관측·상수·결과 보존 중 하나)보다 약하고 덜 구체적이다. 다만 PR-02로 모든 SAT를 `MODEL_CANDIDATE`로만 두므로 건전성 주장을 하지 않는다. **일관되지만, 그 대가로 G4(trace-sound 예측)를 포기하고 모든 긍정 주장이 실행 확인(§11)에 걸린다.** 실행 확인의 메커니즘(SPEC §4.13 hold: ptrace·디버그 레지스터·사건 기반 해제)은 **측정·구현된 적이 없는 가장 약한 부분**이다 [F: SPEC §5.11 untested]. 제안은 이 의존을 명시해야 한다.
- SMT 인코딩의 의미가 없다. "연산 효과의 요약", "잠금 상호 배제", "큐 FIFO·용량"을 어떤 이론(정수·비트벡터·순서 변수)으로 인코딩하는지, SPEC §4.9 항목 10이 인용한 Alglave–Kroening–Tautschnig(CAV 2013)·Wang et al.(FM 2009)식 순서 변수 인코딩을 쓰는지 없다. 외부 의존성(solver)은 README의 "도구 핵심은 C/C++만"과는 양립하나 빌드 고정·해시 규율(`identity.hpp`의 source identity)에 solver 버전을 넣어야 한다 [I].
- cone 선택(§7.2)은 SPEC §4.9 항목 1·§4.10 항목 1과 같은 요구이나 알고리즘(S-간선·reads-from 역방향 닫힘)이 없다.

### P6. 명세 거버넌스

- SPEC rev 1.2(3,702줄, ADR 52개)와 제안 0.1 중 어느 것이 규범인지 정하지 않았다. 제안 §3.2는 코드 유지를 말하지만 **명세 유지**는 말하지 않는다.
- 제안이 "구체화"한다는 「Kairos 연구 설계 재구성 및 기존 순서 위반 탐지 기법 선정」은 저장소에 없다 [U: `research/cfs_procrace/` 검색]. 그 문서의 결정(예: GPredict 선정)이 어디에 기록되는지 불명.
- 결과 어휘가 두 벌이 되면 K0의 `test_core_vocab`(SPEC §1.6·§1.10·§6.2 목록과 열거형의 일치 검사) [F]가 깨진다. 스키마 버전 올림과 변환 규칙(제안 §13 끝)이 필요하다.

### P7. 다섯 사례 표(§12)가 기존 기준(B)과 연결되지 않는다

- §12의 표는 요구 추적표로 좋으나 각 사례의 **분석 기준**이 없다: C1은 D22(공개 BP 기반, CF `281a941`→`833fdbb`), C2는 P-C2(역할 재구성, 10-19 검토 §6.3의 세 구성), C3·C5는 D13(6.4.1/6.4.2, 헤더 민감도), R2는 P-R2CTRL(`b9bec567^`/`b9bec567`). `plan/case_basis_register.md`, `plan/C1_basis_plan.md`, `plan/case_setup_C2_C3_C5.md`와의 참조가 없다.
- §12.5 R2 "고정된 잘못된 순서이면 별도 분류" — 수단은 P1.
- §12.3 C3 "현재 R2의 0 유효성 검사로 C3를 대체하지 않음"은 SPEC §6.4 항목 43과 일치한다. 좋다.

### P8. 관측 계획 합성이 없다

§5.3("조건 인스턴스별로 필요한 사건 종류, 부착 위치, 손실, 미관측 효과")과 §13("관측 계획: 필요한 지점 미확보를 명시")은 요구다. 10-19 검토 D-3이 보였듯 손으로 쓴 `sites.kzp`로는 R2의 순서 간선을 만들 수 없다. 제안 아래에서는 R2의 고정 순서를 주장하지 않으므로 그 간선은 필요 없지만, **C1·C5의 예측 cone에 필요한 writer·잠금·분기 사건**은 계획이 덮어야 한다. SPEC §4.7 항목 1–2가 그 규칙이다. 제안이 이것을 가져오지 않으면 §7.2 "연결이 닫히지 않은 구간은 예측 확정 금지"가 늘 발동한다 [I].

### P9. 실행 확인(§11)이 기존 설계를 버린다

SPEC §4.13의 hold는 정지 지점 선택 규칙(잠금 집합 비어 있음, timebase 콜백 밖, RESERVED 창 밖, 디버그 레지스터 할당), 사건 기반 해제, 레퍼런스에서 읽은 감시견, wait-for 오라클, 교란 비율을 정했다. 제안 §11.1은 "정지·해제 지점, 추가 계측 기록" 수준이다. CF-01–CF-04는 좋은 규칙이고 SPEC의 `refuted`·`inconclusive`·`timeout-exercised` 라벨과 같은 역할이다. **기존 설계를 참조로 남기면 된다.**

### P10. 과적합 방지(§16.3)가 SPEC §7.5보다 약하다

SPEC은 노출·동결 기록(누가 언제 사례·수정·기대 판정을 보았는지)과 `blind`/`non-blind`/`post-freeze-adjusted` 라벨, F1/F2 해시를 요구한다 [F]. 제안은 "엔진·규칙 버전을 고정"으로 줄였다. 다섯 사례가 개발 자료라는 인정(§16.3 첫 줄)은 정직하지만, "새 대상 독립 적용"의 blind 주장을 하려면 기존 기록이 필요하다. 10-15 결정 D8/P-RECALL(변이·전후 쌍 집합은 별도)도 §16.3 다섯째 줄과 일치하므로 가져오기만 하면 된다.

### P11. 작은 사실 확인

- §1.2 [사실] "CF #184는 cFE ES가 앱을 각각의 thread에서 시작한다고 설명한다" — 이슈 원문 재확인 안 함 [U]. 모델상으로는 맞다(ES가 앱마다 OS task를 만든다, SPEC §3.3).
- §3.1 [사실], §14.3 [사실] — 10-19 검토와 일치 [F].
- §12.5 "미등록이 원인이라는 표현은 보고자의 추정" — 일치. R2의 반환은 `ILLEGAL_APP_ID`(유효하지 않은 ID)이지 `NOT_REGISTERED`가 아니다 [F: `cfe_evs.c:185–189`].

이 밖에 P-LADDER·D20의 재정의는 R1·R2에서 따라 나온다. §16.3의 held-out은 SPEC §7.5를 그대로 가져오면 된다(결정 불필요).
