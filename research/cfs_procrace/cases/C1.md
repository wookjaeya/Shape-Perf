## 1. Facts (quoted, linked)

### F1. Issue #184 body

Source: https://github.com/nasa/CF/issues/184. Author jphickey. Created `2022-01-13T23:06:06Z`. Closed `2022-12-01T19:35:24Z`, `state_reason: completed`. Labels `bug`, `draco-rc4`. Milestone `v7.0.0`. Comment count 5.

> **Describe the bug**
> CFE ES starts all applications in their own thread.  Therefore, conceptually at least, all apps are starting at the same time.
>
> If configured to use a throttle sem, the CF app expects that semaphore to be created _before_ it starts.  During startup, it will attempt to bind to that semaphore during CF_CFDP_InitEngine(), and if that fails, CF aborts (see #178).
>
> Problem is, if the semaphore is created by another app, whether it be CI/TO or some other dedicated I/O app, there is no guarantee that the semaphore has been created before CF attempts to use it.
>
> Secondary problem exists if the I/O app that owns the sem gets restarted or reloaded, the semaphore ID will likely change too.   This may be recoverable by disabling the engine and re-enabling it (but haven't tested that).
>
> **To Reproduce**
> Its a race condition, so not readily reproducible.
> Start CF _before_ the app that creates the sem (still not guaranteed, but increases the chance the race will be lost)
> Add an artificial delay during startup for the app that creates the sem (just further increases the chance the race will be lost)
>
> **Expected behavior**
> Should be guaranteed via sync mechanisms, or shouldn't be a hard error (e.g. maybe retry to bind later?)
>
> Suggestion that CF might still start up but with the engine in a disabled state, so at least someone can correct the condition and enable the engine, rather than having CF abort/exit.
>
> Adding a call to CFE_ES_WaitForStartupSync() before starting the engine might help too...
>
> **Code snips**
> https://github.com/nasa/CF/blob/2a024d8efd9f44f54b7a59f7face24f255536236/fsw/src/cf_cfdp.c#L1014-L1015
>
> **System observed on:**
> Ubuntu 21.10

### F2. Issue #178, which #184 cites as the abort context

Source: https://github.com/nasa/CF/issues/178. Author jphickey. Created `2022-01-13T21:22:08Z`. Closed `2022-01-13T22:13:58Z`.

> The default/example table source files include a semaphore name - cf_1_sem and cf_2_sem - for throttling on channel 1 and 2, respectively.
>
> However, CF does not actually create the throttling semaphores, it expects the semaphore to be created before CF starts.  If a new user is starting CF by itself with no other support apps running, this semaphore will not exist.
>
> ... the example table should have an empty string for the semaphore name - this means no throttle.
>
> This will make CF at least boot up and load "out of the box" ... but probably any real deployment will need a throttle, so this means that we don't have an example of a throttling semaphore anymore.

The fix for #178 is commit [06c2473](https://github.com/nasa/CF/commit/06c2473c9f60c45e4388a4b31f6312f82f94d564), merged as **2a024d8** (PR #180, `2022-01-13 17:13:57 -0500`). Its message says: "Unless something actually instantiates this semaphore, this prevents CF from initializing correctly." The diff changes `fsw/tables/cf_def_config.c`:

- `"cf_1_sem"` becomes `"", /* throttle sem for channel 1, empty string means no throttle */`
- `"cf_2_sem"` becomes `""`

See [pre-change L42, L51](https://github.com/nasa/CF/blob/06c2473c9f60c45e4388a4b31f6312f82f94d564~1/fsw/tables/cf_def_config.c#L42-L51) and [after L42, L51](https://github.com/nasa/CF/blob/2a024d8efd9f44f54b7a59f7face24f255536236/fsw/tables/cf_def_config.c#L42-L51).

**Fact:** the revision the reporter linked (2a024d8) is this same merge. So **the default table at the buggy revision has no throttle semaphore**, and the default build does not execute the lookup.

> #### Flow Control
> By default, CF assumes that a per-channel semaphore is provided by the Telemetry Output (TO) application or an equivalent application.  The semaphore name is defined in the CF configuration table and must match the name of the semaphore created by TO. If TO does not create a semaphore, the semaphore name can be left as an empty string in the configuration table indicating that a semaphore should not be used. ### F6. Fix

**PR #342.** https://github.com/nasa/CF/pull/342, "Fix #184, work around throttle sem creation race". Created `2022-11-17T21:42:02Z`; merged `2022-12-01T19:35:23Z` as merge commit `2ffbeccc3e75fc69cd4a10652e7cc6abc2e4c90e`. The body says:

> Adds a retry loop around OS_CountSemGetIdByName, because if this sem is created by another app there may be some delay until the other app gets to the point where it creates the sem.  This works around the race condition.
>
> A retry limit is also imposed so CF will not spin here forever.
>
> Fixes #184
>
> **Testing performed**
> Build and run tests, check file transfers with BP
>
> **Expected behavior changes**
> Should start up more reliably
>
> **System(s) tested on**
> Ubuntu 22.04

**Commit.** https://github.com/nasa/CF/commit/833fdbb27a26f15f2429e79392e7eb73d61abdea. Author Joseph Hickey, authored `2022-11-17 16:37:36 -0500`. Parent `281a94188cd7d885a5aed01ee041f3ece2b0486f`. The message repeats the PR description.

Retry loop at [fsw/src/cf_cfdp.c L991-L1021 @833fdbb](https://github.com/nasa/CF/blob/833fdbb27a26f15f2429e79392e7eb73d61abdea/fsw/src/cf_cfdp.c#L991-L1021):

```c
            /*
             * There is a start up race condition because CFE starts all apps at the same time,
             * and if this sem is instantiated by another app, it may not be created yet.
             *
             * Therefore if OSAL returns OS_ERR_NAME_NOT_FOUND, assume this is what is going
             * on, delay a bit and try again.
             */
            ret = OS_ERR_NAME_NOT_FOUND;
            for (j = 0; j < CF_STARTUP_SEM_MAX_RETRIES; ++j)
            {
                ret = OS_CountSemGetIdByName(&CF_AppData.engine.channels[i].sem_id,
                                             CF_AppData.config_table->chan[i].sem_name);
                if (ret != OS_ERR_NAME_NOT_FOUND)
                {
                    break;
                }
                OS_TaskDelay(CF_STARTUP_SEM_TASK_DELAY);
            }
            if (ret != OS_SUCCESS) { ... CF_EID_ERR_INIT_SEM ...; break; }
```

Constants added in [fsw/platform_inc/cf_platform_cfg.h L329-L349 @833fdbb](https://github.com/nasa/CF/blob/833fdbb27a26f15f2429e79392e7eb73d61abdea/fsw/platform_inc/cf_platform_cfg.h#L329-L349):

- `#define CF_STARTUP_SEM_MAX_RETRIES 25` ("Limits the number of retries to obtain the CF throttle sem").
- `#define CF_STARTUP_SEM_TASK_DELAY 100` ("Number of milliseconds to wait if CF throttle sem is not available").

Unit tests in [unit-test/cf_cfdp_tests.c L866-L889 @833fdbb](https://github.com/nasa/CF/blob/833fdbb27a26f15f2429e79392e7eb73d61abdea/unit-test/cf_cfdp_tests.c#L866-L889) cover three cases:

- "Max retries ... sem was never created at all": returns `OS_ERR_NAME_NOT_FOUND`, engine disabled.
- "Retry ... when sem was created late": one `OS_ERR_NAME_NOT_FOUND`, then `OS_SUCCESS`, engine enabled.

## 7. Required order and its provenance

**Statement.** For each CF channel `i` with a non-empty `sem_name`, the provider's `OS_CountSemCreate(sem_name)` must be complete before CF's `OS_CountSemGetIdByName(sem_name)` in `CF_CFDP_InitEngine`. "Complete" means the OSAL record is finalized with a valid `active_id`.

- At 2a024d8 the lookup is a single attempt ([cf_cfdp.c L1014-L1015](https://github.com/nasa/CF/blob/2a024d8efd9f44f54b7a59f7face24f255536236/fsw/src/cf_cfdp.c#L1014-L1015)).
- If the order is violated, `InitEngine` returns the OSAL error and CF emits event `CF_EID_ERR_INIT_SEM` ("CF: failed to get sem id for name %s, error=0x%08x"). `CF_Init` fails, and CF leaves its main loop with `CFE_ES_RunStatus_APP_ERROR`.
- After the fix, the requirement relaxes to: creation completes before the last of up to 25 lookups, spaced by `OS_TaskDelay(100)`.

**Provenance (all references):**

- Issue #184: "the CF app expects that semaphore to be created _before_ it starts"; "if that fails, CF aborts" (F1).
- Issue #178: "it expects the semaphore to be created before CF starts" (F2).
- CF docs @2a024d8: the name "must match the name of the semaphore created by TO"; "If a semaphore is expected and not found, the application will terminate during initialization" (F4).
- Code: the single lookup and `goto err_out` → `APP_ERROR` (F3).
- Fix commit comment: "if this sem is instantiated by another app, it may not be created yet" (F6).

The **current** docs instead say a failed lookup falls back to "not-in-use" (F5). The code contradicts that (F8), so it is not used as provenance.

- **A4 (startup script).** Script order, priorities, and whether real-time priorities are enforced (root or `CAP_SYS_NICE` vs. permissive fallback), plus CPU count and affinity.
- **A5 (delaying the provider).** How the provider's creation is delayed or held. Per policy, use event-based control (hold creation until CF's lookup is observed, or until the retry loop is observed to finish) rather than a fixed sleep. The issue gives no value.
- **A6 (boundary cases for the fixed version).** To place creation "inside the retry window" or "after the retry window", the experiment must observe the retry iterations (count or `OS_TaskDelay` calls). It must not assume a wall-clock window.
- **A7 (RESERVED-window case).** Testing §4's `OS_ERR_INCORRECT_OBJ_STATE` hypothesis requires pausing the provider between `OS_OBJECT_INIT` and `OS_ObjectIdFinalizeNew` inside OSAL. That is a probe of OSAL internals, so label it a derived extension.
- **A8 (oracle scope).** That `CF_EID_ERR_INIT_SEM` plus CF exit is the failure, and that a delayed bind which later succeeds is the "normal retry" outcome. The roadmap §2.2 asks for this distinction.
- **A9 (secondary problem).** If provider restart and ID staleness are studied, the restart trigger and timing are not specified anywhere.
