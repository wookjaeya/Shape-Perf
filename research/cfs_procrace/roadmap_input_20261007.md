# Process-Level Race Detection in core Flight System
## 5개 사례와 기존 Process-Level Race 도구의 한계 분석에 근거한 cFS 탐지 도구 개발 로드맵

작성일: 2026-10-07  
수정일: 2026-10-07 — 기존 도구의 부족을 반영한 cFS 순서 위반 탐지 도구 신규 개발 방향 정리  
문서 상태: **현재 연구 로드맵**  
가칭: **Process-Level Race Detection in core Flight System**  
중심 사례: **C1·C2·C3·C5·R2**  

**[제안]** 연구의 선행 과제는 **① RacePro 등 기존 process-level race 탐지 도구가 C1·C2·C3·C5·R2를 탐지하는지 검증하고, ② 탐지하지 못한다면 무엇이 부족한지 증거로 설명하는 것**이다. 문헌상 적용 가능성과 실제 실행 결과를 구분한다. 확인된 부족을 개발 요구사항으로 연결하여 **cFS 작업 간 순서 위반을 탐지하는 새 도구를 개발한다.** 기존 도구의 엔진 재사용을 우선 목표로 두지 않으며, 기존 도구가 실제로 무엇을 못하는지는 검증으로 확정한다. 연구 관점은 §1.4, 검증 절차는 §4.7, 연구 단계는 §8, 결과 기록은 §10에 반영한다.

**[현재 확인 범위]** 사례 원문·핵심 댓글·선행 연구의 원 논문 또는 출판사·저자 기관의 자료를 대조했다. 문헌마다 전문·초록·서지만 확인한 범위를 구별한다. 이번 작업에서 cFS 빌드·5개 사례의 새 재현·선행 도구 실행·새 탐지 도구 실험은 수행하지 않았다. 아래 적용 가능성은 분석이며 성능·검출 결과는 향후 측정 항목이다.

## 1. 연구 목적과 범위

### 1.1 연구 목적

**[제안]** cFS 앱·task가 공유하거나 의존하는 자원·서비스·상태 변수·등록 정보에 대해, **기존 도구의 한계 분석에 근거하여 cFS 작업 간 순서 위반을 탐지하는 기법과 새 도구를 개발한다.** 순서 위반의 성립과 그로 인한 반환 오류·종료·잘못된 접근 등 실제 오류 발생은 별도로 검증한다.

기존 5개 기록의 초기화·등록 순서 문제를 출처 기반 검증의 출발점으로 삼는다. 연구 타깃은 cFS 작업 간 순서 위반 오류이며, 잠재적인 추가 순서 위반에 대한 적용 범위는 별도로 검증한다.

**[제안] 연구 수행 원칙:** 먼저 5개 사례별로 RacePro 등 기존 process-level 탐지 도구의 실제 탐지 여부를 확인한다. 미탐지 또는 적용 불가 결과는 관찰·자원 모델·의존성·동기화 모델·실행 탐색·판정·환경의 어느 단계에서 발생했는지 조사한다. 확인된 부족을 cFS 탐지 도구의 설계 요구사항으로 반영하여 새 도구를 개발한다. 신규 개발의 필요성과 효과는 기존 도구와의 비교로 평가한다. 재현 전용 연구의 결과는 탐지 결과와 별도로 기록한다.

### 1.2 Process-Level의 운영적 정의

**[사용자 정의]** Process-Level은 독립적으로 실행되는 cFS 앱·task 사이의 경쟁을 분석하는 수준이다. OS process의 분리를 필수 조건으로 두지 않는다.

**[출처 사실]** cFE ES 문서는 app을 main task와 0개 이상의 child task로 구성된 단위로, task를 OS의 실행 thread로 설명한다. ES·EVS·SB·TIME·TBL은 core application 또는 service로 지칭된다. [D1]

**[분석]** 실행 순서를 추적하는 기본 단위는 task이고, 소유·귀속은 app으로 정리한다. API 이름이 SB·EVS라고 해서 그 호출이 해당 서비스 task에서 실행된다고 가정하지 않는다. C3·R2의 SB→EVS 호출은 호출자 task의 동기 함수 경로다. [C3], [R2], [R2-analysis]

**[출처 사실]** RacePro는 공유 OS 자원에 대한 동기화 부족을 process race로 설명하고, order violation을 주요 원인 유형으로 다룬다. 프로세스와 스레드의 실행을 기록하며, 탐지 모델은 공유 kernel object에 대한 시스템 호출 효과를 사용한다. [P1] (§1·§2.1·§4·§5.2)

**[분석]** 이 논문은 Process-Level 연구 범주와 order violation이라는 결함 유형의 결합을 뒷받침한다. cFE 내부 등록표·서비스 상태를 다루는 새 탐지 도구의 자원·사건 모델은 본 연구에서 검증할 설계 과제다. RacePro가 cFS app/task를 그대로 정의했다거나 이 5개를 직접 검증했다고 인용하지 않는다.

### 1.3 집중 범위

| 항목 | 첫 연구에서의 범위 — [제안] |
|---|---|
| 실행 환경 | 하나의 cFE instance에 속한 앱·task. 먼저 재현 가능한 native 환경 |
| 실행 시기 | 앱 startup, core 초기화, 앱 생성·등록 공개 |
| 의존 대상 | 이름 있는 OSAL 객체, 서비스 준비 상태, cFE 전역 상태·등록표 |
| 주된 결함 유형 | cFS 작업 간 순서 위반 오류 |
| 기본 탐지 경로 | 기존 process-level 도구의 5개 사례 탐지 검증 → 미탐지·적용 불가 원인 분석 → 부족을 반영한 cFS 새 탐지 도구 개발 → 계측·허용 실행 순서 탐색 검증 |
| 정적 분석의 역할 | 의존 자원·사용 지점·실패 경로·계측 지점 및 탐색 후보 추출 |
| 첫 결과의 경계 | 실제 검증한 순서 위반·버전·환경. 모든 실행 순서나 다른 race 유형의 탐지를 주장하지 않음 |

### 1.4 공유자원·의존성과 순서 위반에 대한 연구 관점

**[사용자 정의/연구 관점]** 연구에서 확인할 관계는 다음 세 항목이다.

1. **cFS 어플리케이션 실행 간의 공유자원 및 의존성 정보가 존재한다.** 공유자원은 메모리에 한정하지 않으며, 서비스·상태 변수·이름 있는 객체·등록 정보 등을 포함한다. 의존성은 특정 실행이 다른 실행의 결과나 상태에 의존하는 관계를 포함한다.
2. **그 의존성(실행 순서 등)을 보장하는 동기화/실행 제어가 반영되지 못했다.** 동기화의 유무뿐 아니라 범위·시점·startup 절차·task 실행 허용 등 실제 보장이 필요한 관계를 충족하는지 확인한다. 일부 동기화가 있다는 것만으로 필요한 순서가 보장되었다고 판단하지 않는다.
3. **그 결과 order violation이 발생한다. 실제 오류로 이어지는지는 별개 사항이다.** 요구되는 순서와 실제 허용·관찰 순서를 비교하고, 이후 반환 오류·종료·범위 밖 접근 등 결과는 다른 항목으로 기록한다.

**[분석·검증 범위]** 이는 연구를 진행하는 관점이며, 5개 사례 모두에서 이미 입증된 공통 원인이라는 주장이 아니다. 공유자원·의존성의 근거, 필요한 순서, 현재 동기화/실행 제어의 실제 보장, 허용되는 위반 실행을 사례별로 확인한다. 의존성은 원 보고·코드·API·명세에 존재하거나 그 자료로 복원할 수 있는 관계를 뜻하며, 기계가 읽을 수 있는 의존성 정보가 이미 제공된다는 뜻은 아니다. 개발자가 공유자원을 식별하지 못했기 때문이라고 원인을 추정하지 않는다.

**[제안]** 기존 도구에도 같은 구분을 적용한다. 오류를 관찰했다고 순서 위반을 탐지한 것으로 세지 않고, 순서 위반을 식별했지만 오류가 관찰되지 않은 결과도 남긴다. R2처럼 해당 구성의 고정 초기화 순서가 문제인 경우는 scheduling race와 별도로 분류한다. 이 관점은 특정 준비·사용 수식이나 공통 탐지 알고리즘을 도입하지 않는다.

## 2. 5개 사례가 실제로 보여 주는 것

5개는 **연구 대상 기록 수**다. 확정된 독립 harmful race 5건 또는 cFS 전체에서의 발생 빈도를 뜻하지 않는다.

### 2.1 사실·실행 주체·의존 자원

| ID·1차 출처 | 실행 주체 — [출처 사실] | 공유/의존 대상 — [출처 사실] | 보고된 현상과 증거 | 남은 확인 |
|---|---|---|---|---|
| **C1: CF #184** | BP 앱의 생성 경로 ↔ CF 앱의 초기화 경로 | throttle counting semaphore의 존재·이름 등록 | BP를 먼저 시작해도 객체 생성 전에 CF가 조회해 초기화 실패·종료. 실제 BP–CF 통합은 댓글에 명시 [C1], [C1-BP] | 실제 semaphore 이름, BP 세부 task·함수, 원 통합 구성 미공개 |
| **C2: cFE #198** | EVA CWS의 제공 앱 late-init ↔ 다른 앱의 함수 요청 | 서비스의 late-init 완료·준비 상태 | 같은 startup sync를 통과한 뒤 초기화 완료 전 호출 관찰 [C2] | 앱·함수·변수·채널 실명과 구체 실패 출력 미공개 |
| **C3: cFE #73** | TIME task의 API 경로 ↔ SB·EVS 초기화 | SB AppId, EVS 자신의 AppId·등록/필터 데이터 | Microblaze 디버깅에서 초기화 전 사용과 범위 밖 접근·core crash 경로 보고 [C3] | 역사 소스·플랫폼 tuple 및 native 파생과의 차이 |
| **C5: cFE #72** | ES 앱 생성 코드 ↔ 신규 앱 main task | ES 앱/task 등록표와 TaskID–AppID 연결 | task 생성 전 unlock, 생성 후 등록 완료 사이 GetAppID 실패 가능 경로와 수정 보고 [C5], [C5-fix] | 특정 앱의 원 실패 로그, 역사 수정과 공개 revision의 대응 |
| **R2: cFE #2663** | ES/EVS task init의 SB API 호출 ↔ SB task AppInit | SB global AppId와 event API가 검증하는 ID | gdb로 ILLEGAL_APP_ID 반환 관찰. 후속 댓글은 SB AppId 준비 시점을 원인으로 분석 [R2], [R2-analysis] | 가능한 스케줄에 따른 결과 차이, body의 cFE 버전과 main 링크의 대응 |

**[출처 사실·분석의 경계]** R2 댓글의 원인 설명은 작성자의 코드 분석이다. 이 문서는 원 오류 관찰, 댓글의 가설, 향후 우리의 코드·실행 검증을 별도로 저장한다. C2의 요청을 SB 메시지나 특정 공유 메모리 접근으로 채워 넣지 않는다.

### 2.2 사례별 조사 대상과 결과

아래 조사 항목과 정상·오류 판정 기준은 **[제안]**이다. 필요한 순서는 코드·API 의미·원 보고·확보한 명세에 연결해야 한다. 공통 탐지 모델을 정의하는 표는 아니다.

| 사례 | 확인할 상태·의존성 | 사용·관찰 지점 | 판정할 결과 |
|---|---|---|---|
| C1 | 해당 이름의 counting semaphore가 성공적으로 생성·등록됨 | CF_CFDP_InitEngine의 OS_CountSemGetIdByName, status, 이후 분기 | 조회 실패가 CF 초기화 실패·종료로 전파되는지. 정상 재시도는 별도 해석 |
| C2 | 요청 함수가 실제로 필요로 하는 late-init이 완료됨 | 제공 앱의 초기화 완료와 요청 처리 진입 | 조기 요청이라는 명세 위반. crash·잘못된 출력은 원 자료에 없으며 파생 예제에서 별도 정의 |
| C3 | 호출 경로가 읽는 SB/EVS 상태와 필터 사용 조건이 만족됨 | TIME의 CreatePipe → event API → EVS 필터 접근 | 미준비 상태 사용과 범위 밖 접근의 인과. 순서 보호와 bounds check의 효과를 구별 |
| C5 | 현재 task를 app에 연결하는 ES 등록 정보가 완성되어 사용 가능함 | OS_TaskCreate 내부 실행 가능 시점, 등록 완료, 신규 main task GetAppID | GetAppID 실패와 그 처리. 새 task 실행 자체를 실패로 판정하지 않음 |
| R2 | SB AppId가 해당 event 경로에 필요한 상태로 설정됨 | ES/EVS 안의 SB API, 사용 AppId, EVS 반환 status | ILLEGAL_APP_ID 관찰. 결정적 의존성 오류와 실행 순서 경쟁을 구별 |

**[분석]** C1은 semaphore 카운터에 대한 동시 Take/Give 문제가 아니다. C5는 CFE_ES_CreateChildTask의 race가 아니다. C3의 SB AppId와 EVS AppId는 서로 다른 필드다. R2의 관찰 결과를 C3의 crash로 바꾸어 쓰지 않는다.

### 2.3 연구 타깃과 탐지 설계의 상태

**[제안]** C1·C2·C3·C5·R2는 출처 기반 조사와 검증의 출발점으로 유지한다. 각 사례의 실제 코드·API 의미·원 보고에 근거하여 필요한 선후 관계, 현재 실행이 보장하는 관계, 관찰된 오류를 구분한다. 초기화·객체 존재·등록 상태는 해당 사례의 조사 대상이지 모든 순서 위반을 정의하는 공통 조건이 아니다.

**[미정]** 공통 탐지 모델, 후보 생성 알고리즘, 실행 탐색 절차와 판정 방법은 기존 process-level 연구 및 사례 근거를 검토한 뒤 결정한다. 다섯 사례의 조건을 개별 등록하는 것만으로 잠재적인 추가 순서 위반에 대한 일반성을 주장하지 않는다.

## 3. Process-Level Race 선행 연구끼리의 비교

### 3.1 비교 범위와 선정 기준

**[사용자 결정]** 기존 탐지 도구 비교를 **process-level race 또는 system-level concurrency를 명시적으로 다루는 탐지·재현 연구**로 한정한다. thread data-race 전용 도구와 범용 동시성 검사기는 비교군과 단계별 적용 계획에서 제외한다. 

**[제안]** 비교 대상으로 선정하려면 원 논문 또는 저자·출판사의 1차 자료가 다음을 확인해야 한다.

1. 여러 실행 주체가 시스템 범위의 자원에 접근하거나 사건 순서를 바꾸어 발생하는 concurrency fault를 연구 대상으로 삼는다.
2. 접근·사건의 관찰, 실행 순서의 탐색·제어, 실패 재현 중 제공하는 기능이 명시되어 있다.
3. 원 연구의 실행 단위·자원·입력을 본 연구의 cFS app/task·자원에 대응시킬 때 추가하는 가정과 기능을 구별할 수 있다.

**[분석]** 원 논문의 OS process와 우리가 정한 cFS app/task는 실행 단위가 같다고 전제하지 않는다. 비교표에 원 연구의 단위와 자원을 남긴다. 또한 **새 결함의 탐지**, **이미 보고된 오류의 재현**, **변경 후 회귀 테스트**는 서로 다른 목표이므로 하나의 검출률 순위로 합치지 않는다.

**[검토 한계]** 초록만 확인한 기능을 임의로 세부 알고리즘·지원 플랫폼·cFS 지원으로 확대하지 않는다. SimRacer와 SIMEXPLORER를 별개 행으로 쓰는 것은 문헌 구분이며, 독립적인 검증 표본 수를 늘리는 방식이 아니다.

### 3.3 cFS에 적용할 때의 차이

표 전체는 **[분석]**이다. 원 연구의 기능과 cFS에서 필요한 대응을 비교하며, 실행으로 확인한 검출·누락 결과가 아니다.

| 선행 연구 | 비교할 방법·기능 | cFS 적용에서 확인·추가할 부분 |
|---|---|---|
| RacePro | 자원 효과 모델, 후보 순서 변경, 오류 결과를 통한 후보 검증 | OSAL 객체·cFE 등록표·준비 상태를 원 모델이 관찰하는지. 공유 메모리의 기록 기능과 해당 상태의 결함 탐지 기능을 구별 |
| SimRacer | 입력이 준비된 경우의 process-level 시험과 비교 실험 설계 | 원 구현·자원 모델·cFS task 귀속을 확보해야 함. §7.2의 타 프로그램 결과를 cFS 검출 성능으로 옮길 수 없음 |
| SIMEXPLORER | 실행 관찰, 오류 판정 조건, 세밀한 사건 제어의 결합 | cFS 함수·상태 공개 지점을 관심 사건으로 지정할 수 있는지, 실제 task 우선순위·동기화를 보존할 수 있는지 |
| RRF | 이미 보고된 실패에서 재현 지점과 순서를 좁히는 접근 | syscall·kernel event만으로 보이지 않는 AppId 갱신·등록표 공개·late-init에 대한 계측과 yield 지점 |
| DESCRY | 실패 로그로부터 소스·입력·순서를 연결 | 초기화 중 로그 생성 가능성, 로그–상태 연결, cFS/OSAL 모델, 가상 플랫폼 의존. 로그 순서만으로 실제 준비 순서를 단정하지 않음 |
| SysPro | 자연어 이슈에서 호출·소스 위치를 찾는 적용 자동화 | Linux 호출 사전 대신 cFS/OSAL API·내부 상태를 연결하는 근거. 지연 주입만으로 준비 조건이 생기지는 않음 |
| SimEvo | 수정된 초기화·등록 경로에 대한 영향 분석과 테스트 갱신 | cFS revision 변경과 task·자원 사건의 대응. 원/수정 버전 모두에서 유효한 입력·판정 조건 |

**[출처 사실]** RacePro는 process와 thread 및 공유 메모리의 실행을 기록한다. 그러나 §5.2의 탐지 모델은 kernel object에 대한 시스템 호출 효과다. “공유 메모리를 전혀 보지 않는다”와 “cFE 내부 준비 상태를 원 탐지 모델로 곧바로 판정한다”는 설명은 모두 피한다. [P1]

**[분석]** 기존 process-level 기법에도 오류 조건과 순서 제어를 결합한 접근이 있으므로, “논리적 order violation은 기존 기법으로 불가능하다”는 주장은 근거가 부족하다. 검증할 차이는 **cFS 사건을 얼마나 정확히 복원하고, 어떤 명세·adapter·계측을 추가해야 하는가**다.

아래 전체는 **[분석]**이며 모두 **NOT_RUN**이다. “추가 필요”는 원 도구가 영원히 확장 불가능하다는 판정이 아니다.

### 3.5 비교의 공정성과 결과 표기

전부 **[제안]**이다.

- **원 도구 실행**, **cFS 지원을 추가한 확장 실행**, **논문 방법의 재구현**을 다른 항목으로 기록한다. 기법 재구현을 원 도구의 결과라고 부르지 않는다.
- 먼저 원 연구가 지원하는 작은 예제로 설치·기록·제어·오류 판정이 동작하는지 확인한 뒤 cFS에 적용한다.
- 같은 cFS 실행·자원·판정 기준·시간 예산을 쓸 때만 검출·재현 비용을 비교한다. 로그나 버그 위치를 받은 기준선과 받지 않은 방법은 입력 차이를 표시한다.
- 새 연구와 기존 기법 모두에 동일한 cFS 의미를 준 실험과, 각 방법의 기본 기능만 사용한 실험을 나눈다. 의미 입력의 차이를 새 탐지 알고리즘의 효과로 귀속하지 않는다.
- 설치 실패·API 미지원·사건 미관찰은 **미지원/미확인**으로 기록한다. 검사를 실제 수행하여 판단할 수 있었는데 놓친 경우에만 해당 평가 집합의 누락으로 집계한다.
- 논문마다 다른 benchmark·입력·실패 정의의 수치를 합쳐 검출률 순위를 만들지 않는다.
- §3.2의 탐지·재현·회귀 테스트 역할에 맞는 지표를 사용한다. 알려진 보고서로 오류를 재현한 것을 미지 결함 자동 발견으로 주장하지 않는다.

## 4. 기존 Process-Level 기법의 적용 계획

모든 적용·변경은 **[제안]**이다. 본 문헌 검토는 향후 실제 실행을 위한 계획이며 도구를 구동한 결과가 아니다.

### 4.1 RacePro: 원 도구와 cFS 자원 모델의 경계부터 확인

1. 저자들이 공개한 저장소, 논문 당시 환경, recorder/replayer 의존성을 확보하고 version을 고정한다. 저장소가 공개되어 있다는 것과 현재 환경에서 실행된다는 것은 다르다. [P1-code]
2. 원 지원 대상의 작은 process-race 예제로 기록·후보 생성·재정렬·결과 검사를 확인한다.
3. cFS native 실행에서 OSAL 객체와 cFE 내부 field가 어떤 사건으로 나타나는지 조사한다. app·task·실제 OS process를 함께 기록한다.
4. C1은 객체 생성·등록과 이름 조회, C5는 등록표 공개와 신규 task 조회에 필요한 자원 효과를 대조한다.
5. 원 모델만으로 판정하지 못한다면 cFS 상태 사건·판정 조건을 추가한 **확장**으로 명시하고 그 비용을 측정한다.

앱을 각각 별도 OS process로 다시 작성한 예제는 원 cFS 실행과 다른 파생 모델이다. 그것만으로 cFS 직접 적용이 성공했다고 보고하지 않는다.

### 4.2 SimRacer/SIMEXPLORER: 관찰·제어의 cFS 대응

1. 원 구현 또는 충분한 알고리즘·플랫폼 자료를 확보한다. 전문·release가 확보되지 않은 상태에서는 세부 구현을 추정하지 않는다.
2. C1·C5에 대해 근거가 있는 자원 사건, 관심 지점, 정상·오류 판정 조건을 입력으로 구성한다.
3. 객체 공개·lookup 및 task entry·등록 공개의 순서를 제어할 수 있는지 확인한다.
4. task 생성 전 실행, 존재하지 않는 동기화, 실제 구성에서 불가능한 우선순위를 만드는 schedule은 제외한다.
5. 정상 retry·정상 거부·등록 완료 후 조회를 대조하여 단순한 조기 접근 경고와 최종 오류를 구별한다.

원 virtualization 환경 대신 별도 계측과 native 실행 hook으로 같은 관찰·제어를 구현한다면 **논문 방법의 cFS 재구현**이다. 원 도구 성능의 재현으로 이름 붙이지 않는다.

### 4.3 RRF: 알려진 실패의 재현 기준선

C1·C3·C5·R2의 보고·공개 소스에서 확인한 지점을 이용해 제한된 yield 또는 지연을 제안한다. 수작업으로 선택한 정보·지점·구성 수를 측정한다. 제공 앱의 비공개 부분이나 C2 late-init을 임의로 복원하지 않는다.

실패를 유도하는 순서가 실제 OSAL/task 의미에서 허용되는지 확인하고 원 오류와 반환 경로를 기록한다. 버그 위치를 미리 제공한 재현은 새 결함을 자동 발견한 결과와 별도다. RRF 초록만으로 모든 cFS API를 지원한다고 판단하지 않는다. [P4]

### 4.4 DESCRY·SysPro: 현장 로그와 이슈에서 재현 입력 복원

- **DESCRY 방식:** 원 로그가 있는 사례에서 메시지–source site–실패 경로를 연결한다. 로그가 없는 C2 등에는 해당 방식에 필요한 입력이 없음을 표시한다.
- **SysPro 방식:** CF/cFE 이슈에 나타난 API·함수·상태를 source와 연결한다. Linux syscall 사전을 cFS/OSAL 설명으로 바꾸는 것은 본 연구의 확장으로 표시한다.
- 원 보고의 실제 오류 결과를 판정 조건에 사용한다. 재현이 되더라도 사건 순서와 실패의 인과관계를 확인하기 전에는 race 검증 완료로 표기하지 않는다.
- 지연 주입은 발생 기회를 늘리는 방법이다. 허용 가능한 전체 schedule의 탐색이나 결정적 replay와 동일한 기능이라고 부르지 않는다.

**[출처 사실]** DESCRY의 §7은 로그–소스 분석, KLEE 기반 symbolic execution, Simics 기반 schedule generator 구현을 보고한다. [P5]

### 4.5 SimEvo: 수정 후의 회귀 테스트 단계

C1의 retry 수정, C5의 등록 보호 수정, C3/R2의 준비·방어 경로가 고정 revision에서 확보된 뒤 변경 영향에 따른 테스트 갱신을 검토한다. 원 논문의 변경 영향 분석을 cFS 자원·task 사건에 대응시키는 것은 추가 작업이다. 초기 5개 기록의 존재만으로 regression 범위나 성능을 확정하지 않는다. [P7]

### 4.7 핵심 검증: 기존 도구가 5개 사례를 탐지하는가, 못한다면 무엇이 부족한가

이 절 전체는 **[사용자 결정에 따른 제안]**이다. 실행 결과는 아직 없으며, 문헌상 미지원 추정은 실제 미탐지 결과로 바꾸지 않는다.

**첫째, 원 도구의 탐지 여부를 확인한다.** RacePro를 우선 기준선으로 삼고, SimRacer·SIMEXPLORER는 전문·구현·실행 환경을 확보한 범위에서 검증한다. 각 도구의 지원 예제로 정상 동작을 확인한 뒤, §7의 같은 cFS 사례 입력과 정상 대조를 적용한다. 원 도구의 기본 기능을 사용하는 실험과 cFS 명세·판정 조건 등을 추가한 실험을 분리한다. 필요한 원 자료가 없으면 원 사례는 자료 부족으로 남기고, 파생 실험 결과에는 원본성을 표시한다.

| 탐지 기준선 | C1 | C2 | C3 | C5 | R2 |
|---|---|---|---|---|---|
| RacePro 원 도구 | NOT_RUN | NOT_RUN | NOT_RUN | NOT_RUN | NOT_RUN |
| SimRacer 원 도구 | NOT_RUN | NOT_RUN | NOT_RUN | NOT_RUN | NOT_RUN |
| SIMEXPLORER 원 도구 | NOT_RUN | NOT_RUN | NOT_RUN | NOT_RUN | NOT_RUN |

표의 각 칸에는 앞으로 **탐지 / 미탐지 / 적용 불가 / 자료 부족 / 미실행**과 결과 기록의 위치를 남긴다. 탐지는 도구 출력이 근거 있는 순서 위반을 식별하고, 해당 순서가 실제 구성에서 허용됨을 확인한 경우다. 단순 crash·반환 오류만 보고되었다면 오류 관찰로 별도 기록한다. 미탐지는 실행·지원 범위·입력·판정 기준이 확인된 평가에서 대상 순서 위반을 식별하지 못한 경우이며, 탐색 예산도 함께 남긴다. 적용 불가나 자료 부족을 미탐지/FN으로 집계하지 않는다. R2가 결정적 의존성 오류로 확인되면 race 검출률의 양성 분모에서 제외하고 진단 결과를 남긴다.

**둘째, 미탐지 지점을 분해하여 원인을 검증한다.** 다음 분류는 문헌의 공식 taxonomy가 아닌 본 연구의 진단 절차다. 여러 원인이 함께 있을 수 있으며, trace·모델·도구 출력·설정의 근거를 각각 남긴다.

| 확인 단계 | 확인할 부족 또는 제약 | 원인 확인에 필요한 증거·대조 |
|---|---|---|
| 사건 관찰 | 생성·등록·상태 갱신·호출·조회 사건이 기록되지 않음 | native 사건 기록과 원 도구 trace 비교. syscall 기록과 내부 상태 관찰을 구별 |
| 자원 표현·연결 | 접근이 있어도 동일 자원·이름·ID·등록표 관계로 연결되지 않음 | 모델의 자원 key·효과와 실제 객체·필드 대응. 연결 보완 전후 비교 |
| 의존성·요구 순서 | 관찰한 접근에서 필요한 선후 관계를 표현·도출하지 못함 | 출처 있는 의존성 및 후보 생성 규칙 비교. 추가 명세·수작업 입력량 기록 |
| 실행 주체·동기화 모델 | app/task 귀속 또는 lock·startup·task 생성의 보장을 다르게 해석 | 실제 호출자와 모델 실행 단위, 실제 동기화와 도구의 순서 관계 대조 |
| 후보 생성·실행 탐색 | 관련 사건은 있지만 후보가 없거나 위반 순서를 탐색·실행하지 못함 | 후보 목록, 탐색한 순서, hook·replay 제약, 시간·횟수 예산. 더 큰 예산과 비교 |
| 결과 판정 | 순서 위반을 식별할 정보는 있지만 기본 판정이 오류 결과만 검사하거나 정상 retry와 혼동 | 중간 후보·실행 trace·판정 조건·최종 출력 대조. 순서 위반과 오류 발생을 따로 기록 |
| 적용 환경·입력 확보 | kernel·가상 플랫폼·API·원 코드·로그가 확보되지 않음 | 설치/빌드 기록, 미지원 API, 미확보 자료. 알고리즘의 미탐지와 별도 기록 |

**셋째, 부족한 기능을 보완했을 때 결과가 바뀌는지 확인한다.** 원인에 대응하는 명세·adapter·계측·자원 모델·판정·순서 제어를 최소 단위로 추가하고 동일 입력·가능하면 동일 예산에서 비교한다. 이 대조는 부족 원인의 검증 실험이며 기존 엔진 재사용을 최종 개발 목표로 정하는 절차가 아니다. 확인한 부족은 새 cFS 탐지 도구의 기능 요구사항으로 옮긴다. 보완 후에도 탐지되지 않으면 해당 기능만으로 충분했다고 주장하지 않는다. 기본 출력은 없지만 중간 후보가 존재하는 경우도 구분한다. 개별 사례 위치·필요 순서를 사람이 제공했다면 알려진 결함의 검사·재현 결과이며, 미지 결함 자동 탐지로 일반화하지 않는다.

**[제안] 산출물:** 도구×5개 사례의 탐지 결과표, 단계별 미탐지·적용 불가 근거, 보완 기능과 diff, 보완 전후 대조 결과. RRF·DESCRY·SysPro는 §3.2의 역할대로 재현 성공·실패와 부족 입력/기능을 별도 표로 남긴다. SimEvo는 수정 후 회귀 평가로 유지한다. 새 cFS 탐지 도구의 요구사항·지원 범위·평가 항목은 이 결과를 근거로 구체화한다.

## 6. cFS 순서 위반 탐지 도구의 신규 개발 계획

### 6.1 설계 요구사항의 도출

**[제안]** §4.7에서 확인한 기존 도구의 부족을 근거로, cFS 앱·task의 공유자원·의존성과 실제 동기화/실행 제어를 다루는 새 탐지 도구를 설계·개발한다. 구현 기반과 공통 탐지 알고리즘은 아직 확정하지 않는다.

| 개발 요소 — [제안] | 요구사항을 정할 근거 | 검증할 결과 |
|---|---|---|
| 자원·사건 표현 | 기존 도구가 관찰·연결하지 못한 객체·서비스·상태·등록 정보와 source site | 같은 공유/의존 대상과 실제 app/task를 정확히 연결하는지 |
| 의존성과 실행 제어 분석 | 필요한 순서의 출처와 실제 lock·startup·task 생성의 보장 | 요구되는 관계와 실제 보장을 구별하는지 |
| 순서 위반 탐지·판정 | 기존 후보 생성·판정의 부족과 사례별 정상 대조 | 순서 위반을 식별하고 정상 retry·거부를 구별하는지 |
| 실행 기록·탐색·검증 | 원 도구의 사건·스케줄 제어 범위와 재현 제약 | 허용되는 실행에서 위반을 관찰·재현하고 불가능한 순서를 제외하는지 |
| 근거를 포함한 결과 보고 | source·사건·의존성·도구 출력의 대응 | 순서 위반 여부와 실제 오류 발생을 별도로 설명하는지 |

신규 도구의 설계 요소는 확인된 부족과 연결한다. 5개 사례의 위치나 정답 조건만 등록하여 탐지한 결과와 추가 순서 위반에 재사용 가능한 탐지 규칙은 구별한다. 특정 사례를 탐지하지 못한 원인이 자료·환경 부족이라면 새 알고리즘의 필요성으로 곧바로 해석하지 않는다.

### 6.2 기록할 사건

**[제안]** 사건 하나는 task token, app 귀속 정보, source site, 자원 key, 동작 종류, 관찰 값/status, 준비 단계, 실제 동기화 근거를 포함한다.

| 사례 | 필요한 사건 |
|---|---|
| C1 | 객체 생성·등록, 이름 조회와 status, retry, CF 초기화 결과 |
| C2 | early/late-init 상태, 필요한 단계 완료, 요청 진입, 요청 처리/거부 |
| C3 | SB/EVS 상태 공개, TIME 안의 API 호출, 사용한 AppId, 필터 접근·오류 |
| C5 | task 생성·entry, 등록표 공개, lookup의 실제 보호·결과 |
| R2 | SB AppId 설정, ES/EVS caller의 SB 호출, EVS에 전달한 ID와 반환값 |

event 종류나 도구 내부 모델 이름을 정의하면 모두 본 연구의 제안 명칭이라고 표시한다. API 이름만으로 필요한 선후 관계를 임의 생성하지 않는다.

### 6.3 계측의 정확성을 좌우하는 문제

모두 **[제안]**인 구현·검증 요구다.

1. **실제 공개 시점.** 생성 함수가 return하기 전에 다른 task가 객체를 찾을 수 있다. 함수 exit 로그가 늦었다는 이유만으로 조기 사용을 판정하지 않는다. 실제 공개 지점·사용 status·계측 구간을 함께 사용한다.
2. **기록 순서와 실행 순서.** 여러 buffer의 flush 순서는 원 사건 순서가 아니다. per-task sequence, 실제 동기화, 관찰 값으로 판단하고 필요한 관계를 복원할 수 없으면 미확인으로 남긴다.
3. **관찰이 경쟁을 없애는 문제.** 모든 probe를 전역 logger mutex로 직렬화하면 새로운 동기화가 생길 수 있다. per-task buffer 등 방식과 비계측 실행을 비교한다.
4. **공유 값의 중복 읽기.** 기록하려고 원 프로그램이 읽지 않던 field를 다시 읽으면 새로운 접근을 만든다. 가능한 한 원 load·API가 이미 관찰한 값을 기록한다.
5. **초기화 서비스 의존 금지.** recorder가 EVS event, SB pipe, TIME service, 준비 전 GetAppID에 의존하면 C3·C5·R2의 관찰 자체가 실패하거나 실행을 바꾼다. 독립적인 기록 경로를 사용한다.
6. **최적화·inlining.** probe와 source mapping을 최적화 단계에서 보존하고 계측한 바이너리를 확인한다. 알려진 source site가 누락된 경우 coverage에 반영한다.
7. **손실·부하.** startup 사건의 drop·buffer 부족·실행시간 증가를 측정한다. 로그가 없다는 사실을 정상 실행 증거로 사용하지 않는다.
8. **동적 loader.** 본체만 계측하고 실제 앱·library를 누락하지 않는다. module별 계측 지원 상태를 기록한다.

### 6.4 동적 관찰과 잠재 race 탐지를 구별

**[제안]**

- 관찰 모드는 실제 실행에서 출처에 근거한 순서 위반 후보와 결과를 확인한다.
- 탐색 모드는 기존 scheduler/model checker 또는 의미를 검증한 hook으로 다른 허용 실행을 만들어 검사한다.
- 예측 모드는 trace·소스·동기화 모델에서 가능한 다른 순서를 제안하고 native 실행으로 검증한다.

좋은 실행에서 경고가 없었다는 것은 나쁜 순서가 없다는 증명이 아니다. 반대로 두 사건의 timestamp를 바꾼 것이 실행 가능한 witness라는 뜻도 아니다.

task 생성 전 실행, 실제 동기화가 금지하는 순서, 고정 startup 절차가 허용하지 않는 실행을 강제로 만들지 않는다. 특히 R2에서 SB를 임의로 먼저 실행시킨 결과만으로 원 구성에 race가 있다고 판정하지 않는다.

## 7. 사례별 실험 설계

### 7.1 원본성의 구분

**[제안]** 각 입력을 다음 중 하나로 기록한다.

| 입력 종류 | 의미 |
|---|---|
| 원 환경·원 코드 재현 | 원 보고의 version/config/platform과 실제 앱을 확보한 경우 |
| 공개 코드 + 파생 환경 | 관련 원 코드 일부를 유지하고 provider·플랫폼·실행 제어를 대체한 경우 |
| 역할 기반 파생 예제 | 비공개 앱·상태를 근거 있는 역할·명세로 작성한 경우 |
| 합성 대조 | 하나의 보호·guard·retry·명세 조건을 통제한 실험 입력 |
| 확보 불가 | revision·환경·자료를 확보하지 못한 상태. 정상/음성으로 분류하지 않음 |

각 파생 변경, 모델 adapter, 추가 assertion, scheduling hook을 diff로 남긴다.

### 7.2 5개 실험 package

모든 변형은 **[제안]**이다. 특정 횟수·성능·검출 결과를 미리 채우지 않는다.

| 사례 | 결함·의존성 입력 | 정상·경계 대조 | 결과 판정 기준과 주의 |
|---|---|---|---|
| C1 | 공개 CF 경로 + 객체 생성이 늦는 provider | 생성 후 사용, retry 안의 생성, retry 종료 뒤 생성, 존재하지 않는 이름 | CF status·engine 상태·종료. 없는 이름의 설정 오류와 timing 문제 구별 |
| C2 | early-init sync 뒤 late-init 진행 중 요청하는 역할 기반 앱 | late-init 완료 보장, NOT_READY 처리, 실패 허용/재시도 | 조기 호출을 먼저 확인. 인위적 assertion/crash는 파생 결과로 표기 |
| C3 | 역사 호출 경로를 보존한 core 상태 미준비 입력 | startup 준비 보장, bounds check만 강화, 준비 후 호출 | 미준비 값·필터 접근·범위 밖 접근과 실제 실행 결과. 원 Microblaze 재현과 native 파생 구별 |
| C5 | task 생성 뒤 등록 공개가 늦을 수 있는 경로 | 같은 실제 lock으로 조회까지 보호, 공개 후 실행 허용, 실패 후 정상 재시도 | 등록 상태·TaskID 연결·GetAppID 결과. CreateChildTask 사례로 바꾸지 않음 |
| R2 | 고정한 소스에서 원 event 오류 경로 | 실제로 허용되는 준비 우선 실행, fixed startup 순서, 별도 잘못된 ID 대조 | 반환 오류와 경로. scheduling으로 성공/실패가 달라지는지 먼저 판정 |

**[출처 사실]** C1의 공개 수정은 NAME_NOT_FOUND에 대한 제한 재시도이며 영구적인 준비 보장이 아니다. [C1-fix]

**[출처 사실]** C5의 댓글은 과거 runtime 앱 loading 중 watchdog servicing deadline 문제로 lock 범위를 줄였다는 변경 맥락을 설명한다. [C5-context]

**[분석·제안]** 따라서 보호를 넓힌 수정이 의미상 안전하다는 결과와 지연·blocking 비용을 구별한다. C5를 근거로 모든 앱 생성 절차를 무조건 긴 critical section으로 만들라고 권고하지 않는다.

### 7.3 R2의 분기

R2는 다음 중 어느 결과가 나오는지 판정하는 연구 대상이다.

| 향후 결과 | 분류·처리 — [제안] |
|---|---|
| 같은 입력·허용 환경에서 실행 순서에 따라 성공/실패가 달라짐 | 준비 순서 race의 검증된 양성 후보. 실패 trace와 성공 대조를 보존 |
| 해당 구성의 startup 절차가 항상 미준비 사용을 강제 | 결정적 초기화 의존성 결함. 해당 구성의 scheduling race TP에 합산하지 않음 |
| 실제 오류가 다른 원인임 | 원 관찰은 유지하고 SB AppId 가설을 수정 |
| 허용 실행·revision을 확정하지 못함 | 미확인. 음성/TN으로 취급하지 않음 |

고정 구성에서 결정적인 오류여도, 다른 허용 구성에서 race가 될 수 있는지는 별도 질문이다. 가정을 바꾼 실험을 같은 결과로 합치지 않는다.

## 8. 새 연구 로드맵

단계·관문은 **[제안]**이다. 기간은 버전 복원·환경 확보·개발 여건을 확인한 뒤 산정한다. 미확인 자료에 근거해 주차별 완료를 확약하지 않는다.

| 단계 | 작업 | 5개 사례의 역할 | 산출물 | 다음 단계의 관문 |
|---|---|---|---|---|
| **A. 근거와 입력 고정** | 원 보고·수정·필요한 순서·version tuple·원본성·정상·오류 판정 기준 작성 | 전체 5개. R2 revision 불일치와 C2 비공개 범위 명시 | 사례 ledger, source snapshot, 재현/파생 구분 | 각 사례의 사실·가설·요구 조건이 분리됨 |
| **B. 기존 도구 탐지 검증·부족 분석** | §4.7에 따라 기존 도구의 사례별 실제 탐지 여부를 확인하고 미탐지 단계·부족 기능·탐색 예산·환경 제약을 구별 | C1·C5 우선 후 전체 5개 결과 기록. C2 원/파생 분리, R2 race 여부 별도 확인 | 도구×사례 결과표, trace·후보·출력, 미탐지/적용 불가 원인과 근거 | 새 도구가 해결할 부족과 평가 가능한 범위가 근거로 특정됨. 부족이 입증되지 않은 부분은 미확인으로 유지 |
| **C. cFS 새 탐지 도구 설계·개발** | 확인된 부족을 자원·사건·의존성·실행 제어·후보 생성·판정 요구사항으로 반영하여 새 도구 개발 | 실제 자원·호출자·필요 순서와 오류 결과를 구별. 공통 탐지 모델은 근거 검토 후 결정 | 요구사항–부족 근거 대응표, 설계·구현, 사건 기록·결과 보고 | 구현이 요구사항을 충족하고 정상 retry·고정 의존성 오류·순서 위반을 구별함 |
| **D. 비교·탐색·적용 범위 검증** | 같은 의미 입력·가능하면 같은 예산에서 기존 도구와 새 도구 비교. 허용 순서 탐색과 기능 요소 제거 실험 | 5개 사례와 명시된 파생·대조. R2 분류 및 C3/R2 관련성 유지 | 탐지 변화·위반 trace·오류 결과·비용·지원 범위 | 확인된 부족을 새 도구가 해결하는지, 다른 가정이나 입력이 차이를 설명하는지 구별 |
| **E. 기여 확정** | 새 도구의 효과·적용 부담·한계와 증거 정리 | 5개 결과를 독립·관련 묶음으로 보고 | 논문 초안, 재현 자료, 주장–증거 표 | 기존 도구 대비 해결한 부족과 아직 해결하지 못한 범위를 명확히 제시 |

### 8.1 가장 먼저 실행할 작업

1. 5개 사례의 version/config tuple, 필요한 조건의 출처, 결과 판정 기준을 동결한다.
2. C1과 C5를 먼저 실행 가능하게 만든다. 둘은 객체 존재와 등록표 공개라는 서로 다른 자원 모델을 검증한다.
3. RacePro 등 원 도구의 지원 예제부터 확인한 뒤, 5개 사례의 탐지 여부를 §4.7 결과표에 기록한다. 원 도구 기본 기능과 cFS 의미를 추가한 확장·재구현을 구별하고, 지원·예산·입력 차이를 남긴다.
4. C3·R2에서 사용하는 실제 AppId와 event 반환을 기록해, 결과 오류와 준비 순서를 연결한다.
5. C2는 비공개 부분을 확보하거나 명세 입력이 있는 파생 예제로 제한한다.
6. 미탐지는 관찰·자원·의존성·동기화·후보/탐색·판정 중 원인을 trace와 코드로 확인한다. 자료 부족·적용 불가와 구별하고, 부족을 확인하는 대조 실험을 수행한다.
7. 확인된 부족을 요구사항으로 반영하여 cFS에 맞는 새 탐지 도구를 개발하고, 같은 입력·의미·예산 조건에서 기존 도구와 비교한다. 기존 도구로 이미 충분한 부분에 대해서는 새 도구의 우위를 주장하지 않는다.

### 8.2 단계 결과에 따른 설계 변경

| 확인된 결과 | 이후 선택 — [제안] |
|---|---|
| 기본 도구가 대상 순서 위반을 충분히 탐지·설명 | 해당 부분은 기존 도구의 부족으로 주장하지 않음. 새 도구가 해결할 별도 요구사항이 있는지 확인하고 신규 개발 필요성을 평가 |
| cFS 사건·판정 조건을 준 process-level 기법이 검출 | 부족이 사건·명세 입력에 있는지 엔진에 있는지 구별. 새 도구의 자원·의존성 분석과 적용 부담을 같은 의미 입력에서 평가 |
| 수동 runtime checker는 검출하지만 자동 계측이 누락 | 탐지 규칙을 늘리기 전에 source/IR 복원과 계측 정확도를 개선 |
| native 실행과 선행 기법의 자원·사건 모델 결과가 다름 | OSAL·task·상태·guard 및 실행 단위의 차이를 조사 |
| R2가 race가 아님 | 의존성 오류의 구별 능력을 평가. 5개 중 하나를 임의의 양성으로 대체하지 않음 |

|---|---|
| **RQ1.** 5개 기록에서 실제 필요한 선후 관계와 실행 순서 의존성을 얼마나 복원할 수 있는가? | 출처·source site·manual annotation·미확인 항목 대조 |
| **RQ2-a.** RacePro 등 기존 process-level 탐지 도구는 C1·C2·C3·C5·R2의 순서 위반을 탐지하는가? | §4.7의 도구×사례 실제 실행 결과. 후보·순서 위반·오류 관찰·원/파생·기본/확장·입력/예산 차이를 구별 |
| **RQ2-b.** 탐지하지 못한다면 어느 단계에서 무엇이 부족하며, 어떤 보완이 필요한가? | 단계별 trace·모델·출력 대조, 미탐지와 환경/자료 제약 분리, 기능별 보완 전후 비교. 재현 연구의 부족 입력·기능은 별도 평가 |
| **RQ3.** cFS 작업 간 순서 위반 탐지 방법을 추가 순서 위반 사례에 적용할 수 있는가? | 판정 설계를 동결한 뒤 설계에 사용하지 않은 사례에서 규칙·입력·알고리즘 변경과 지원 범위를 구분하여 평가 |
| **RQ4.** 새 cFS 탐지 도구는 확인된 기존 도구의 부족을 해결하는가? | 부족 근거와 새 기능 대응, 동일 입력·가능하면 동일 예산의 탐지 결과 및 기능 요소 제거 실험 |
| **RQ5.** 새 도구의 적용 부담과 실행 비용은 어느 정도인가? | 명세·수작업 입력량·계측 누락·부하·지원 범위를 기존 도구와 구분하여 측정 |
| **RQ6.** 실행 탐색이 단순 반복보다 실패 순서의 발견·재현을 개선하는가? | 같은 입력·정상·오류 판정 기준·시간 예산에서 반복·지연 주입·가능한 순서 탐색 비교 |

### 9.1 비교군

**[제안]** 탐지·재현 선행 연구는 process-level 대상으로 한정한다. 새 cFS 도구와 그 기능을 제거한 변형은 제안 방법 내부의 비교이며 외부 선행 도구라고 세지 않는다.

| 비교군 | 비교 목적·조건 |
|---|---|
| 원 native 실행·기존 재현 절차 | 원 오류와 조건을 확인하는 기준 실행 |
| RacePro 원 도구 또는 명시된 cFS 확장 | 공유자원 효과·순서 변경·실패 검증의 적용 범위 |
| SimRacer/SIMEXPLORER 원 도구 또는 명시된 재구현 | 같은 자원 사건·입력·오류 조건에서 관찰·제어의 효과 |
| RRF 방식의 보고된 오류 재현 | 수작업 지점·구성 입력을 포함한 재현 성공·비용 |
| DESCRY 방식의 로그 기반 재현 | 원 로그가 있는 부분집합에서 source·입력·schedule 복원 |
| SysPro 방식의 보고서 기반 재현 | 보고서→cFS API/상태→source site 연결. 추가 사전·수작업 입력량 포함 |
| 새 cFS 순서 위반 탐지 도구 | 기존 도구에서 확인한 부족을 해결하는지, 같은 입력·의미·예산에서 탐지와 비용 비교 |
| 새 도구의 기능 요소를 제거한 변형 | 자원 연결·의존성·실행 제어·판정 기능의 효과를 개별 확인 |
| 새 도구에 순서 탐색 없이/추가하여 실행 | 단순 반복·지연 주입·허용 사건 순서 탐색의 차이 |
| SimEvo식 변경 영향·회귀 테스트 | 수정 revision과 동결한 테스트가 확보된 후 후속 평가 |

외부 도구를 실행할 수 없으면 문헌상 비교 또는 명시된 기법 재구현으로 남긴다. 자료 부족·설치 실패를 성능 열의 0이나 미검출로 바꾸지 않는다. 알려진 실패 재현은 신규 결함 발견과 다른 지표로 보고한다.

### 9.2 모델 요소 제거 실험

**[제안]** 같은 엔진에서 자원 identity, phase 구별, caller 귀속, 반환값·retry, 실제 동기화, 결과 checker를 하나씩 제거하고 어떤 판정이 바뀌는지 확인한다.

같은 기능을 동시에 제거해 자원·의존성 모델과 탐색 효과가 섞이게 하지 않는다. source mapping과 실행 사건이 다른 비교도 별도로 표시한다.

### 9.3 일반화 평가의 한계

**[분석·제안]** 5개는 이미 알고 있는 동기 사례다. 이를 모두 설계에 사용한 뒤 “미지 사례 일반화”라고 표현하지 않는다.

정의·규칙을 동결한 뒤 별도 변형·revision·설정을 평가한다. 변형은 부모 사례의 파생으로 집계하고 새로운 독립 실제 버그 수에 더하지 않는다. C3·R2는 SB 준비 의존성이 관련되므로 완전히 독립한 일반화 사례라고 취급하지 않는다. 추가 실제 앱·프로젝트 평가를 확보하면 별도 외부 검증으로 보고한다.

## 10. 결과 표기와 평가 지표

### 10.1 탐지 결과를 단계별로 기록

**[제안]**

| 결과 상태 | 필요한 증거 |
|---|---|
| 후보 | 자원·작업 간 필요한 선후 관계·가능한 실패 경로의 source 근거 |
| 모델 witness | 명시된 의미·경계에서 실행 가능한 위반 순서 |
| 실행 관찰 | native 또는 표시된 파생 실행의 상태·status·결과 |
| 검증된 순서 위반 | 출처 있는 요구 순서와 허용 실행에서의 실제 순서가 어긋남을 확인. 실제 오류 발생 여부는 별도 |
| 검증된 scheduling race | 원 조건을 보존하는 허용 실행들의 순서 차이가 대상 순서 위반의 발생 여부에 영향을 줌 |
| 오류로 이어진 순서 위반 | 위반과 반환 오류·종료·잘못된 접근 등의 인과를 추가 확인 |
| 결정적 의존성 오류 | 해당 구성에서 고정된 잘못된 초기화 순서와 결과 |
| 정상/보호됨 | 근거 있는 보호·guard·정상 실패 처리와 검증 범위 |
| 미확인/미지원 | 명세·revision·API·실행·계측의 부족 |

경고가 없었다는 결과만으로 “정상/보호됨”을 선택하지 않는다. 모델 witness와 실행 관찰도 자동으로 같은 증거 수준이 되지 않는다.

| 영역 | 측정 — [제안] |
|---|---|
| source 추출·계측 | 근거가 있는 site 대비 복원/계측 site, 잘못된 귀속, 누락, 수작업 입력량 |

## 11. 예상 기여와 주장 허용 조건

모두 **[제안]**이다. 구현·평가 전에는 기여가 입증된 결과로 표현하지 않는다.

| 제안 기여 | 입증할 것 | 현재 주장하지 않을 것 |
|---|---|---|
| 5개 기록의 출처 기반 검증 자료 | version·원본성·명세·trace·원인 구별 | cFS 전체 빈도, 독립 harmful race 5건 |

| 기존 process-level 도구의 탐지 여부·부족 분석 | 5개 사례별 실제 결과, 미탐지 단계·근거, 보완 전후 변화와 비용 | 미실행/적용 불가를 미탐지로 처리, 기존 기법으로 원리상 불가능 |
| cFS 새 탐지 도구와 source-linked 설명 | 확인된 부족의 해결, 순서 위반 탐지·정상 대조·근거 설명·적용 비용 | 자원·의존성을 근거 없이 자동 이해함, 기존 도구보다 항상 우수함 |
| 실행 탐색과 검증 연결 | 허용 순서 witness와 native 결과의 대응 | 모든 실행 탐색, 비행 환경 고장 예측 |

**[사용자 결정·제안]** 첫 핵심 질문은 **기존 process-level 도구가 5개 사례를 탐지하는지, 탐지하지 못한다면 무엇이 부족한지**다. 그 결과에서 확인된 부족을 반영하여 cFS에 맞는 새 탐지 도구를 개발하고, 부족을 해결하는지 비교 검증한다. 기존 도구가 충분한 부분과 새 도구가 필요한 부분을 구별하여 신규 개발의 필요성과 기여 범위를 설명한다. 공유자원·의존성, 실제 실행 제어, 순서 위반과 오류 발생을 분리한 근거를 유지한다.

## 12. 이번 작업의 결과와 첫 완료 기준

**[출처 검토 완료]** 5개 사례 근거를 유지하고 process-level 탐지·재현·회귀 연구끼리의 비교로 개정했다. 문헌별 확인 범위는 §3.2·§4.6·§13에 기록했다.

**[미실행]** 새 재현, process-level 도구 적용, 새 cFS 탐지 도구 구현·실행, 성능 측정은 수행하지 않았다.

**[현재 개발 방향]** 기존 도구의 5개 사례 탐지 여부와 부족을 먼저 검증하고, 확인된 부족을 반영한 cFS 순서 위반 탐지 도구를 새로 개발한다. 공유자원·의존성, 실제 실행 제어, 순서 위반과 실제 오류 발생을 별도 평가한다. 현재 내용은 연구 계획이며 새로운 실험 결과가 아니다.

**[제안] 선행 검증·부족 분석 완료 기준**

- C1·C5의 근거를 보존한 실행 package와 정상 대조가 있다.
- C2·C3·R2는 원/파생/미확인 범위 및 필요한 명세가 분리되어 있다.
- RacePro 등 탐지 기준선의 5개 사례 결과표에 실제 탐지/미탐지 또는 구체적인 적용 불가·자료 부족 원인이 있고, 원 도구/확장/재구현이 구분되어 있다. 아직 미실행인 항목은 완료로 처리하지 않는다.
- 미탐지 항목에는 단계별 부족의 근거와 보완 기능이 있으며, 보완한 항목은 같은 입력에서 전후 결과를 비교한다. 환경·자료 제약으로 원인 검증이 불가능하면 그 범위와 남은 과제를 명시한다.
- 공유자원·의존성의 출처, 실제 동기화/실행 제어, 순서 위반 여부와 실제 오류 발생 여부가 별도 기록되어 있다.
- 순서 위반 판정 방법의 근거와 지원 범위를 설명한다. 공통 모델은 사전에 확정하지 않으며 추가 순서 위반 사례의 적용 가능성을 별도로 평가한다.
- R2의 race 여부를 판정하거나 판정에 부족한 증거를 명시한다.

**[제안] cFS 새 탐지 도구 개발·평가 완료 기준**

- 자동 계측이 수동 site와 대응하고, 기록이 결함의 실행을 왜곡하는 정도를 측정한다.
- 기존 도구의 부족 근거와 새 도구 기능을 연결하고, 동일 입력·의미·예산 조건에서 해결 여부와 비용을 비교한다.
- 기존 도구로 충분한 부분에는 신규 개발의 우위를 주장하지 않으며, 새 도구의 실제 기여와 한계를 구분한다.
