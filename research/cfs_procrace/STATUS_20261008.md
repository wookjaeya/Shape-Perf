## 2. ENV에서 확인한 사실

- **빌드 대상:** `nasa/cFS` `main` = 태그 `v7.0.1`(`088b2fa8`, 2026-05-13). README L50이 "v7.0.1: OFFICIAL RELEASE"라고 적은 판이다. submodule 25개의 commit을 고정했다.
- **빌드 방법:** README L102–105 그대로다. 일반 사용자로 `make native_std.prep`, `make native_std.install`을 실행했다. bundle의 `Makefile`과 `sample_defs/`는 고치지 않았다.
  - 결과: 경고 0, 성공.
  - 코드는 `-g`만 붙고 `-O` 옵션이 없어 `-O0`으로 빌드됐다(C5).
- **CF:** 문서화된 기본 구성에 이미 들어 있다(`sample_defs/targets.cmake` L91). 추가하거나 바꾼 것이 없다.
- **실행:** README L109–114대로 7회 실행했다. 모두 약 1.6초 만에 OPERATIONAL에 도달했고, 앱 15개가 모두 올라왔다.
- **매 실행 앱 초기화 완료 순서가 달랐다.** POWER ON 부팅 4회도 서로 달랐다. 원인을 스케줄링으로 단정하지는 않았다. 순서는 cFE 타임스탬프로만 판단한다.
- **컨테이너의 제약.** 우회책은 적용하지 않았고 모두 기록했다.
  1. 일반 사용자 실행에서는 task 우선순위가 적용되지 않는다(best effort). README L102가 문서화한 동작이다. 원인은 `pthread_setschedparam`이 `EPERM`을 돌려주는 것이고, 그래서 startup script의 우선순위가 스케줄링에 효과가 없다(E4).
  2. 메시지 queue 깊이는 `msg_max`=10으로 잘린다. 10보다 깊은 queue가 모두 그렇다. 예를 들어 DS는 45가 10으로 줄고, `SBNSubPipe`에서 overflow가 실행마다 8–16번 났다(E5).
  3. `/proc/schedstat`이 없어서 HS의 system monitor가 실패한다. 그러면 HS는 startup sync를 건너뛴다(D-3).
  4. 커널에 IPv6가 없어서 OSAL 단위 시험 하나가 실패하고 make가 멈춘다(C12).
  5. root로 실행하면 실시간 우선순위는 되지만 queue 생성이 실패한다. 컨테이너가 root에서도 `CAP_SYS_RESOURCE`를 뺐기 때문이다(D-4).
- **C1 경로는 기본 구성에서 실행되지 않는다.** 기본 CF table의 throttle semaphore 이름이 빈 문자열이기 때문이다(`cf_def_config.c` L60, L78). 이 경우 조회 코드(`cf_cfdp.c` L1270–1291)를 아예 타지 않는다. 그런데 CF 문서(`cfs_cf.dox` L507–509)는 "기본으로 TO가 semaphore를 제공한다고 가정한다"고 적어, 기본 table과 어긋난다(D4, D7).

## 3. 결정 요청

항목마다 선택지는 모두 레퍼런스가 있는 것만 적었다. 권고는 근거와 함께 적었지만 결정은 연구자 몫이다.

### D1. 기준 cFS 판 (A2)

| 선택지 | 레퍼런스 | 영향 |
|---|---|---|
| **(가) `main` = v7.0.1 (현재 빌드)** | README L50 "v7.0.1: OFFICIAL RELEASE" | 공식 release라 논문에서 인용하기 쉽다 |
| (나) `dev` = v7.0.2rc1 (`01e8416c`) | README L91의 branch 없는 clone은 기본 branch `dev`를 받는다 | release candidate이고, 기본 앱에서 MM이 빠진다. 다시 빌드해야 한다 |

권고: (가). 공식 release이고, R2(cFE #2663)가 현재 코드에 남아 있는지는 사례 조사에서 두 판 모두 확인한다.

### D2. 메시지 queue 깊이 (E5)

| 선택지 | 레퍼런스 | 영향 |
|---|---|---|
| (가) README 모드: `msg_max`=10, 깊은 queue는 잘림 (현재) | README L102 ("best effort message queue") | 메시지 손실이 실행마다 다르게 난다. 순서·손실을 측정하는 연구에서 잡음이 된다 |
| (나) bundle CI 모드: `msg_max`=64 | `actions/start-cfs-container/action.yml` L29–34 | 잘리는 queue가 없다. 이 컨테이너에서 sysctl을 바꿀 수 있는지는 아직 시험하지 않았다(host 공유 값) |

권고: (나)를 먼저 시도한다. 실패하면 (가)로 하고, 잘린 queue를 모든 결과에 표시한다.

### D3. 반복 실행의 종료 방법과 reset 정책 (E7, E11)

| 선택지 | 레퍼런스 | 영향 |
|---|---|---|
| **(가) CI의 ES Restart(POWERON) 명령으로 종료** | `build-run-app-reusable.yml` L209–214 | 매 실행이 POWER ON 부팅이다. 종료 시점이 CI_LAB 읽기 주기만큼(최대 500 ms) 늦을 수 있다 |
| (나) SIGINT(콘솔 CTRL+C) | PSP `cfe_psp_exception.c` L182–233 | 부팅 종류가 PO → PR → PR → PO로 돈다. 실행마다 조건이 달라진다 |
| (다) 시작 시 `-R PO` | PSP usage text | 부팅 종류를 고정할 수 있다 |

어느 방법을 쓰든 `/dev/shm/osal:RAM`과 `EEPROM.DAT`는 실행 사이에 남는다. 이를 지우는 레퍼런스는 찾지 못했다.

권고: (가). 이유는 bundle CI가 쓰는 방법이고 매번 같은 부팅 조건을 주기 때문이다.

### D4. 우선순위 스케줄링 (E4, D-4)

| 선택지 | 레퍼런스 | 영향 |
|---|---|---|
| (가) README 일반 사용자 모드. 우선순위 미적용 (현재) | README L102 | priority로 순서가 정해지던 경우(C3 #73이 그런 보고)는 재현 조건이 다르다. 논문에서 "우선순위가 순서를 보장하지 않는 환경"으로 범위를 밝혀야 한다 |
| (나) root에 `CAP_SYS_RESOURCE`나 `RLIMIT_RTPRIO`를 주는 host에서 실행 | OSAL `bsp_start.c` L66–78, `os-impl-queues.c` L59–63 | 이 컨테이너에서는 불가하다. 다른 실행 환경이 필요하다 |

권고: 1차 실험은 (가)로 하고 범위를 명시한다. 우선순위에 기대는 사례는 사례 조사 결과를 보고 (나)가 필요한지 다시 묻겠다.

### D5. 기타 (확인만 필요)

- **C12 단위 시험 실패(IPv6 없음):** 연구 대상과 무관하니 기록만 하고 넘어갈 것을 권고한다.
- **D-3 HS system monitor 실패:** HS가 관련된 사례가 없으면 기록만 하고, HS 관련 결과는 해석에서 뺄 것을 권고한다.
- **C1 throttle semaphore 조건(D7):** 기본 구성에서는 C1 경로가 실행되지 않는다. semaphore 이름과 제공 앱(원 보고의 BP)은 사례 조사 결과로만 정한다. 원 BP 코드는 공개되지 않았다. 그래서 C1은 공개 CF 코드 위에 역할 기반 제공 앱을 둔 파생 실험이 될 가능성이 크다. 사례 조사가 끝나면 2차 현황에서 결정을 요청하겠다.

## 4. 운영상 조치 (결정 불필요)

- 여러 작업이 같은 계정으로 OSAL 프로세스를 실행하면 `/dev/shm/osal:*`가 겹친다(E13). 그래서 cFS 실행은 한 번에 하나씩만 한다. `run_cfs.sh`는 다른 OSAL 활동이 보이면 실행을 거부한다.
