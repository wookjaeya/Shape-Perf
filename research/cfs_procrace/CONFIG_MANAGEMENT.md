# 형상관리·공개 범위 규칙 (2026-10-28)

- 결정: `Architecture/spec/PI_DECISIONS_RESOLVED_20261028.md` Q1·Q2 [D]. 여기서 공개는 **논문 등 외부 발표물에 싣는 것**을 말한다. 구현 코드와 원시 자료는 논문에 공개하지 않고, 논문에는 아키텍처와 알고리즘을 싣는다. 향후 공개를 고려해 형상관리한다. 저장소 호스팅 설정과는 별개다(2026-10-29 PI 확인).
- 함께 지키는 규칙: `CONDITIONS_POLICY.md`(조건은 레퍼런스 기반, 없으면 `unspecified_by_reference`·deviation).
- 기존 예: `plan/artifact_manifest_20261026.md`(기록 다섯 개의 경로·해시·판 연결). 이 문서는 그 형식을 모든 결과에 적용하는 규칙이다.

## 1. 실행 하나에 연결하는 것

결과표의 행 하나는 아래를 실행 식별자로 되짚을 수 있어야 한다. 값은 경로와 sha256으로 적는다.

| 묶음 | 항목 |
|---|---|
| 대상 | cFS 번들·cFE·OSAL·PSP·앱 커밋, 빌드 명령과 빌드 이탈(예: C1 `-Wno-error=restrict`), 실행 파일 sha256 |
| 계측 | 컴파일러와 plugin 판, site manifest(`kzs-sites`)와 binding 표, 런타임 판, 런타임 모드(`KZ_RT_MODE`), 보류 계획(`.kzh`, `kz_rt` 계획) |
| F0 관측 | 관측 계획(`.kzp`), basis(B), 보류 계획과 보류 기록(`hold.kzr`) |
| 분석 | 분석기 커밋과 도구 바이너리 sha256, Φ 프로필 디렉터리와 프로필 해시, 정적 닫힘(B/B′, `facts`), 읽기 옵션(`--outcome-narrowing`, `--reads-from-outcome`, `--control-order` 등) 전체, `--const` 값과 그 출처 |
| 출력 | 원 기록(`.kzt`, dump), 재생 컨테이너(`--out`), 전체 판정 텍스트 |
| 환경 | 커널(실행마다), 실행 사용자, 명령행, 시작 상태 기록(`persist_snapshot.sh`, R2는 `start_state_poweron.sh`), 정지 방법, 실행 라벨(natural pilot / build-smoke / controlled …) |

전체 판정 텍스트와 원 기록은 지운 적 없이 보존한다. 재생 컨테이너의 요약만 남기지 않는다(AD §4.3).

## 2. 바뀐 것의 구분

- 소스 변경, 계측 설정 변경, 분석 규칙(프로필·분석기) 변경, 실행 조건 변경을 서로 다른 이력으로 적는다. 커밋 메시지와 결과 문서의 "판" 칸에 어느 종류인지 쓴다.
- 한 결과표에 서로 다른 판의 분석이 섞이면 행마다 적용 판(분석기 커밋·프로필 해시·읽기 옵션)을 표시한다. 하나의 최신 성과처럼 합쳐 쓰지 않는다.
- 새 사례를 적용할 때는 프로필·관측점 변경과 엔진 변경을 따로 기록한다.

## 3. 논문에 싣지 않는 자료와 공개용 문서

| 구분 | 내용 | 현재 |
|---|---|---|
| 작업 자료(논문 비공개) | 이 저장소의 코드·스크립트·프로필·결과 문서, 원 기록·빌드, 내부 경로, 사용자별 환경 정보 | 논문에 싣지 않고 보존한다 |
| 공개용 문서(논문 등) | 아키텍처와 알고리즘 설명. 구현 코드·원시 자료·내부 경로·사용자별 환경 정보를 넣지 않는다 | 논문을 쓸 때 별도로 작성한다. 지금은 없다 |

- 공개용 문서는 비공개 자료를 고쳐 쓰지 않고 따로 쓴다. 공개용 문서의 주장마다 비공개 근거(결과 문서·커밋)를 내부 기록에 연결해 둔다.
- 자료를 비공개로 보존한다는 사실과 외부 재현 검증을 마쳤다는 주장은 다르다. 제3자 재생 검증은 아직 없다.

## 4. 유래와 라이선스 표기

- 외부 소스(cFS·cFE·OSAL·PSP·CF·BP, 비교 도구, LLVM 등)의 유래와 기존 저작권·라이선스 표기를 그대로 보존한다. 복사·파생한 파일에는 출처 커밋을 적는다.
- Kairos 코드(`kzgcc` 포함)의 배포 라이선스는 코드 공개를 추진할 때 고른다. 이번 결정에서 새 라이선스를 지정하지 않는다.
- 민감 정보: 환경 변수 값은 기록하지 않는다(`<value not recorded>`). 자격 정보가 들어 있는 파일은 열거나 복사하거나 저장소에 넣지 않는다.

## 5. 원 기록의 보존 위치와 확인 (2026-10-29)

- 결정: `Architecture/spec/PI_DECISIONS_RESOLVED_20261029.md` A2. 2026-10-29에 세션 컨테이너가 바뀌면서 저장소 밖의 원 기록과 빌드가 모두 없어졌다(`REVIEW_ANALYSIS_20261029.md` §0). 그래서 원 기록은 컨테이너 밖에 둔다.
- 위치: 이 저장소 지정 브랜치의 `research/cfs_procrace/records/<묶음 id>/`.
  - 묶음 하나는 다음 파일로 이루어진다: `MANIFEST.sha256`(묶음 안 파일마다), `bundle.tar.xz.NN`(45 MB 조각), `PARTS.sha256`, `INFO.txt`.
  - 도구: `env/tools/preserve_bundle.sh`, `env/tools/verify_bundle.sh`.
- 묶음에 넣는 것 (IP §5):
  - 원 기록
  - 실제로 실행한 바이너리와 동적 모듈
  - B/B′와 정적 사실
  - 계측 manifest·binding, 관측·보류 계획과 실제 제어 기록
  - 재생 컨테이너와 전체 판정 텍스트
  - 정상·실패·정체·거부된 실행의 기록
  - 환경 기록: 커널·컴파일러·런타임·회수 도구 판, 시작 상태, 시작·종료 조건
- 묶음에 넣지 않는 것: 큰 중간 빌드 산출물(목적 파일 트리, LLVM 빌드). 대신 다시 빌드할 명령, 입력 커밋·해시, 도구 바이너리의 sha256을 넣는다. 실행 파일·모듈과 B/B′는 소스 해시로 대신하지 않는다.
- 보존 완료의 조건: `verify_bundle.sh`로 원격 브랜치를 새로 clone한다. 그다음 조각 해시, 압축 무결성, 묶음 안 파일 해시를 확인한다. 분석 입력을 열어 재생할 수 있는지도 확인한다. 이 조건을 마치기 전에는 결과 문서에 "보존됨"이라고 쓰지 않는다.
- 새 실행은 새 실행 식별자를 쓴다. 과거 실행의 이름과 수를 맞춰 복원한 것처럼 표시하지 않는다.
- 결과 문서는 실행마다 그 묶음 id를 적는다.
