## 0. 요약

1. **기존 도구의 실제 적용 결과는 오늘 0건이다.** 여덟 도구 × 다섯 사례 40칸에 실행 기록이 없다(MX §0.2 항목 1, §3.2; `baselines/availability.md` "Status at a glance"). MX 이후 저장소에 도구 실행 기록은 더해지지 않았다(`STATUS_20261027.md` §1 H4 행 "비교 미착수"). [M] 도구별 파일 여덟 개의 sha256은 MX §8.1이 읽은 판과 같다.
2. **40칸은 조사 장부다.** 수행해야 연구가 성립하는 40개 실험도, 기존 도구의 40개 실패도 아니다(CR §11.1). 칸을 채우는 것을 목표로 두지 않는다.
3. **구조(PD29 D6, CR §11.8).**
   - H4-개념(§2): 입력·자원·사건·후보·판정·제어를 출처별로 대응시킨다. 유지하는 작업이다.
   - H4-적용성(§3): 도구 × 사례마다 공통 질문과 자료·실행·모델의 차단 요인을 적는다. 유지하는 작업이다.
   - H4-실행(§4): 앞의 둘에서 성립한 비교만 실행한다. 조건부 작업이다.
4. **기록 축(§1).** 접근·실행, 대상 도달, 사건 표현, 결과, 의미, 적용 형태, 설명을 따로 적는다. 다섯 범주(2026-10-28판)는 쓰지 않는다. 목표 경로 미도달과 유보·재생 이탈은 "탐지하지 못함"이 아니다.
5. **오늘의 접근·실행.**
   - RacePro는 이 컨테이너에서 미실행(E)이다. 별도 머신 경로는 미시도이고, N1으로 보류했다(PD29 D6).
   - 나머지 일곱은 미실행(M: 접근 가능한 출처에서 구현 미도달)이고, 저자 요청 경로는 미시도다.
   - C2는 모든 방법에 사례 쪽 입력 사유(I)가 더해진다.
   - 사건 표현의 "모델 밖"을 지원 범위의 배제로 쓸 수 있는 원문 배제 문장은 0칸이다. 후보 문장(DESCRY p.1 등)의 판단은 PI 몫이다(MX §3.3, §5.4 항목 1·14).
6. **Kairos도 같은 축으로 적는다(§1.4, §3.9).**
   - R2·C1은 실행 기록이 있다(pilot·build-smoke·제어) [기록]. 원 기록은 2026-10-29에 없어졌다.
   - C5는 사례 경로가 아직 실행되지 않았다(사례 쪽 C).
   - F0 관측기와 정적 분석(B′)은 지금 64비트 little-endian ELF만 받는다(`kairos/probe/anchor/elf_image.cpp` L57–58, `kairos/lib/llvm/elf_info.cpp` L36) [F].
   - C2·C3은 미시도다.
7. **능력 분해(§2.2–§2.3).** 예측·탐색과 실행 확인은 여러 기존 도구에 이미 있다(MX §4.3, §4.4 행 5). Kairos와의 차이 후보는 넷이다: cFS 내부 상태·값 전달의 관측, 이름·ID·AppId의 정체성 결합, 허용 오류·회복과 최종 결과의 분리, 순서 근거 종류의 보고. 모두 가설이다. 확인된 부족은 0건이다(MX §4.1).
8. **고정된 실행 순서는 없다.**
   - 2026-10-28판의 "다음 실행 후보는 RacePro, 자체 시험 다음 C5"는 철회했다(PD29 D6, IP §3.2).
   - H4-실행의 대상은 §4.1의 성립 조건으로 정한다.
   - RacePro가 공개 코드가 있는 유일한 도구라는 사실과 6.4.x readme의 i386 빌드 host 사실은 적용성 자료로 남긴다(§3.0a, §3.1, §4.2). 이 사실들이 실행 순서를 정하지 않는다.
9. **해석의 한계.** 외부 실행이 없으면 외부 도구 대비 우위는 미확인이다. 그렇다고 Kairos 판정 타당성 평가가 실패한 것은 아니다. 반대로 내부 대조가 성공해도 외부 우위가 입증되지는 않는다(CR §11.8, IP §4 D6 [분석]).
10. **공정 비교의 조건(§4.3)과 쓰지 않을 주장(§4.4)을 적었다.** 판정 단위는 순서위반이다. 최종 실패·피해는 따로 적는다(PD28 §2 항목 6, §3).

## 1. 기록 축

### 1.1 축의 정의

CR §11.6의 축을 PD29 D6(N3)이 채택했다. 축마다 값을 따로 적고, 한 칸에 합치지 않는다. 같은 규칙을 Kairos 칸에도 쓴다(§1.4).

| 축 | 값 | 칸에 반드시 적을 근거 | 집계 |
|---|---|---|---|
| 접근·실행 | 미시도 / 구현 미확보(**M**: 구현·전문) / 입력 미확보(**I**: 방법이 요구하는 사례 입력이 없음) / 빌드·환경 차단(**E**) / 입력 형식 미지원(현재 구현) / 실행됨 | 미시도: 대기 중인 결정의 번호, 또는 시도하지 않은 이유(공통 질문 미성립 포함). M·I·E: 구체적 차단 요인, 측정·검색 기록과 그 날짜, 근거 등급. "찾지 못함"은 "없음"의 확인이 아니다(MX §1.2). 실행됨: 실행 라벨, 판, 입력 구성, deviation 목록 | 실행됨이 아닌 칸은 나머지 축을 "해당 없음(실행 없음)"으로 두고 미탐지 수에 넣지 않는다 |
| 대상 도달 | 목표 경로 도달 / 미도달 / 불명. 사례 쪽 **C**: 사례 경로가 그 환경에서 실행되지 않음 | 목표 경로(사용 지점과 그 발생)에 이른 기록 | 미도달·불명은 미탐지가 아니다. 그 칸으로 탐지 능력을 판정하지 않는다(MX §3.1) |
| 사건 표현 | 직접 대응 / 부분 대응 / 모델 밖 / 미확인 | 사례의 의존 사건·자원이 방법의 후보 모델에 드는지. 문헌·코드 분석에서 나온 값에는 "(분석)"을 붙이고 실행에서 확인한 값과 나눈다(PD29 D6 N3). "모델 밖"을 지원 범위의 배제로 쓰려면 원출처의 배제 문장과 쪽·절이 있어야 한다. "서술이 없다", "less effective", "초점 밖" 같은 문장은 배제 문장이 아니다. 그런 칸은 후보로만 적고 PI 판단을 기다린다(MX §3.3, §5.4 항목 1·14) | 분석 값은 결과가 아니다 |
| 결과 | 목표에 대응하는 경보·재현 / 경보 없음 / 유보·재생 이탈 | 실행됨이고 도달한 칸만 적는다. 경보 없음이면 원인 하나를 적는다: 관측 부족, 분석 부족, 목표와 다른 경보(§1.3 대응 실패). 유보·재생 이탈의 예는 RacePro의 Diverged, Kairos의 `INCONCLUSIVE`다 | 유보·재생 이탈은 미탐지가 아니다. 경보 없음은 원인별로 센다 |
| 의미 | 관측 위반 / 예측 후보 / 실제 제어로 확인 / 최종 실패(별도 열) | 경보가 무엇을 보였는가. 제어 실행이면 실행 라벨 | 예측 후보를 확인된 위반으로 세지 않는다. 최종 실패만 재현한 출력은 순서위반 결과로 세지 않는다(§1.3) |
| 적용 형태 | 원 구현 / 지원된 사용자 설정 / 관측 확장 / 모델 확장 / 재구현 / 평가 절차 | 받은 정보와 바꾼 구현. 분류 원칙은 §6 N2(PD29 D6) | 확장·재구현의 결과를 원 도구의 결과로 쓰지 않는다 |
| 설명 | 도구가 직접 출력한 것 / 평가자가 따로 확립한 것 | task–앱, 자원, 순서 근거 각각 | 설명의 상세함은 따로 평가한다. 탐지 결과와 합치지 않는다(CR §11.6) |

**표 쓰는 법.**
- §3.1–§3.9의 마지막 열 "접근·실행(오늘)"이 접근·실행 축의 값이다. "미실행(M, E)"처럼 적으면 괄호 안 사유로 실행되지 않았다는 뜻이다. C는 사례 쪽 사유다(§3.0).
- 미실행 칸에서 대상 도달·결과·의미·설명은 "해당 없음(실행 없음)"이다.
- 사건 표현은 같은 행의 "자원·동기화"·"필요 사건" 열에 있고, 모두 문헌·코드 분석 값이다. 실행에서 확인한 사건 표현은 아직 한 칸도 없다.
- 적용 형태의 후보는 "필요한 확장·추가 입력" 열에 있다. 실행 전 분석이다. 2026-10-28판의 `EXTENSION` 표기는 §1.2의 대응으로 읽는다.

| (라벨 없음) | 지원된 사용자 설정(원 도구가 지원하는 인터페이스 안의 실패 검사), 평가 절차(평가자가 결과와 원 사례를 사후 대응) |
| `ANALYSIS`(문헌) | 실행이 아니다. 사건 표현 축의 "(분석)" 값으로만 적는다 |

- **실행 전 분석은 결과가 아니다.** 문헌·코드 분석에서 나온 D4 상태(관측 범위 밖, 표현 불충분)는 사건 표현 축에 "모델 밖(분석)"처럼 적는다. GAP 이름을 쓰지 않는다. SPEC §8.3은 이 두 상태를 질문에 따라 `INAPPLICABLE` 또는 `OBSERVATION_GAP`·`ANALYSIS_GAP`에 대응시킨다. MX §3.1·§4.1은 GAP 두 상태와 "확인된 부족"을 실행 뒤로 한정한다. 이 문서는 강도가 낮은 쪽(MX)을 따랐다. 두 문서는 고치지 않았다(§6 N3).
- **실행 라벨의 승격 금지.** `DEVIATION-RUN`, 확장, 재구현에서 나온 경보 없음(관측 부족·분석 부족)은 "deviation 조건 한정", "확장 한정", "재구현 한정"으로 따로 적는다. 원 도구의 부족으로 올리지 않는다(MX §5.3 S2·S4·S6). 재구현 결과가 생겨도 원 도구 칸의 값을 바꾸지 않는다.

### 1.3 결과의 대응 확인

PD28 Q4가 정한 네 항목을 쓴다. 평가자가 출력과 사례의 순서위반을 네 항목에서 대응시킨다.
- 도구가 네 항목을 모두 출력할 필요는 없다. 평가자가 독립 검토로 대응시킬 수 있으면 그 질문의 결과로 인정한다.
- 무엇을 도구가 냈고 무엇을 평가자가 확립했는지는 설명 축에 따로 적는다(CR §11.6 [권고], PD29 D6 N3).
- 사례 쪽 기준은 아래 표의 장부 항목과, 프로필과 독립인 사례별 기대 판정 근거표(PD29 §4 단계 2, IP §6.1, 아직 없음)다. Kairos 출력이나 프로필의 선언을 다시 읽어 기준으로 삼지 않는다.

| 항목 | 내용 | 사례 쪽 기준 |
|---|---|---|
| 위반 대상 | 사용 지점(호출)과 그 발생 | `cases/ledger.md` §1a "User task / site". C5는 `plan/c5_execution_basis_20261028.md` §4 |
| 관련 task | 사용 task와 provider·생성자 task | ledger §1a "Publisher task / site" |
| 공유자원 | 자원 키와 세대 | ledger §1a "Resource" |
| 판정 근거 | 순서를 세운 근거(무엇이 무엇보다 먼저였음을 무엇이 보였는가) | ledger §1a "Required order + provenance" |

- 출력이 다른 자원이나 다른 순서를 가리키면 결과는 "경보 없음(목표와 다른 경보)"이다. 예: RacePro가 go-live 뒤 무관한 후보 이름으로 실패를 보고하는 경우(RacePro p.363, MX §2.4.1 C1 Q5). R2 ③의 fd table 쌍(MX §6.2)도 AppId 의존과 다른 자원이다.
- 방법 자신의 실패 기준(checker, oracle, failure point, 재현 판정)이 순서위반 기준과 다르면 두 결과를 함께 적는다(SPEC §8.3 "Unrun tools").
- **최종 실패·피해는 별도 열이다.** CF 종료, `ILLEGAL_APP_ID` 거부, `CFE_ES_ERR_APPID`, crash가 그 예다. 최종 실패만 재현한 출력은 순서위반 탐지로 세지 않는다. 최종 실패 없이 순서위반만 있는 경우(R2: 프로세스 실패 없음)도 순서위반으로 판정할 수 있다(PD28 §2 항목 6, §3 연구 범위).

### 1.4 Kairos의 대칭 보고

- Kairos 칸에도 같은 축과 같은 근거 요구를 쓴다.
- 사례 쪽 차단(§3.0)은 모든 방법에 같은 사유로 적는다. 방법의 결함으로 쓰지 않는다(MX §3.2 "사례별 추가 사유").
- Kairos 구현이 받지 않는 입력은 접근·실행 축에 "입력 형식 미지원(현재 구현)"으로 적는다. 근거는 코드·문서 위치다.
  - F0 관측기는 little-endian ELF64 x86-64만 받는다(`kairos/probe/anchor/elf_image.cpp` L57–58) [F].
  - 정적 분석(B′ 생성)도 64비트 little-endian ELF만 받는다(`kairos/lib/llvm/elf_info.cpp` L36) [F]. 2026-10-28판은 이것을 빠뜨렸다(RA §1).
  - 이것은 현재 구현의 범위다. PD29 D3에 따라 정적 분석기·B′의 ELF32 지원(E-ST)은 진행하고, F0의 32비트 관측·보류는 C5 첫 검증에서 보류한다(c5_execution_basis §0 항목 8, §10).
- Kairos의 `INCONCLUSIVE`는 결과 축의 "유보"다. 미탐지가 아니고 안전의 근거도 아니다(`Architecture/07_evaluation.md` §0 "경보 없음은 안전이 아니다", SPEC §6.4 항목 2).
- Kairos의 관측 부족도 같은 이름으로 적는다. 예: F0 R2 pilot3에서 `CFE_SB_Global.AppId` 위치는 `open{effect_unsupported}`였다(`CFE_ES_GetAppID` 저장 미관측). 판정은 그 위치를 읽지 않고 인자 직접 포획으로 섰다(`plan/results_pilot_20261025.md` §1 R2-1). 계측 경로는 그 값을 직접 포획한다(`plan/results_instr_pilot_20261026.md` §8).
- 내부 대조(F0 대 G-I, F0 대 G-I-H)와 Kairos ablation은 외부 방법과의 비교가 아니다(PD28 §3; MX §5.3 S5). G-I-H 36회는 실행 경로 대조이며 H3에 넣지 않는다(PD28 §2 항목 5).
- Kairos 결과도 실행 라벨(natural pilot, build-smoke, controlled …)과 함께 적고, 라벨이 다른 수를 더하지 않는다(`plan/results_pilot_20261025.md` 머리말). 지금까지의 Kairos 실행은 모두 pilot·build-smoke·제어 실행이며 본 실험 결과가 아니다(`STATUS_20261027.md` 머리말). 그 원 기록은 2026-10-29에 없어졌으므로 Kairos 칸의 실행 결과는 [기록]이다(RA §0.1). 새 기록으로 다시 확인하면 새 실행 식별자로 적는다(`CONFIG_MANAGEMENT.md` §5).
- Kairos 칸의 결과는 아직 프로필과 독립인 기대 판정 근거표로 대조하지 않았다(PD29 §4 단계 2). 그래서 설명 축의 "평가자가 확립한 것"은 비어 있다.
- **실행 단위의 정의 차이를 먼저 밝힌다.** 이 연구의 Process-Level은 cFS 애플리케이션·task 단위의 운용 정의다(로드맵 §1.2). native cFS는 한 Linux 프로세스이고 OSAL task는 pthread다. 기존 도구 대부분의 단위는 OS 프로세스다(MX §0.3). 이 차이는 비교의 적용 조건이다(CR §11.3). 여기서 생기는 결과를 도구의 결함처럼 쓰지 않는다.

## 2. H4-개념: 입력·자원·사건·후보·판정·제어의 출처별 대응

H4-개념은 무엇을 이어받았고 무엇이 다른지를 출처별로 대응시키는 일이다. 실행 결과가 아니다. 도구 칸은 모두 문헌·코드 분석이다.

### 2.1 도구 수준 모델: 지원 자원, 순서·동기화(후보), 입력 사건, 사용자 입력, 출력·판정

칸은 MX §2.2와 도구별 파일 §2.1의 압축이다. 쪽 번호의 기준 판은 MX §1.1에 있다. STVR(SimRacer·SIMEXPLORER·SimEvo가 기대는 서술)과 RRF의 쪽 번호는 단일 취득 경로이며 독립 재확인이 없다(MX §1.1 "취득 경로").

| 도구 (본문 등급) | 지원 공유자원 | 순서·동기화 모델 | 관측·모델하는 사건 | 사용자 입력 | 출력·판정 기준 |
|---|---|---|---|---|---|
| RacePro (전문 + 코드 직접 읽음) | 커널 객체. 논문 Table 2(p.357): inode, file, file-table, mmap, cred, global, pid, ppid. 코드: INODE, FILE, FILES_STRUCT, PID, FUTEX, IPC(System V), MMAP, PPID, SUNADDR. - **같은 process-level 연구라도 같은 실험 질문은 아니다**(CR §11.2, 검토자 분석). RacePro는 기록된 실행의 커널 자원 접근 순서를 바꿔 새 잘못된 동작을 찾는다. DESCRY는 실패 실행의 로그에서 입력·스케줄을 구해 실패를 재현한다. SysPro는 보고서와 소스에서 시스템 호출 위치를 찾아 재현을 유도한다. 이 질문들은 "실행된 순서위반의 관측 판정"과 다르다. 질문이 다른 결과를 한 탐지율 표에 합치지 않는다(§4.1).
- **RacePro는 세 능력을 따로 본다**(CR §11.3, 검토자 분석): 공유 메모리의 재생 지원, 내부 의존성의 후보 생성, 실제 잘못된 동작의 확인. 위 표의 RacePro 행은 공유 메모리를 기록하되 HB·후보에 쓰지 않는다고 적는다(p.358, K5). 후보 모델에 직접 들어오지 않는다는 것이, 다른 제어가 관련 실패를 우연히 드러낼 가능성까지 없다는 증명은 아니다.

### 2.2 네 층: 관측, 모델링(후보), 판정, 제어·재현

기존 도구 칸은 MX §2.2·§4.3의 압축이며 모두 미실행 분석이다. Kairos 칸의 꼬리표: **[기록]** 기록된 실행으로 보임(인용). 2026-10-29부터는 그 원 기록이 없어졌다는 뜻도 함께 가진다(RA §0.1). **[구현]** 구현·설계만 있고 사례 실행 기록 없음. **[단위]** 단위 시험만.

| 방법 | 관측 | 모델링 | 판정 | 제어·재현 |
|---|---|---|---|---|
| RacePro | syscall, signal, 커널 객체 접근 순서, 공유 메모리 page ownership(재생용)(§4 pp.356–357) | 커널 객체 micro-op, HB 4종 + 프로그램 순서, 벡터 시계, 경로별 위치(§5) | 후보(논문: load-store·wait-wakeups·wakeup-waits, 코드: RESOURCE·EXIT-WAIT·SIGNAL). checker가 녹화 때 없던 실패를 볼 때 Harmful로 보고(p.363) | 앵커 syscall 순서를 바꾼 branch → replay → go-live. 결정적 재생(§6) |

### 3.0a 도구 수준 실행 요구와 오늘의 차단 요인, 범위 밖 후보

## 4. H4-실행 (조건부) [제안]

H4-실행은 §2·§3에서 비교가 성립한 경우에만 한다(PD29 D6) [D]. 고정된 실행 순서는 없다. 외부 환경 복원이 핵심 검증(PD29 §4 단계 2–5)을 막는 관문이 되지 않게 한다(CR §13.5).

### 4.1 실행 비교의 성립 조건

아래는 CR §11.5의 평가 설계 권고다. 문헌의 공식 분류를 인용한 것이 아니다.

| 확인 항목 | 확인 방법 | 성립하지 않을 때 |
|---|---|---|
| 공통 질문 | 순서위반 판정, 실패 재현, 회귀 시험 가운데 무엇을 비교하는지 명시(§3.0 "공통 질문" 열) | 다른 질문을 한 탐지율 표에 합치지 않는다 |
| 실행 가능한 구현 | 확보한 판·의존성·허용 환경과 자체 예제 동작을 기록 | 확보·빌드·부팅·실행의 차단 단계를 보고한다. 미탐지로 세지 않는다 |
| 입력의 의미 | 원 방법이 요구하는 로그·보고서·소스·사용자 조건을 확보 | Kairos 입력을 외부 도구에도 당연히 주는 정보로 가정하지 않는다 |
| 사건·자원의 대응 | 원 후보 모델에 드는 사건과 빠지는 사건을 소스에 연결(§3 분석 열) | 적용 범위 분석으로 보고한다. 모델 확장 결과는 원 구현 결과와 나눈다 |
| 실험 조건의 정합성 | 목표 경로·판·초기 상태·입력·종료 조건을 맞추거나 차이의 영향을 설명 | 다른 환경·작업 구간의 시간을 성능 순위로 쓰지 않는다 |
| 결과 판정의 정합성 | 경보·실패가 목표 결함에 대응하는지 독립 확인(§1.3) | 무관한 crash·미도달·유보를 같은 실패나 미탐지로 합치지 않는다 |

입력 차이는 두 방식으로 다룬다(CR §11.5).
- 실제 적용성 평가: 각 도구가 본래 요구하는 입력을 주고, 사람이 준비한 정보·수정·작업량을 적는다.
- 분석 기능의 대조: 같은 실제 기록에서 근거 종류만 바꾸는 등 정보 차이를 통제한다. 이것은 원 도구 전체 성능의 비교가 아니다.
- Kairos에 정답에 가까운 수동 프로필을 주고 다른 도구에는 제한된 자료만 준 결과로 자동 탐지 성능의 우위를 말하지 않는다.

### 4.3 공정 비교의 조건

1. **같은 사례 판과 입력.** 사례의 소스 판(ledger §1b, `plan/case_basis_register.md`), 빌드 명령, 시작 상태(R2는 PD28 Q3의 Power-On 공통 절차), 시작 스크립트·앱 집합을 같게 한다. 다른 것은 행마다 deviation으로 적는다(CONDITIONS_POLICY).
2. **같은 환경을 우선하고, 다르면 차이를 기록한다(PD29 D6 N4).** 같은 환경을 만들기 위한 큰 환경 복원·변환 작업을 비교의 선행 조건으로 강제하지 않는다. 기존 도구가 다른 실행 환경을 요구하면(예: RacePro의 i386 2.6.35-scribe) 두 길이 있다.
   - (a) 같은 기계에서 Kairos도 실행한다. 그 커널에서 uprobe·tracefs와 계측 런타임을 쓸 수 있는지는 이 문서가 확인하지 않았다 [U].
   - (b) 환경 차이와 그 영향을 deviation으로 적고, 같은 사례 판의 순서위반 판정만 대조한다.
   - 어느 쪽이든 빈도·시간·비용의 직접 우열은 비교하지 않는다.
3. **같은 판정 단위.** 단위는 순서위반이다. 네 항목(위반 대상, 관련 task, 공유자원, 판정 근거)으로 대응을 확인한다(§1.3, PD28 Q4). 최종 실패·피해는 별도 열이다(PD28 §2 항목 6). 방법 자신의 실패 기준에 따른 결과를 함께 적는다(SPEC §8.3).
4. **받은 정보를 적는다.** Kairos가 받은 것(Φ 프로필, site, 요구·허용 기록)과 기존 도구가 받은 것(checker·oracle, SR 지정, 자원 이름, 보고서, 소스)을 행마다 적는다. 기존 도구에 cFS 고유 사건·자원을 더 주면 관측 확장 또는 모델 확장이다(§6 N2). Kairos의 사례별 프로필은 수동 입력으로 표시한다(로드맵 §11.5 "수동 입력과 자동 추출을 구분").
5. **같은 실행 라벨끼리.** 자연 실행과 제어 실행을 나눠 적는다. 제어 실행의 결과는 빈도가 아니다. 같은 제어 사실을 주지 않은 대조를 수집·제어 경로의 우월로 읽지 않는다(PD28 §3 "83/86"의 원칙).
6. **동결.** 사례마다 첫 출력 전에 기대표를 동결한다. 비교 전에 분석기·cFS 규칙·관측 계획·판정 기준·checker·재구현을 동결한다(로드맵 §11.3, `Architecture/07_evaluation.md` §0). 이후 고친 것은 변경 이유와 함께 따로 표시한다.
7. **형상 연결.** 행마다 도구 판(커밋), 논문 판(쪽 기준), 입력 구성, deviation 목록(MX §5.3 S8), 실행마다의 커널, 해시, 원 기록 묶음 id를 적는다(`CONFIG_MANAGEMENT.md` §1, §5).
8. **수치.** 사례 수, 순서 구조 수, 계획 수, 실행 수, 호출 수를 따로 적는다(PD28 §3). 도구 사이에 점수·순위·짝지은 검정을 두지 않는다(SPEC §8.3). 탐지율을 낸다면 정의한 평가 모집단과 미지원·미도달·유보의 수를 함께 낸다(CR §11.6). 반복 수·임계값·시간 한도는 비교를 설계할 때 측정 질문마다 정하며 그 전에는 `unspecified_by_reference`다(PD28 Q4). 도구 매개변수(RRF의 `ST`·`r`, DESCRY의 `N`·`L_max`, SysPro의 sleep 길이)의 논문 값은 논문 사례의 값이다. cFS 조건으로 가져오지 않는다(도구별 파일 §4.1). 레퍼런스에 있는 상수나 사건 기반 제어만 쓴다(CONDITIONS_POLICY).
9. **평가 자료.** 실제 cFS 사례와 1차 출처를 쓴다. 작은 합성 입력은 도구 시험으로만 쓰고 사례 수에 넣지 않는다(PD28 §3). RacePro의 자체 예제(§4.2 "RacePro 문서화된 설정 실행" 행)도 사례 결과가 아니다.

### 4.4 쓰지 않을 주장

- "도구 X가 사례 Y를 탐지(재현)하지 못한다." 실행하지 않은 도구에 쓰지 않는다. 미시도, 미실행, 사건 표현 "모델 밖"을 미탐지·false negative로 세지 않는다(D4, ADR-058, `availability.md` §5.4).
- 목표 경로 미도달, 유보, 재생 이탈을 "탐지하지 못함"으로 쓰는 것. Kairos 칸에도 같다.
- 40칸을 채워야 할 실험 수나 기존 도구의 실패 수로 쓰는 것(CR §11.1).
- 탐지율, false negative 수, 성능 비교, 도구 순위. 현재 자료로 외부 도구 0/5, Kairos 2/5 같은 수를 만들지 않는다(CR §11.6).
- "기존 process-level 기법은 순서위반을 다루지 못한다"(`availability.md` §5.4). RacePro는 순서위반을 겨냥해 설계됐다(p.355). RRF의 race 정의는 order violation을 포함한다(p.2).
- "RacePro는 공유 메모리를 기록하지 못한다." 기록하되 HB와 후보에 쓰지 않는다(p.357–358). 반대로 "공유 메모리를 기록하므로 cFS 내부 등록·AppId 의존을 자동으로 분석한다"도 쓰지 않는다. "cFS가 한 Linux 프로세스이므로 무조건 적용 불가"도 쓰지 않는다(CR §11.3).
- "관측된 실행만 다루는 기존 방법에 비해 Kairos는 예측·탐색과 실행 확인을 한다." 근거가 없다(MX §0.2 항목 5, §4.4 행 5).
- 외부 실행이 없다는 것을 Kairos 판정 타당성의 실패로 쓰는 것. 내부 대조의 성공을 외부 우위로 쓰는 것(IP §4 D6 [분석]).
- 확인하지 않은 출력(`REPORTED`)을 사례 탐지로 쓰는 것(§1.3).
- 재구현·확장의 결과를 원 도구의 결과로 쓰는 것. Kairos ablation이나 내부 F0·G-I·G-I-H 대조를 기존 도구 결과로 쓰는 것(MX §5.3 S2·S4·S5, PD28 §3).
- 읽지 않은 도구(SimRacer 본문, ReDPro 전문)의 능력이나 범위를 초록·검색 발췌로 말하는 것(SPEC §6.4 항목 54).
- `availability.md` §5.4 "May use"의 둘째 문장("none of the five case dependencies is an event in that model")을 도구 구분 없이 쓰는 것. SIMEXPLORER에는 쓸 수 없고 SimRacer에는 단정할 수 없다(MX §2.5 항목 8, §5.5).
- C2의 역할 재구성 결과를 원 비공개 시스템의 재현으로 쓰는 것(P-C2). C3의 파생 구성 실행을 원 사례의 재현으로 쓰는 것(PD28 §4).
- 강제 보류로 만든 소진(E-06, `timeout-exercised`)을 새 운영 결함이나 자연 빈도로 쓰는 것(STATUS_20261027 §5).

## 6. 남은 것과 N1–N4의 처리 (PD29 D6)

- MX §5.4의 열린 항목은 그대로다. 이 문서에 직접 걸린 것: 항목 1(같은 프로세스 안 task 쌍의 `INAPPLICABLE`), 3(저자 연락), 4(재구현·확장), 5(RacePro 별도 머신), 6(Simics 설치), 14(C2 입력 미충족의 `INAPPLICABLE`).
- **N1. RacePro userland: 보류**(PD29 D6) [D].
  - 공통 평가 질문, 사건 모델 대응, 구현 가용성을 먼저 확인한다(§4.1). 그 뒤에 구체 환경을 검토한다.
  - 기록으로 남기는 사실: RacePro 쪽 userland는 `unspecified_by_reference`다. 6.4.x readme의 i386 빌드 host가 cFS 쪽 레퍼런스와 함께 맞출 후보다(§4.2) [I].
- **N2. 사용자 실패 검사와 확장의 분류: 원칙 채택**(PD29 D6) [D]. 실제 적용 때 받은 정보와 바꾼 구현을 확인해 다음 가운데 하나로 적는다.
  - 원 도구가 지원하는 인터페이스 안에서 기존 관측 정보로 실패를 검사한다: 지원된 사용자 설정인지 확인해 기록한다.
  - 새 cFS hook이나 원 도구가 주지 않는 수집 기능을 더한다: 관측 확장.
  - 내부 상태를 새 공유 자원·후보 생성 규칙에 넣는다: 모델 확장.
  - 논문을 바탕으로 새 구현을 쓴다: 재구현.
  - 평가자가 결과와 원 사례를 사후 대응시킨다: 평가 절차.
  - 내부 값을 읽는다는 사실만으로 분류하지 않는다. 정보의 출처와 추가 작업을 확인한다.
  - RacePro checker의 경우: checker가 cFS 내부 반환값이나 상태를 보게 하는 것이 논문이 허용한 사용자 checker(p.363)의 범위인지, cFS 쪽 관측을 더한 관측 확장인지는 적용할 때 이 원칙으로 정한다. R2는 출력이 없어 이 분류가 결과의 적용 형태를 정한다.
- **N3. 문서 상태 용어 충돌: 이 구조로 해소**(PD29 D6).
  - 이 문서 안에서는 §1의 기록 축이 문헌·코드 분석(사건 표현 "(분석)")과 실행 관측을 나눈다. 미시도·미실행·미도달·유보를 미탐지에서 뗀다.
  - SPEC §8.3 "Unrun tools"가 D4의 문헌·코드 상태를 질문에 따라 `OBSERVATION_GAP`·`ANALYSIS_GAP`에도 대응시키는 문구와, MX §3.1·§4.1이 두 GAP 상태를 실행 뒤로 한정하는 문구는 고치지 않았다. 두 문서는 이 문서 담당이 아니다. 이 문서는 MX 쪽(강도가 낮은 쪽)을 따른다(§1.2).
- **N4. 환경이 다른 경우의 비교**(PD29 D6) [D]. 같은 환경을 우선한다. 큰 환경 복원·변환 작업을 강제하지 않는다. 환경이 다르면 차이와 영향을 기록한다. 빈도·시간·비용의 직접 우열은 비교하지 않는다(§4.3 항목 2).
- 사례 이슈 댓글(MX §5.2 "공통" 행): DESCRY의 실패 로그 입력과 SysPro의 보고서 입력 판단이 이 경로에 걸려 있다. 2026-10-29에 #2663과 #73의 댓글을 공개 이슈 페이지로 읽었다(`cases/R2.md` §1.5, `cases/C3.md` §1.2.3). 이 문서의 칸은 그 때문에 바꾸지 않았다. 입력 판단은 적용할 때 한다.
- MX §5.5가 적은 다른 문서의 정정(예: `availability.md` §1·§3·§5.4의 낡은 서술)은 아직 반영되지 않았다. 이 문서는 그 문장을 근거로 쓰지 않았다.
