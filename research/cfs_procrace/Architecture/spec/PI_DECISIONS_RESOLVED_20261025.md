## 2. 단계 A–D (RV §11)

- **A.** 판정 근거 종류를 네 가지로 나눠 보고한다: 직접 포획 값 / 관측 상태·동기화·생성 순서·정체성 가정 / 반환값·동일 id에서 유도한 순서를 포함한 상태 재생(RF) / 반환값으로 조건을 직접 좁힘. `via`, A-OWNER(생성 id로 효과 대상 결정), RF는 결과표에 신뢰 가정으로 드러낸다.
- **B.** C1 E-06(수정 후 재시도 소진)을 실제 프로그램에서 관측한다. P-C1HOLD(2026-10-15 §3.3)의 보류를 쓴다: provider의 `OS_CountSemCreate` 진입 직전에서 보류하고, CF의 재시도 종료 또는 최종 초기화 결과 사건에서 해제한다. 하네스가 끝내 반복이 열린 채 종료된 실행은 소진 위반으로 세지 않는다. E-06의 `VIOLATING`은 채택한 요구·허용 모델의 판정이고, PR #342가 재시도 상한을 의도적으로 두었다는 사실과 함께 해석한다.
- **C.** 같은 바이너리·설정에서 다른 관련 순서가 가능한지 확인한다. 자연 실행으로 얻지 못하면 실제 코드의 실행 제어를 쓴다. **이 제어 실행은 P-C1HOLD 밖의 연구자 개입이다**(C1 계획 Q-9가 기본으로 두지 않던 "제어된 정상 경로"에 해당). 별도 표시하고 자연 A2 결과와 섞지 않는다. 값·앱 로직·자원 이름은 바꾸지 않는다. BP-first 설정(#184 2022-08-02 댓글)은 별도 구성으로만 보고한다.
- **D.** 검증한 C1 범위에서 명시적 탐색으로 한정 예측을 하고, 후보를 실제 실행으로 확인한다. RF처럼 관측 실행에 종속된 간선과 다른 실행에서도 유지할 동기화 제약을 구분한다. B·C 결과를 본 뒤 시작한다.
- 선행 조건으로 두지 않는 일: R19로 R2 240건 확정, 손실의 task 귀속, CF 필드 포인터 분석 완성, 원 도구 환경 복원, 선택 증명 경로.

## 3. 상태 문서 문장 교체 (RV §7)

"수정 전 실패는 시작 순서만으로 매번 난다"를 다음으로 바꾼다: 공개 BP 구성은 CF 생성 요청이 BP보다 먼저다. 관측한 수정 전 기동에서는 모두 조회 실패가 나타났다. 이 결과만으로 모든 허용 스케줄에서 실패가 필연적이라고 판단하지 않는다. 같은 구성의 다른 실행 순서가 가능한지는 후속 검증 대상이다.
