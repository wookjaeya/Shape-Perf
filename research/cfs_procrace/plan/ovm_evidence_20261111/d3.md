## 1. Definition

**The property.** [I] Where the framework leaves two actors unordered, the shipped system implies one order requirement without anyone stating it: either order must settle in the same place. A *publication* w (an operation after which another actor's operation is answered differently) and a *use* u violate it when u is answered from the pre-publication state, its actor acts on that answer, and the action still stands after the system has settled although the answer has become false. I call this a **stale decision**. Healing = the same use is repeated and answered from the published state. Loss = it is not. The property is observable in two ways: across two runs that differ only in the order of w and u, or, when only one order can exist, across occurrences of the same use before and after w in one run.

Decidable definitions:
- D1 *Thread instance* τ: one thread-creation call instance joined to the first execution of its child (3.5). app(τ) = the application named by the creation request.
- D2 *Operation*: one call of a function declared in the framework's public headers, recorded as (τ, call site, key, class). key by rule R-KEY, class ∈ {ok, info, fail, no-return} by rule R-CLASS (section 2).
- D3 *Class-divergent operation* of τ between two runs: the first position at which the two operation sequences of τ, aligned by (site, key) with immediate repetitions collapsed, differ in class.
- D4 *Stands*: an operation with class fail stands if no later operation of the same (τ, site, key) in that run has a class other than fail, up to the snapshot R-SNAP.
- D5 *Minimal flip* of (w, u): two runs of the same build and inputs that differ by one gate only. In ρ(u≺w) the thread of w is gated just before w and released as soon as u has returned once. In ρ(w≺u) the thread of u is gated just before u until w has returned. One of the two is normally an ungated reference run.
- D6 **Order violation (V1).** A pair (w, u) with app(τw) ≠ app(τu) is reported iff both runs of D5 are accepted as feasible (section 5) and the class-divergent operation u* of τu is fail or no-return in one run and neither in the other, and it stands. Required order = the order of the run in which u* does not fail. Qualifier *insufficient tolerance*: equal at zero margin, but u* fails and stands when the gate is kept for the horizon H.
- D7 **Premature use under a fixed order (V2).** For a step 2a relation row (shared field L, write w, use sites U): reported iff in every reference run (a) at least one occurrence of U by a thread of another application precedes w and every such occurrence has class fail, (b) the occurrences of U after w are not empty and none returns a status value seen in (a), (c) at least one occurrence of (a) stands, and (d) a gate on the using thread before its first u ends at H without w having executed (the other order cannot be produced).
- D8 Other outputs, never counted as detections: TOLERATED (the first classes differ, nothing stands, at zero margin and at H), ENFORCED (the gate shows that u cannot precede w), BENIGN (no class-divergent operation), ORDER-DEPENDENT-UNDIRECTED (the runs differ in keys, out values or executed sites, but no fail/non-fail split), SILENT-PREMATURE (D7 (d) holds and a use precedes w, but (a) fails), UNDECIDED (exhaustion tag, masked entry, row not exercised, run budget used up).
"Between applications" includes core services (application records of type CORE) and the ES creator thread acting for the application it creates; the report names both actors, so cases inside the framework (C3, C5, R2) are reported as such.

## 3. Candidate discovery

3.1 **No candidate list is needed to detect.** The search moves threads and looks for class-divergent operations. Schedule family, generated from the reference trace:
- S0 reference, no gate, N_ref times.
- S1 children-first: at every return of the outermost API call that contains a thread-create primitive (here `OS_TaskCreate`) the creator is gated until the child reaches init-end, or blocks on a lock the creator owns, or H. One boot covers every spawn.
- S2 T-last(b): for each thread instance T and each phase boundary b of T (thread start; return of a sync call of I8), gate T at b until every other thread has reached init-end, or H.
- S3 T-first: gate at thread start every thread that is not an ancestor of T and that the 2a await facts do not show as awaited by a creator, until T reaches init-end, or H.
init-end(T) := T enters `CFE_ES_RunLoop` or `CFE_ES_ExitApp`, or a wait-forever call, or ends. A schedule is a *witness* if some thread has a class-divergent operation against every reference run, outside R-MASK.
For two threads A and B, A-last and B-last together realize both orders of every pair of init-time operations [I]. S3 adds the conjunction "several publishers late at once" that C3 needs.
3.2 **Localization, still without an object model.** In a witness, u* = the earliest class-divergent operation. w is found by (a) a shortcut: operations of other threads whose order against u* differs between witness and reference and whose key shares a string with the key of u* (C1: the name is a plain string argument on both sides [F C12 §4 obs 4]); otherwise (b) delta debugging over the set of gated threads, then bisection of the release point over the gated thread's operation sequence: w = the operation whose completion before u* removes the divergence. Each step is one boot. (c) The 2a row whose sites lie inside the dynamic extent of u* and w is attached as the field-level explanation.
3.3 **Rows, for what perturbation cannot show.** A fixed order has no second schedule. The 2a rows are instantiated on the reference trace: probes at the row's write and use sites give (thread instance, time, class) per occurrence. Rows with a use by another application's thread before the write feed D7. Rows instantiated in one order only and not flipped by S1-S3 get a targeted minimal flip, gated at the acquisition or call entry the row names. Rows never executed in startup are listed "not exercised".
3.4 **Identity of the shared object.** Detection does not compare object identities: a pair is two operation instances, and the evidence that they are related is the intervention (moving one changes the outcome of the other). This removes the three identity problems of the cards: keys that exist only at run time (C1: consumer key from a table file, publisher key from a literal [F C12 §1.3]); keys computed inside the callee (C5: `OS_TaskGetId()` [F C5 §3]); keys that name the wrong object (R2 and C3: AppID 0 [F C3R2 "Observations" 3]). Within one run a row's read and write are matched by the address actually accessed. Numeric IDs are never compared across runs: they are creation serials and change with order by construction [F FO §f].
3.5 **Actor to application.** Thread instance = the creator's thread-create call instance plus the child's first execution, joined by a token the tracer passes through the creation call. Never by `OS_TaskGetId`, AppId or the event application name: these bound SAMPLE_APP to SAMPLE_LIB in the recorded boots [F C5 §15]. Application = the name argument of the creation request that leads to the spawn (I10); a child task inherits its parent's application; the process initial thread is the actor "boot" [F C5 §15 obs 2, 4].

## 4. The oracle

4.1 **Decision (V1).** For a localized pair, run the minimal flip (D5). Take the consumer thread τu. Its code is sequential, so with the same inputs its operation sequence is the same in both runs up to the first operation that was answered differently; that operation is u* (D3). The verdict is V1 iff u* has class fail or no-return in exactly one of the two runs and stands there (D4, D6). The required order is the order of the other run. Nothing else enters the verdict: no dump comparison, no list of events, no count.
4.2 **Decision (V2).** When the other order cannot be produced (D7 (d)), the two publication states are sampled inside one run: the occurrences of the row's use sites before and after the row's write. V2 iff the split is perfect (all before fail; no status value of the before half recurs after), one failure stands, and the users before w belong to another application than the writer.
4.3 **Why the inference is legitimate.** [I]
1. *The requirement comes from the system, not from a person.* The framework does not order the init code of two script applications [F FS §B O1], documents that "test apps may be executed in a different order than they are listed in the startup script" [F FS §D: README_functionaltest.md:38-40], and offers late start and restart through the same creation path [F FS §E]. An execution in which one thread is merely slower is therefore a legal execution. A system whose settled outcome depends on it has a dependence that nothing enforces.
2. *The direction comes from the framework's own classes.* The method never chooses which status or event matters. It reads four class definitions (I4-I7) that hold for every application of that framework version. They are the vocabulary in which the framework authors and, through return values and event types, the application authors already wrote "this did not work". The tool does not interpret a code; it reads two bits, a sign, an enum.
3. *Attribution is by intervention.* A fail class alone proves nothing: BP's own probe returns -17 on every first boot [F C12 §1.11 N1], routine statuses such as `CFE_SB_TIME_OUT` carry the error class [F FS §C], and the framework expects event floods at initialization [F FS §D: cfe_sb.dox:494-495]. Such operations fail in both runs of a flip, are never class-divergent, and cancel out. Only a failure that appears when w is moved behind u and disappears when it is moved back is attributed to the order.
4. *"Stands" separates healing from loss.* A retry, a poll or a later periodic re-evaluation repeats the same (thread, site, key) and ends in a non-fail class: the decision was revised. A single call followed by an exit, a skipped registration or a discarded status never is.
4.4 **The fixed-order case.** In R2 the other order does not exist, so "the other order is harmful" cannot be shown; what is shown is that the use is answered from the pre-publication state, that this answer is a framework error, that the same use is answered without error once the publication exists, and that nobody repeats the failed use. The evidence is a split inside one run plus the static data flow of the row. It is weaker than a flip and is reported as its own class.
4.5 **When it cannot decide.** The run pair differs but u* has no fail/non-fail split → ORDER-DEPENDENT-UNDIRECTED with both traces. Premature use under a fixed order with a non-fail answer → SILENT-PREMATURE with the row. A bounded wait was exhausted only because of the gate → UNDECIDED (beyond the framework's startup budget). An entry is in R-MASK → UNDECIDED (naturally unstable). The method never turns these into a verdict.

## 5. Enforcement and feasibility

- **Gate points.** Thread start; return of the outermost API call that contains a thread-create primitive; entry of an outermost framework API call, optionally conditioned on call site and string key; entry of a lock acquisition that a 2a row names ("acquired-at"). Never inside an API's own transaction: a publisher stopped between the name store and the finalization of an OSAL create would expose the -35 path [F C12 §1.5, §4 obs 7].
- **A produced order is accepted as feasible** iff (i) the gated thread owned no program lock when it was gated (lockset from the P0 mutex events), (ii) the gate was released by its condition, or at H, (iii) no bounded wait exited by its bound in the gated run unless it also did in a reference run. Bounded waits are the P0 timed waits and the sleep-poll loops that 2a lists with their bounds. Argument [I]: a gate only makes one thread slower; no framework rule bounds the speed of a thread except its timed barriers, and (iii) keeps the run inside them.
- **The order is enforced or fixed** when: (a) lock: while the publisher is gated the consumer blocks on a lock the gated thread owns → released at once → ENFORCED (lock); (b) await: until H the awaited operation does not occur because its thread does not exist yet or waits for the gated thread → ENFORCED (await, up to H), and for D7 "order fixed"; (c) creation: w precedes the creation chain of τu → the pair is never gated.
- **Artifacts of the intervention that are recognized.** Exhaustion tags as in (iii); the runtime's own refusal and timeout records for a gate; class-divergent operations in threads other than τu and its children are not used for a verdict of that pair; numeric ID changes are invisible through R-KEY; reference runs carry the same instrumentation with gates disabled, so a difference is caused by the gate and not by the probes.
- **Not recognized** [I]: a failure in τu itself that the length of a gate causes through a queue or message limit rather than through w; only the zero-margin release and the repetitions limit it.

## 7. False positives and false negatives

False positives:
- *Designed one-shot fallback.* An application that probes an optional peer once and then runs without it gives a fail class that stands and flips with the order. The method reports V1. C1 N3 would be this if its publisher were concurrent. CF's documentation even states the exit as intended behaviour [F C12 §4 obs 10], and #184 was still accepted as a bug. The report is true to the definition; a developer may call it intended.
- *Failures caused by the length of a gate.* Message-limit and pipe-overflow errors arise during initialization [F FS §D: cfe_sb.dox:494-495; C12 §2.11 L1 comment]. If one hits τu during a gate held for H, it can look like "insufficient tolerance". Mitigation: the plain V1 verdict uses the zero-margin release only.
- *The v7 entry poll (C5 N10).* Its budget is the same constant from which H is derived [F C5 §8]; a gate of H leaves one poll period of margin. A late release would exhaust it and be tagged, so it yields UNDECIDED, not V1, but the margin is thin [I].
- *Coarse keys.* If R-KEY drops what distinguishes two instances, "stands" is judged on the wrong instance (next item).
False negatives:
- *Silent wrong values.* C3's sub-order "SB late, EVS registered" returns `CFE_SUCCESS` and misattributes the event to app 0 [F C3R2 C3 §5 yield row 3]; EVS's fixed-order read in 6.4.2 does the same. No class differs: UNDIRECTED or SILENT-PREMATURE at most.
- *Lost SB messages.* A send before the first subscription returns `CFE_SUCCESS` and nothing is retained [F FO §d]. The loss is visible only if the receiver later fails in class.
- *Reused sites.* In R2, 17 of the 20 early failures of the ES task are event 14, sent at one site [F W6:462; C3R2 R2 §5]. If the same thread reaches that site again after SB's store with the same format string, those occurrences do not "stand" by D4 [I; whether it does in the records is U]. R2 is still reported through events 5 and 10, but the count of lost events can be understated.
- *Outside startup.* Lookups in commands, and the stale identifier after a provider restart [F C12 §4 obs 8], are not exercised. Restart and late-start schedules are a natural extension, not part of this design.
- *Conjunctions.* S3 covers "all others late"; a defect that needs two specific threads late and a third early is found only if delta debugging starts from a witness.
- *Unrecorded operations.* A use that is an inline field read with no API call inside it is seen only through a 2a row probe; if 2a has no row, it is missed. [M] No row of REL(c5_641) has `EVS_AppData_t.RegisterFlag` as its field; it occurs only inside the callee check of B64 (:2520).
- *C2*, as stated.

## 8. Cost and construction

- **Boots.** N_ref + 1 (S1) + Σ over threads T of (2 + number of sync-call returns in T's init) + per witness: delta debugging over k gated threads, O(k log k), bisection over m operations, O(log m), and 2 confirmations (zero margin, H) + 1 per fixed-order row group (the D7 (d) gate; several rows whose users are in different threads share a boot) + targeted flips for rows left in one order. With the 12 tasks of the recorded 6.4.x boot [F C5 §2] and N_ref = 2: 27 boots before localization [I]. Each boot lasts startup plus the settle time of R-SNAP plus its gates (each ≤ H). Linear in the number of threads; independent of the number of relation rows except for the targeted flips.
- **Instrumentation.** Entry and exit probes on the functions of I3 with arguments by prototype and the return value; P0 probes; a thread-start trampoline with the creation token; gates at the four kinds of gate point; probes at 2a row sites that are not at an API boundary (field read or write). Whether the present compiler hook can bind a statement-level site from a row coordinate is [U].
- **Exists in Kairos.** Profile-free extraction and the relations query with loop bounds, locksets and await facts [F static_facts.md §5a-§5e]. A runtime with gates, releases, gate timeouts, context classes (a lock-holding thread is gated only with an explicit flag), string and value conditions, and control records [F R/kairos/docs/event_semantics.md §4-§7].
- **Partial.** Site manifests and hold plans are written by hand per case today [F C12 §1.12] and must be generated from I3 and from rows. Runtime limits: 32 control points per plan, one held thread per gate, one gate per actor [F event_semantics.md §6; M R/kairos/runtime/include/kz_rt.h:73]: gating many threads at thread start needs an extension. Thread identity: the old binding rule is void [F C5 §15].
- **New.** The schedule driver; the class map and R-MASK; sequence alignment and the D3 comparator; the delta-debugging and bisection driver; lock wait-for detection; exhaustion tags from 2a loop facts; the in-run split of D7; header parsers for I3-I7 and R-KEY.

## 10. The weakest point

The oracle sees only what crosses the instrumented framework boundary as a *class*. Where both orders can be run, a fail/non-fail split that stands is strong, interventional evidence. Everywhere else the method has no oracle of its own:
- **Fixed order (R2).** The verdict rests on a correlation inside one run, on the static data flow of one 2a row, and wholly on the framework's status classes. If the framework had returned `CFE_SUCCESS` there, as 6.4.2 does for EVS, the method would only list the row. V2 is a weaker claim than V1 and the paper must say so.
- **Silent harm.** A wrong value returned with a success status (C3's misattribution, a lost SB message) produces no verdict, and the reported harm of C3 itself, an out-of-bounds access, is visible only as a fault or with a generic memory checker.
- **"Stands" is judged per (thread, site, key).** It is a proxy for "the decision was revised"; a reused site can hide a loss, a coarse key can invent one.
- **Nothing here was executed.** The verdicts for C3 and C5 are predictions from code reading; the violating order of C5 was never recorded [F C5 §14 U1]. The size of R-MASK on a real boot, and whether the gate family stays inside the timed barriers of each build, are unknown until the first run. H for 6.4.x, N_ref, R-KEY and the run budget have no framework reference and must be pre-registered with the PI.
