## 3. cFS 프레임워크 의미론 인벤토리

이 절은 분석기가 알아야 하는 cFS 프레임워크 동작을 고정 버전의 소스와 이 컨테이너의 실측으로 정리한다. 대상은 Software Bus(SB), OSAL queue·task, Executive Services(ES), Table Services(TBL), Event Services(EVS), Time Services(TIME)다. 각 항목을 세 부분으로 나눈다. 정확한 동작, 프레임워크가 이미 보장하는 순서, 보장하지 않는 순서다. 끝에서 분석기가 반드시 모델링할 사실(§3.8)과 가정해도 되는 사실(§3.9)을 정리한다.

이 절은 공유 메모리 data race를 다루지 않는다. 앱 사이의 메시지 순서, 메시지로 갱신되는 상태, startup·lifecycle 의존성, Table Services만 다룬다.

**[설계 제안]** ES-1, ES-4, ES-5를 합치면 startup sync에서 얻을 수 있는 HB 간선은 조건부다. 아래는 분석기에 넣을 규칙의 초안이다.

```text
# 입력: 각 앱의 main task CFG, startup script 순서
# ready(B) := B의 main task에서 처음 도달하는 다음 호출 중 하나
#             WaitForSystemState(B, S>=OPERATIONAL) 진입, WaitForStartupSync(B) 진입, RunLoop(B) 진입
#             (이 지점에서 B.AppState := RUNNING)
# opW      := ES main의 'SystemState := OPERATIONAL' (cfe_es_start.c L235)
# wait_A   := A의 WaitForSystemState(OPERATIONAL, t)가 CFE_SUCCESS로 돌아온 지점
#             (WaitForStartupSync는 상태를 버리므로 wait_A로 쓸 수 없음)

규칙 R-sync-1 (무조건):  opW  →HB  wait_A.return
규칙 R-sync-2 (가정 필요): 가정 NoStartupTimeout(B)가 있을 때만  ready(B) →HB opW
결과:                     B에서 ready(B) 이전의 사건(예: B의 Subscribe 성공) →HB A에서 wait_A 이후의 사건(예: A의 첫 Transmit)
가정이 없으면:              간선 없음. ES는 1000 ms soft limit 뒤 진행한다(ES-4).
주의:                      ready(B)가 B의 Subscribe보다 먼저 오면 이 간선은 Subscribe를 덮지 않는다(ES-5, ES-7).
```

**[미확인]** `SystemState`는 lock 없이 읽힌다. 다중 코어에서 B의 앞선 쓰기가 A에게 보이는 메모리 순서는 확인하지 않았다.

### 3.7 구성·데이터가 정하는 통신 관계

프레임워크 API만으로는 실행 시 구독 집합이 정해지지 않는다. 기본 번들 앱에서 구독과 발행 MID의 상당 부분이 table·명령·build 설정에서 온다.

(S22)

### 3.8 분석기가 반드시 모델링해야 할 프레임워크 사실

각 항목은 근거(위 표의 ID)와 모델 요소의 초안을 함께 적는다. 모델 요소는 모두 **[설계 제안]**이며 구현되지 않았다.

**M1. 발행은 destination별 put 사건의 열이다.** 근거: SB-3, SB-4, OS-1. 원자적 broadcast로 모델링하면 안 된다. 수신자는 `TransmitMsg` 반환 전에 실행될 수 있다. 아래는 고정 commit의 코드 경로를 요약한 모델이다.

```text
# [설계 제안] cfe 546a0025 기준 TransmitMsg(m, IsOrigination) 의미 모델 (task T에서 호출)
tx.begin(T)
  if bad_arg(m) or too_big(m) or pool_empty: return ERR                 # SB-8
  copy := memcpy(m)                                                      # 호출 시점의 payload
  lock(SB)
    r := route(mid(m))
    if r == ⊥: NoSub++ ; event(14, gated by EVS type mask of T) ; unlock ; return SUCCESS   # SB-5
    if IsOrigination: r.seq++ ; copy.seq := r.seq                        # SB-6: destination 0개여도 증가
    D := [d in r.dests head-first | d.active ∧ ¬(d.ignoremine ∧ d.pipe ∈ pipes(app(T)))][:MaxPipes]
    for d in D: if d.buffcnt >= d.msglim: drop(d, MSGLIM) else d.buffcnt++   # SB-7
  unlock(SB)
  if IsOrigination: copy.time := TIME.now()                              # EVT-6
  for d in D \ dropped (순서 유지):
      put(d.pipe, copy)            # 사건 e_put(d); 이 순간 더 높은 priority 수신 task가 선점 가능
      if queue_full: drop(d, QFULL)                                       # SB-7, OS-1
tx.end(T) ; return SUCCESS
HB 간선: tx.begin →po e_put(d_1) →po … →po e_put(d_k) →po tx.end
         e_put(d) →HB 그 copy를 꺼낸 get(d.pipe)
         tx.end 와 수신 handler 사이: 간선 없음
```

**M2. 발행 성공은 전달 성공이 아니다.** 근거: SB-5, SB-6, SB-7, SB-8. route 없음, destination 0개, MsgLim 초과, queue full이 모두 `CFE_SUCCESS`다. ‘필수 consumer’ 같은 요구는 분석기가 별도 계약으로 받아야 한다.

**M3. SB에는 durability·latching이 없다.** 근거: SB-2, SB-6, SB-12. 구독 완료 전의 발행과 재시작 창의 발행은 사라진다. 첫 메시지 유실을 판단하려면 구독 완료와 첫 발행 사이의 HB를 분석기가 직접 증명해야 한다.

**M4. (MID, pipe)마다 용량 매개변수가 있다.** 근거: SB-1, SB-2, SB-7, OS-2. `msglim(MID, pipe)`(Subscribe 기본 4, SubscribeEx 지정값)과 `depth_eff(pipe) = min(요청 depth, 배치가 정한 상한)`을 모델 매개변수로 둔다. 두 receive 사이의 burst가 이 값을 넘으면 그 구독자에게만 drop이 생긴다.

**M5. pipe 사이 순서는 없다.** 근거: SB-3, SB-4, OS-1, OS-5. 한 메시지의 여러 pipe 도착 순서, 그리고 메시지와 그 결과(relay의 재발행) 사이의 다른 pipe 도착 순서는 구독 순서·priority·CPU 수·permissive mode에 달려 있다. 순서 주장은 스케줄링 모델을 인자로 가져야 한다.

**M6. 수신은 네 갈래다.** 근거: SB-9. 성공, `NO_MESSAGE`, `TIME_OUT`, 오류를 나누고 상태 갱신은 성공 경로에만 둔다. 수신 buffer는 같은 pipe의 다음 receive까지만 유효하다. payload 복사와 포인터 보관을 다른 사건으로 둔다.

**M7. startup sync는 조건부 간선이다.** 근거: ES-1–ES-7. §3.3의 규칙 R-sync-1, R-sync-2를 쓴다. `WaitForSystemState`·`WaitForStartupSync`·`RunLoop` 호출은 호출자를 준비 완료로 선언한다. `WaitForStartupSync`는 timeout을 숨긴다. OPERATIONAL은 모든 앱의 RUNNING을 뜻하지 않는다.

**M8. 분석 단위는 task, 정체성 단위는 앱이다.** 근거: ES-8, TBL-2, TBL-3. child task의 ES·SB·TBL 호출은 부모 앱의 것으로 기록한다. TBL LockFlag는 같은 handle을 쓰는 task들이 공유한다.

**M9. 재시작은 비동기 요청과 정해진 순서의 teardown이다.** 근거: ES-9, ES-10, SB-12, TBL-7, EVT-1. 모델 사건열은 `request → (RunLoop false | kill timer) → cleanup(EVS, SB, TA, TBL, TIME) → delete tasks → create(new AppId) → re-init`이다. 이 창에서 구독자의 pipe·queue·state가 초기화된다. 다른 앱의 AppId 보관과 table 공유는 새 인스턴스와 연결되지 않는다.

**M10. TBL 잠금은 descriptor 단위이고 갱신 의미는 buffering에 달려 있다.** 근거: TBL-1–TBL-5, TBL-9. 아래 상태를 둔다.

```text
# [설계 제안] TBL 추상 상태 (handle h, table t)
desc(h)  = { lock: Bool, buf: BufId | ⊥, updated: Bool }
table(t) = { kind: SINGLE | DOUBLE, active: BufId | ⊥, loadInProgress: Bool, owner: AppId | UNDEFINED }
GetAddress(h):  t.owner == UNDEFINED          → (UNREGISTERED, ptr=NULL)
                t.active == ⊥                 → (NEVER_LOADED, ptr=NULL), desc 불변       # TBL-1
                otherwise                     → desc.lock:=true; desc.buf:=t.active; ptr→t.active
ReleaseAddress(h): desc.lock := false (buf는 그대로)
locked(t, b) := ∃h' ∈ handles(t). desc(h').lock ∧ desc(h').buf == b                       # TBL-3
SINGLE update: locked(t, active) → (INFO_TABLE_LOCKED, loadInProgress 유지)                  # TBL-4
DOUBLE load:   locked(t, inactive) → (NO_BUFFER_AVAIL, loadInProgress=false)                 # TBL-5
               else 기록 후 active := inactive (holder의 ptr는 옛 buffer를 계속 가리킴)
경고 후보: ptr를 얻은 뒤 같은 h로 GetAddress를 다시 부르고 옛 ptr를 쓰는 경로 (TBL-2)
```

**M11. NEVER_LOADED와 INFO 코드는 구현 기준으로 해석한다.** 근거: TBL-1, TBL-9. NEVER_LOADED 포인터는 NULL이다. INFO 코드는 양수다. `GetAddresses`의 집계 상태로 handle별 잠금을 판단하지 않는다.

**M12. EVS는 진단 근거로 약하다.** 근거: SB-5, EVT-1, EVT-2, EVT-3. 등록 전 event는 사라진다. SB event는 발행 앱의 등록과 type mask, 그리고 SB 전체에서 공유되는 filter 상한에 걸린다. 분석기는 event 존재 여부를 정상 동작의 증거로 쓰지 않는다.

**M13. 시각 정보의 의미는 프레임워크가 정한다.** 근거: EVT-4, EVT-6. header 시각은 발행 시각이다. 시작 직후 시계는 NOT_SET이다. freshness 판단에 header 시각을 쓰려면 이 두 조건을 반영해야 한다.

**M14. 통신 그래프의 입력에 table·명령·build 설정이 들어간다.** 근거: SB-2, SB-11, SB-13, §3.7. `Quality`는 local 전달에 영향이 없다. 구독 집합은 시간에 따라 바뀐다(table update, AddPacket, route disable).

### 3.10 수정본에 대한 정정과 남은 미확인 항목

**[확인된 사실]** 수정본에서 고쳐야 할 세 문장(§4.2 L185의 0-pipe 경로, §7.1 L315의 update 차단, §7.1 L317의 `NEVER_LOADED` 포인터)은 근거 항목(SB-5·SB-6, TBL-4·TBL-5, TBL-1)과 함께 §10.4.2의 RV3–RV5에 모았다.

**[미확인]** 다음 항목은 이 절의 결론에 쓰지 않았다.

- VxWorks queue의 순서 의미와 RTOS 비행 build의 선점 동작.
- child task가 부모 AppState와 TBL 잠금에 주는 영향(ES-8). 코드만 읽었다.
- owner `CFE_TBL_Load`의 lock 밖 구간 후보(TBL-6). stress 시험을 하지 않았다.
- TBL ground 경로(Load → Validate → Activate → `NotifyByMessage` → `Manage`)와 알림 유실 시나리오(TBL-8).
- 협조하지 않는 앱의 kill-timeout 재시작 경로와 재시작 중 SB 경로의 실행.
- SBN과 원격 구독, EDS build, mission의 MSG·MID mapping override.
- 다중 코어에서 `SystemState` 읽기의 메모리 순서.
