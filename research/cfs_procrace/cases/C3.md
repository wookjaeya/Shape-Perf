## 4. Resources and where they are published (buggy revision 6.4.1)

The roadmap (§2.2) warns that the SB AppId and the EVS AppId are different fields. They are kept separate here.

GitHub permalinks below point to tag `v6.5.0a` = `b2765d9f` (2017-07-07). The earliest git revision with cFE code is the import `792f5e35` (2017-06-29); its `cfe/` subtree is identical to `b2765d9f`, so the permalinks show the import's code (§3). Both are already **fixed**. A permalink is given only where the cited statement is unchanged from 6.4.1. The buggy pin is the tarball line.

**R-SB: `CFE_SB.AppId`, the SB task's ES application ID, used as the event sender ID by SB APIs.**
- Storage: `cfe_sb_t CFE_SB;` is a file-scope object with no initializer (`641:cfe/fsw/cfe-core/src/sb/cfe_sb_task.c:L105`; same in [v6.5.0a cfe_sb_task.c#L105](https://github.com/nasa/cFE/blob/b2765d9f905aa11f0c3b419b62233597366a7db9/cfe/fsw/cfe-core/src/sb/cfe_sb_task.c#L105)).
  - Its value before publication is therefore 0. This is consistent with the issue ("In this case the value used is actually 0").
  - `CFE_SB_EarlyInit` does not set it (`641:…/sb/cfe_sb_init.c:L121-L166`).
- **Publication site:** in the SB task, `CFE_SB_TaskMain` → `CFE_SB_AppInit` → `CFE_ES_GetAppID(&CFE_SB.AppId);` (`641:…/sb/cfe_sb_task.c:L127, L184, L198`; [v6.5.0a#L206](https://github.com/nasa/cFE/blob/b2765d9f905aa11f0c3b419b62233597366a7db9/cfe/fsw/cfe-core/src/sb/cfe_sb_task.c#L206)).
- SB then registers with EVS: `CFE_EVS_Register(CFE_SB.EventFilters, …)` at `641:…/sb/cfe_sb_task.c:L257`.

**R-EVSID: `CFE_EVS_GlobalData.EVS_AppID`, EVS's own application ID, used by `EVS_SendEvent` for EVS's own events.**
- Initial value: `CFE_EVS_EarlyInit` (run by the ES main thread before any core task exists) zeroes the global, then sets `EVS_AppID = CFE_EVS_UNDEF_APPID` (`641:…/evs/cfe_evs_task.c:L188, L190`).
  - The constant is `#define CFE_EVS_UNDEF_APPID 0xFFFFFFFF` (`641:…/evs/cfe_evs_task.h:L105`; [v6.5.0a#L105](https://github.com/nasa/cFE/blob/b2765d9f905aa11f0c3b419b62233597366a7db9/cfe/fsw/cfe-core/src/evs/cfe_evs_task.h#L105)).
- **Publication site in 6.4.1:** in the EVS task, `CFE_EVS_TaskMain` → `CFE_EVS_TaskInit` → `Status = EVS_GetAppID(&CFE_EVS_GlobalData.EVS_AppID);` (`641:…/evs/cfe_evs_task.c:L320, L372, L385`).
  - This is the **second** step of TaskInit, right after `CFE_ES_RegisterApp()` (L377), and before EVS registers itself with `CFE_EVS_Register` (L393), creates its pipe with `CFE_SB_CreatePipe` (L401) and subscribes. The same order holds in 6.4.2 before F2 moved the global assignment (`642:…/evs/cfe_evs_task.c:L386` RegisterApp, `L394` `EVS_GetAppID(&AppID)`).

**R-EVSREG: `CFE_EVS_GlobalData.AppData[i].RegisterFlag` and the per-app filters, i.e. EVS registration state.**
- Zeroed in `CFE_EVS_EarlyInit` (`641:…/evs/cfe_evs_task.c:L188`).
- Published per app by `CFE_EVS_Register` (`641:…/evs/cfe_evs.c:L127` onwards sets `RegisterFlag = TRUE`).
- EVS registers itself at `641:…/evs/cfe_evs_task.c:L393`.
- `AppData` is the first member of `CFE_EVS_GlobalData_t` and has `CFE_ES_MAX_APPLICATIONS` (=32, `641:cfe/fsw/platform_inc/cpu1/cfe_platform_cfg.h:L570`) entries (`641:…/evs/cfe_evs_task.h:L154`).

**R-ES: ES TaskTable/AppTable entries for each core task, including the TaskId → AppId link that `CFE_ES_GetAppID` reads.**
- Published by the ES main thread in `CFE_ES_CreateObjects`, under the ES shared-data lock, before that lock is released (`641:…/es/cfe_es_start.c:L838` lock; `L875` `OS_TaskCreate`; `L919` `TaskTable[…].AppId = j`; `L933` unlock).
- This resource is protected (§6). It is listed because it is what makes `CFE_SB.AppId = 0` meaningful.

**Which app owns AppId 0 (inference from code).**
- `CFE_ES_Main` clears every `AppTable[i].RecordUsed` at each start (`641:…/es/cfe_es_start.c:L200-L207`).
- `CFE_ES_CreateObjects` takes the first free slot (`L825-827`).
- `CFE_EVS` is the first `CFE_ES_CORE_TASK` in the object table (`641:…/es/cfe_es_objtab.c:L120`).
- So AppId 0 = CFE_EVS. This matches the issue's "0 … is in fact a valid AppID for a different app".
- jphickey's Trac comment of 2015-05-07 supports determinism, "for the core applications, they are always present and always get the same AppIDs" (§1.2.1 #1b), but does not say which app gets 0.
- The syslog line "ES Startup: Core App: %s created. App ID: %d" (`L924`) would confirm it in a run.

## 7. Required order and its provenance

**Statement.**
- Issue and VDD form (from-reference): each core app reaches its main loop ("RunLoop") before the next core app starts its init, regardless of priority. This is a sufficient condition.
- Fine-grained form (**inference from code at the 641 pins**; neither the issue nor the VDD states (a) and (b)). Before a task executes an SB API path that sends events with `CFE_SB.AppId` (here TIME's `CFE_SB_CreatePipe` in `CFE_TIME_TaskInit`):
  - (a) SB has published `CFE_SB.AppId` (R-SB, `641:…/sb/cfe_sb_task.c:L198`) **and** registered with EVS (`L257`);
  - (b) EVS has completed `CFE_EVS_TaskInit`: R-EVSID valid (`641:…/evs/cfe_evs_task.c:L385`) and R-EVSREG for EVS set (`L393`).

**Provenance.**
- Issue #73 first list, item 1 (the synchronization requirement) and second list, items 3-7 (the failing interleaving).
- 6.4.2 VDD Table 1.2-2 row 1: "This forces each core application to reach its respective main loop before the next core application will be started regardless of the platform's priority settings".
- 6.4.2 VDD Table 1.2-2 row 3: "set the EVS_AppID value last. This will assure that all other initialization is done before the AppID is valid".
- jphickey, Trac comment of 2015-05-07 (§1.2.1 #1-#1d): "There are two possible approaches to solving this". Option 1 moves "more of the critical initialization bits into the EarlyInit calls", noting that core apps "are always present and always get the same AppIDs". Option 2 keeps the init in the task and uses startup sync so each core task reaches "the run loop before starting the next task. This would only need to be done for the core tasks". Option 2 is the issue-level order above.
- jphickey, 2015-05-08: "DEPENDENCY NOTE: Trac #71 implements the first part of this fix," (§1.2.1 #2).
- Branch comment (§1.2.1 #3a): "that once the AppID is valid that all other initialization is also done."

**Inference: when the crash happens (from code at the 641 pins).**
- The crash condition: TIME's `CFE_SB_CreatePipe` event call happens while
  - EVS has **not** reached `641:…/evs/cfe_evs_task.c:L385`, so `EVS_AppID == 0xFFFFFFFF`, **and**
  - `AppData[CFE_SB.AppId].RegisterFlag` is FALSE, i.e. SB has not reached `641:…/sb/cfe_sb_task.c:L257`, whether or not it has run L198.
- Why L257 and not L198 is the binding SB point:
  - before L198, `CFE_SB.AppId == 0` (EVS's slot), unregistered while EVS is before L393;
  - between L198 and L257, the event carries SB's own AppId, whose `RegisterFlag` is still FALSE;
  - both go `EVS_NotRegistered` → `EVS_SendEvent` → `EVS_IsFiltered(0xFFFFFFFF)` (`641:…/evs/cfe_evs.c:L285-L294`; `641:…/evs/cfe_evs_utils.c:L199-L215, L616`), which crashes while EVS is before L385.
- (b) violated alone (EVS before L385, SB past L257): this state is **possible, but it cannot crash on this path**. U3 takes the `EVS_IsFiltered(SB's id)` branch, not `EVS_NotRegistered`.
- (a) violated alone (EVS past L385): no out-of-range index, no crash. The outcome depends on how far SB has got:
  - SB before L198: the event carries AppId 0 = EVS and is misattributed to EVS. If EVS is past L393, `EVS_IsFiltered(0, DEBUG)` drops it, because `CFE_EVS_DEFAULT_TYPE_FLAG` is 0xE ("Debug = OFF", `641:cfe/fsw/platform_inc/cpu1/cfe_platform_cfg.h:L1424`; set at registration, `641:…/evs/cfe_evs.c:L131`). If EVS is between L385 and L393, `EVS_NotRegistered(0)` → `EVS_SendEvent` → `EVS_IsFiltered(0)` finds `ActiveFlag` FALSE and drops the event; the syslog line is still written.
  - SB between L198 and L257: `EVS_NotRegistered(SB's id)` emits one ERROR event "App %s not registered with Event Services. Unable to send event." (`CFE_EVS_ERR_UNREGISTERED_EVS_APP`) plus the same syslog line (`641:…/evs/cfe_evs_utils.c:L199-L215`).

### 8.3 What each part guarantees (inference from code unless quoted)

**F3 guarantees the order:**
- Core TaskInit k+1 begins only after core task k has finished TaskInit and called `CFE_ES_WaitForStartupSync`. This holds regardless of priority, because task k+1 does not exist yet.
- The order is the table order EVS → SB → ES → TIME → TBL.
- TIME's `CFE_SB_CreatePipe` therefore runs after SB's AppInit and EVS's TaskInit, which closes §7 (a) and (b) for TIME.
- Failure is **fail-stop**: on timeout, `CFE_PSP_Panic` is called. It is not a soft continue.
- This is a polling barrier (50 ms poll), not a lock or semaphore hand-off.

**F1 guarantees** that `EVS_SendEvent` never indexes `AppData` with an out-of-range `EVS_AppID`. Such an event is dropped ("Otherwise do nothing", VDD). It is a guard, not an ordering.

**F2 guarantees** that a valid `EVS_AppID` implies EVS init is complete (VDD row 3). It narrows, but does not remove, the window in which EVS's own early events are dropped by F1.

**Not guaranteed by the fix:**
- F3's table order puts EVS **before** SB (`642:cfe/fsw/cfe-core/src/es/cfe_es_objtab.c:L120, L122, L124, L126, L129`: EVS, SB, ES, TIME, TBL; same order as 6.4.1). In `642:…/evs/cfe_evs_task.c`, EVS registers (`L402`) and then calls `CFE_SB_CreatePipe` (`L410`) before it publishes `EVS_AppID` (`L436`). That call therefore still runs while `CFE_SB.AppId == 0`.
- With the 6.4.2 table, AppId 0 = EVS (inference, same derivation as §4: `642:…/es/cfe_es_start.c:L211` clears `AppTable[i].RecordUsed`, `L803` takes the first free slot), which has just registered. So the event is attributed to EVS: no crash, but misattribution. The DEBUG event is then dropped by the default type flag (inference, §7).
- In current code (§9; order since `b9bec567`, committed 2026-04-07) the default order is ES, EVS, SB, TBL, TIME. Both ES and EVS call `CFE_SB_CreatePipe` before SB publishes `CFE_SB_Global.AppId`, and the undefined AppId yields `CFE_EVS_APP_ILLEGAL_APP_ID`.
- This is **version-dependent**.
