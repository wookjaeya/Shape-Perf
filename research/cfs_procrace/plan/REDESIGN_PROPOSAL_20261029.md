## 0. 한 줄 요약

지금 Kairos가 내는 VIOLATING/TOLERATED는 도구가 찾은 것이 아니라, 버그를 아는 사람이 사례·판마다 적어 넣은 규칙(`rspec`의 `appreq`·`allowed`·`harm`, 역할, 예측 모델)을 기록에 대조한 결과다. 고치는 방향은 **판정 규칙을 사례와 무관한 하나로 고정하고(서로 다른 행위자 사이의 "초기화 → 사용" 의존이 기록된 동기화로 순서 지어지지 않으면 보고), 결과 분류는 관측에서, 처리 분류는 코드에서 자동으로 내고, 사람 입력은 cFE/OSAL 판마다 한 번 쓰는 플랫폼 모델로만 제한**하는 것이다. 사례 지식은 탐지 입력에서 빼고 평가(정답)로만 쓴다.

### 1.3 왜 이렇게 됐나 [F][I]

- SPEC §1.6 "세 판정"은 **caller 수준 판정**(`appreq`, caller 측 `allowed`)만이 상태(TOLERATED/VIOLATING)를 정하게 했고, QT-4(2026-10-15)는 "**규칙(코드 패턴)만으로는 어떤 발생도 받아들이지 않는다**"고 정했다. 코드에서 자동으로 뽑은 재시도 루프(`code_pattern`, `code-derived` 등급)는 `NOT_READY_UNJUDGED`로만 남는다.
- 그 결과 **판정의 근거는 반드시 사람이 읽은 글(`prov` 기록, side `caller`)**이어야 한다. 이것이 외부 검토의 "근거 없는 라벨" 지적에 대한 답이었지만, 도구를 "사람이 적은 요구를 기록에 대조하는 검사기"로 바꿔 놓았다.
- "레퍼런스 기반"이라는 말이 두 뜻으로 쓰였다. (a) **실험 조건·환경은 레퍼런스에서**(PI 규칙; 유지해야 한다). (b) **판정도 레퍼런스 글에서**(이것이 문제). (b)는 사람이 결론을 적고 도구가 확인하는 구조다.
- SPEC §1.11의 "기여 가설 반증 조건"에 "**규칙이 다섯 사례에 맞춰진 것이 아님**: 고정된 엔진과 일반 규칙을 새 사용에 적용 … 모든 대상에 버그 전용 조건이 필요하면 주장할 수 없다"가 이미 적혀 있다 [F]. 지금 상태는 SPEC 자신의 반증 조건에 걸린다.

## 2. 설계 원칙 — 탐지기가 받아도 되는 입력

기존 탐지기와 비교하면 경계가 분명하다 [F: SPEC §1.11 관련 연구표의 범위 안].

| 도구 | 사람이 한 번 쓰는 것 | 버그마다 쓰는 것 |
|---|---|---|
| TSan/FastTrack | 스레드 라이브러리의 동기화 의미(lock/unlock = acquire/release, create/join) | 없음 |
| RacePro 계열(프로세스 race) | 커널 호출이 어떤 공유 객체를 읽고 쓰는지(플랫폼마다 한 번), 실패 판별(crash·오류·출력 차이) | 없음 |
| **Kairos 지금** | 위 + 자원 모델 | **사례·판마다 요구·허용·피해·역할·예측 모델** |
| **Kairos 제안** | cFE/OSAL 판마다 플랫폼 모델(자원·연산·동기화·관측 지점) | **없음** |

플랫폼 모델이 "사례를 보고 쓴 규칙"이 되지 않게 하는 세 가지 보호 장치 [D-제안]:

- **G1 사례 무관성 lint**: 플랫폼 모델 파일에 이슈 번호, 사례 id, 앱 이름(CF, BP, SAMPLE_APP …), 특정 CF 커밋 참조가 있으면 `kz phi check`가 거부한다. `authored`의 "cases inspected" 필드는 평가 보고에만 남긴다.
- **G2 정적 사실 교차 검증**: 모델이 주장하는 효과(어느 함수가 어느 테이블 필드를 쓰고 읽는지, 키가 무엇인지)는 kz-static의 writer/reader 사실과 맞아야 한다. 이미 `bind field … via …`가 있으므로(§1.1) 검사는 확장이다. 맞지 않는 항목은 오류다.
- **G3 선동결**: 플랫폼 모델은 그 판의 어떤 사례도 돌리기 전에 커밋·해시로 동결하고, 같은 판의 모든 사례에 같은 파일을 쓴다. 사례를 본 뒤의 편집은 새 판 번호로만 허용하고 평가에 "편집 후"로 표시한다.

## 3. 재설계 안

### 3.1 판정 규칙 하나 [D-제안]

플랫폼 모델이 주는 것은 다음 세 가지뿐이다: (i) 키가 있는 공유 자원(이름 테이블, id 테이블, 파이프 경로)과 그 **초기화 연산**(publish: create/register/subscribe)·**사용 연산**(lookup by name, use by id, send)·**해제 연산**(retire), (ii) 각 연산의 결과 코드가 "준비됨/준비 안 됨/오류" 중 무엇인지(`20_ops.kzp`에 이미 있다), (iii) 동기화 간선(task 생성, 큐 전달, 세마포어, 단계 장벽).

규칙: **행위자 A의 사용 u(자원 r, 키 k)에 대해, 같은 세대의 초기화 p(r, k)가 다른 행위자 B에 있고, 기록된 동기화만으로 p → u 순서가 서지 않으면 (p, u)를 순서 없는 의존으로 보고한다.** 사용 결과(성공/실패)는 순서를 세우는 데 쓰지 않는다(지금의 "outcome narrowing", RF 규칙은 "이번 실행에서 무엇을 읽었나"를 복원하는 데만 쓴다).

이 규칙에는 사례 입력이 없다. 어떤 호출이 "의존 사용"인지는 역할 선언이 아니라 **연산의 종류**(키 있는 lookup/use)에서 온다. `appreq`는 없다: 이름으로 찾는 코드는 그 이름이 있기를 요구한다는 것이 곧 API의 뜻이다.

### 3.2 결과 분류 — 관측에서 [D-제안]

보고된 쌍 (p, u)마다 이번 실행의 사실을 붙인다. 사람이 정하는 것이 없다.

| 분류 | 조건(기록에서) |
|---|---|
| `OBSERVED_FAIL` | u의 결과가 플랫폼 모델의 not_ready 코드(예: `OS_ERR_NAME_NOT_FOUND`, `CFE_ES_ERR_APPID`) |
| `OBSERVED_WRONG_VALUE` | u가 성공했지만 읽은 레코드의 키 쓰기가 "이 행위자의 세대"의 p가 아니다(reads-from 불일치; §3.5) |
| `LATENT` | u가 성공했지만 p → u 동기화 순서가 없다(이번엔 운 좋게 맞음) |
| `USE_BEFORE_ANY_PUBLISH` | 기록 안에서 u가 모든 p보다 앞(프로그램 순서·기록 순서 모두) |
| `ORDERED` | p → u가 동기화로 선다(보고하지 않음; 수만 센다) |

이 분류는 지금 엔진의 "관측된 결과(consequence)"(SPEC §1.6 세 번째 판정)와 같은 자리이고, 그것이 **유일한 판정**이 된다.

### 3.3 처리 분류 — 코드에서, 판정이 아니라 사실로 [D-제안]

실패했을 때 프로그램이 어떻게 하는지는 **정적 분석과 기록이 자동으로** 분류한다. 지금 SPEC §1.6의 `allowed` 어휘(`retry_until_ready`, `returned_and_tested`, `fallback`, `exit`)를 그대로 쓰되, **사람이 고르지 않고 kz-static이 뽑는다**:

- 재시도: u의 반환값을 not_ready 코드와 비교하는 분기가 같은 호출로 되돌아가는 루프 안에 있으면 `retry(bound=N)`. N은 빌드 상수. (SPEC §4.3 루프 인식과 `cont_candidate` 추출이 이미 있다 [F]. QT-4가 그 결과를 판정에서 막았을 뿐이다.)
- 종료: 실패 경로가 `CFE_ES_ExitApp`/`ResetCFE`/`PSP_Restart`에 닿으면 `exit`.
- 무시: 반환값을 검사하지 않으면 `ignored`.
- 대체: 다른 연산으로 가면 `fallback(op)`.
- 기록에서는: 같은 행위자가 같은 키로 u를 반복해 성공하면 `retried_then_ok(k)`, 그 뒤 종료 이벤트가 오면 `exited`.

처리 분류는 **race를 지우지 않는다**. "순서 없는 의존, 재시도로 처리됨(상한 25, 이번 실행 2회 만에 성공)"처럼 같이 보고한다. 수정 후 CF가 그런 예다: 수정은 race를 없앤 것이 아니라 실패를 시간 상한이 있는 재시도로 바꾼 것이고, 도구는 그렇게 말해야 한다.

### 3.4 동기화 강도 [D-제안]

cFS는 하드 동기화 대신 시간에 기대는 곳이 많다(`CFE_ES_WaitForStartupSync`의 timeout, `OS_TaskDelay` 뒤 재시도) [F: SPEC §3.6, §3.14]. 동기화 간선을 두 강도로 나눈다.

- `hard`: task 생성 → 자식 첫 이벤트, 큐 put → get, 세마포어 give → take, mutex.
- `timed`: timeout이 있는 장벽, sleep-폴링 루프, 재시도 지연. **이것은 순서를 세우지 않는다.** 보고에 "시간 의존 순서"로 표시한다.

timed만 있는 (p, u)는 `LATENT(timed)`로 남는다. 이것이 #184 수정 후 상태의 정확한 이름이다.

### 3.5 행위자 정체성과 세대 [D-제안]

C5가 보여 준 대로 `pthread_t`는 재사용된다. 행위자 정체성은 **(스폰 사건 id, 세대)**이고, 레코드의 키 쓰기도 세대를 가진다(SPEC §1.3의 generation을 그대로 쓴다). "이 행위자의 p"는 "이 행위자를 만든 스폰과 같은 세대에서 그 키에 한 쓰기"다. E-ID1은 스폰 요청 발생과 task id로만 잇는다(지금 구현의 원칙 [F])에 **세대 비교**를 더한다. 이것으로 C5의 잘못된 AppId 반환은 `OBSERVED_WRONG_VALUE`가 된다 [I].

### 3.6 검증 단계 — 예측 모델 대신 강제 순서 [D-제안]

`kz predict`의 `.kzm`(행위자와 프로그램을 손으로 쓴 모델)은 사례 전용 입력이므로 뺀다. 보고된 `LATENT` 쌍의 검증은 **`kz hold`로 p와 u의 순서를 실제 바이너리에서 뒤집어 돌리는 것**으로 한다(RacePro의 replay-validation과 같은 자리; SPEC §4.13의 확인 절차가 이미 있다 [F]). 결과가 `OBSERVED_FAIL`/`WRONG_VALUE`가 되면 확인된 잠재 위반, 안 되면 (i) 모델에 없는 동기화가 있거나 (ii) 무해한 쌍이다. 둘 다 세어 보고한다. 모델 기반 예측(`kz predict`)은 cone을 **정적 사실 + 기록 접두사에서 자동으로** 만들 수 있을 때만 다시 넣는다(SPEC §4.9의 구성은 원래 그렇게 쓰여 있다 [F]).

### 3.8 플랫폼 모델의 자동 유도 — 2단계 [I]

플랫폼 모델도 손으로 쓰는 한 "사람이 아는 것"이라는 비판이 남는다. kz-static(clang AST)은 이미 테이블 walk 펼치기, 필드 writer, spawn 사실을 뽑는다 [F: `docs/static_facts.md` §4–§5]. 여기에 패턴 셋을 더하면 모델의 큰 부분을 **유도**할 수 있다:

- 이름 조회: 전역 테이블을 돌며 문자열 필드를 인자와 비교하는 함수 → `lookup(kind=테이블, key=name)`.
- id 사용: 인자 id에서 인덱스를 계산해 레코드를 읽는 함수 → `use(kind, key=id)`.
- 생성/등록: 빈 레코드의 키 필드를 쓰는 함수 → `publish`; 키 필드를 지우는 함수 → `retire`.
- 결과 코드: 조회 실패 경로가 돌려주는 상수 → `not_ready` 코드.

유도된 모델과 손으로 쓴 모델의 일치율을 보고하면 "사람 입력이 얼마나 남았나"가 수치가 된다. 이것은 연구 기여가 될 수 있지만 범위 위험이 있어 1단계(§9) 뒤에 둔다.

## 4. 세 사례를 새 규칙에 대입 [I]

| 사례 | p (초기화, 행위자) | u (사용, 행위자) | 동기화 | 기대 보고 |
|---|---|---|---|---|
| C1 수정 전 | `OS_CountSemCreate("BP0_tsem")`, BP | `OS_CountSemGetIdByName("BP0_tsem")`, CF | 없음(둘 다 ES 시작 스크립트가 만든 task; 스크립트 순서는 생성 순서일 뿐 완료 순서가 아님) | `OBSERVED_FAIL`, 처리 `exit`(`CFE_ES_ExitApp`) |

세 사례 모두 같은 한 가지 모양("다른 행위자의 키 있는 공유 테이블 초기화에 동기화 없이 의존")이다. 논문의 주장도 이 한 문장으로 세울 수 있다. 위 표는 기대이고, 실제 수는 기존 W6·C5 기록을 다시 재생해 얻는다(부팅 불필요, §8).

## 7. 위험과 한계 [I]

1. **HB 모델의 완전성.** 모델에 없는 하드 동기화는 오탐을 만든다. 대응: RQ2의 "강제해도 안 됨"을 모델 갭 후보로 돌려 플랫폼 모델을 고치되, 고친 뒤 판 번호를 올리고 다시 전체를 돌린다(G3).
2. **후보 폭증.** 키 있는 사용 전부를 보므로 수가 커진다. 대응: 분류별 집계, 검증 우선순위(관측 실패 > 잘못된 값 > latent), 같은 (호출 지점, 키 종류) 묶기.
3. **시간 의존 동기화의 처리.** timed를 순서로 안 세우면 cFS의 많은 시작 순서가 latent로 보고된다. 그것이 사실이다. 대응: `LATENT(timed)`를 따로 세고, 검증에서 지연을 넘기는 강제 순서(hold)로 실제로 깨지는지 본다.
4. **관측 비용.** 플랫폼 ops 전체를 보면 이벤트가 늘어난다. 대응: 손실 계정은 이미 있다(SPEC §5.6). 계측 경로가 먼저다(D3).
5. **플랫폼 모델도 사람이 쓴다.** 1단계에서는 남는 한계다. 대응: G1–G3와 RQ5, 2단계의 자동 유도(§3.8).
6. **C5 32비트·실시간 조건**은 이 제안과 무관하게 그대로다.

- **PI 결정 요청 중인 항목**(W3 G-I-H, E-03, E-15, ctloff, 통제 쌍 집계): 모두 지금 규칙에 대한 질문이므로 **보류**한다. 재설계 뒤 같은 기록에서 다시 묻는다.
