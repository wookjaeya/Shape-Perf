# Semantics coverage rule (revision 1, 2026-11-16)

Revision 2 (2026-11-18) is section 8.  It changes the name-space entries (section 4, N) only and writes its data into new
files; sections 1-7 and the data files of revision 1 stand as they are.

This rule says which entries the semantics data files under `semantics/` hold, before any of those files exists. The data
files are generated by a mechanical scan of version-pinned files (research `env/tools/semantics_scan.py`, `generate`), and
the provenance check (`semantics_scan.py check`) regenerates them and compares, so that no entry is chosen by hand and no
entry is chosen because a case uses it. `kz-static extract --semantics FILE` reads the files (`docs/static_facts.md` 5t)
and joins the entries that apply to the build into the facts section SEMANTICS; `kz-static relations` names the items a row
rests on that are not verified (`sem-unverified(...)`).

Whether this tier of input (framework-layer semantics generated from version-pinned framework source) is the
framework-adapter tier the method admits is an open question for the PI. This rule does not assume it. The data files
carry the tier name `framework-layer data` and name no case; the lint `case-ids-data` checks the second, and the lint
`semantics-names` keeps every API name of the data files out of engine code.

## 1. Components and anchors

A component is one version of one framework component (or of the C library headers), with:

- its tree root, its public headers (globs relative to the root) and its definition sources (globs);
- its anchors, each a line range or a name in a version-pinned file, written into the component list before any data
  file (`records/semantics-20261116/semantics_trees.tsv`):
  - status: the line range of the header block that defines the status constants (from the success constant on), the
    status typedefs (if the version has one), the success constant, and the severity masks (if the version has them);
  - event-type and run-status: the line range of the enumeration or macro block of each, and its typedef (if the version
    has one);
  - object-id generation (a component whose objects are named through a common object-id layer): the layer's lookup,
    create and delete functions, its name-initialising macro, the kind macro of a source file and the name field of the
    common record;
  - C library headers: the root of the headers the builds read and the local copy of C library source text the P0 table
    cites.

The anchors are framework or library names. They are data of this rule, never engine constants. Every anchor is resolved
by the scan to its file:line, and every file a data file cites is pinned by its sha256.

Components of revision 1: OSAL 5.0.99 (tree f34759d6), cFE 6.7.99 (tree 6cccb3f5), OSAL 7.0.1, cFE 7.0.1, OSAL 4.1.1,
cFE 6.4.1, cFE 6.4.2 (the framework versions the five analysed builds read) and the C library 2.39 headers. Not in
revision 1: the platform support package, the applications, the framework's unit-test stubs.

## 2. Groups

The constants of a kind are every integer macro (`#define NAME value`) or enumerator (`NAME = value`) in the anchor's
line range. Their value is the value of the literal as written (a cast is not applied; it is the value `RET_CONSTS`
gives for the same constant). A macro whose value is another constant of the range takes that constant's value.

## 3. Entries

A function declared in the public headers of a component (a prototype statement outside comments and preprocessor
lines) is an entry when one of these holds:

- **E1**: its return type or the type of a parameter is a status, event-type or run-status typedef of the component (or
  a pointer to one);
- **E2**: the comment block right above its declaration names a status constant in a return line (`@retval`, `\retval`,
  `\retcode`, `@return`, `\return`, `\returns`), or an event-type or run-status constant (`#NAME`, also in `\arg` lines)
  in the paragraph of a parameter (`@param`, `\param`);
- **E3**: its definition in the component's sources (one definition by text) returns a status constant (`return NAME;`).

E2 and E3 exist because several versions declare the status, event-type and run-status values as plain integers (an
`int32` return, a `uint16` event-type parameter) and say their domain only in the documentation, or in no documentation
at all (OSAL 4.1.1 headers carry no per-function documentation).

Per entry the data holds: the declaration (file:line), the definition (file:line, or `-` when there is none or more than
one by text), the kind of the return and how it was found (`typed`, `doc`, `body`, joined by `+`), the rule(s) that made
it an entry, each documented return constant with its value and line (`ret`), each parameter of a kind with its position
and how it was found (`arg`; positions only, no parameter names), and each status constant the definition returns by
text (`body-ret`, the evidence of E3). The status space of the component (success constant, severity masks) is given
once (`status-space`).

The scan also prints the number of public functions declared (`declared=`), so that the share of entries is reported.

## 4. Name-space entries

The name-space entries are what judgement rules 8.2 condition (가) asks for: per named object kind, the table, the
functions that look a name up in it, create it and delete or clear it, the comparison function and its comparison, the
stored name and its declared extent, each with its framework version, file:line and the file's sha256.

- **N (object-id generation)**, for a component with the object-id anchors: one entry per source file that sets the kind
  macro; the kind constant and its value (public header line); the functions of that file whose bodies call the layer's
  lookup with the kind (lookup), its create with the kind (create), its delete (delete); the stored name: the
  name-initialising macro's field in each create and its one-byte array declaration (extent and its line); other stores
  into the common name field in that file (`other-store`, the evidence a name mapping into the table needs, condition
  (다)); once per component, the comparison function (a function whose body compares a parameter with the name field
  through a byte-string comparison of the P0 comparison table) and the status constants named in the bodies of the
  layer's lookup and the functions of its file it calls, to depth 3 (`chain-status`, where the absence constant and the
  other constants of the lookup come from).
- **T (table generation)**, for every other framework component: one entry per stored-name path (a subscripted table
  path, subscripts written `[]`) that a function compares with one of its parameters through a byte-string comparison of
  the P0 comparison table; the comparing functions and their bound argument (`compare`); the public ones that do not
  copy into the path (`lookup`) and those that do (`create-check`); every function that copies one of its parameters into
  the path (`copy`) or clears it (`clear`); the extent of the path's last field when its one-byte array declaration is
  found through the declared types of the path (`extent`, else `-`).

The comparison bound value of a configured constant (e.g. a maximum name length) is the build's: the entry names the
constant, and the value is read from the build's configuration header when a rule needs it.

## 5. P0 declarations

For every entry name of the P0 tables (`lib/llvm/p0.cpp`), its first prototype in the C library headers the builds read
(file:line, pinned by sha256) and the attributes of that declaration: `pure`, `const`, `noreturn`, `nonnull(i,...)`,
`warn-unused-result`, `nothrow`. These are collations with the declarations of the C library version the builds link; the
behaviour the P0 table states beyond them is collated only where the local copy of C library source text has the lines
(the P0 table's `source`), otherwise it is `unverified`. Collation with any other text (other C library versions, the
POSIX text) needs a new external resource and is not done.

## 6. Verification states (SEMANTICS)

| state | meaning |
|---|---|
| `doc-collated` | read from the version-pinned header of the build (documentation or declaration), applied because the build holds that file (or the entry's definition file) with the pinned sha256 |
| `body-derived` | derived by kz-static from the bodies in the build's facts (`RET_CONSTS`, `RETURNS`), or computed from such items (agreement) |
| `standard-collated` | collated with the local copy of library source text the P0 table cites |
| `unverified` | none of these: a P0 statement without such a copy, a comparison that could not be made, an entry of a version the build does not hold |

`kz-static` counts the items of each layer and state; the report gives collated / total per layer and the number of
entries the first observation path uses.

## 7. What revision 1 does not cover

Functions of the public headers without a status, event-type or run-status return, parameter or documentation;
event-type and run-status domains documented outside a parameter paragraph; definitions found more than once by text
(their body returns are not read: the entry keeps `def=-`); named object kinds whose stored name is reached through an
accessor function rather than a field path (the comparison is in a function whose operand is a call); the platform
support package and the applications. A later revision of this rule is written and committed before the data files it
changes.

2026-11-18, exclusions found by review that the list above did not state (the rule and the data files are unchanged;
a revision is a later step):

- **Named object kinds without a per-file kind macro.** Section 4 (N) says the lookup and the create are taken `with the
  kind`; the scan (`env/tools/semantics_scan.py`) takes a kind only from a `LOCAL_OBJID_TYPE = …` line of the file and a
  lookup or create only when the layer call passes that macro.  A file that passes the kind constant directly has no
  lookup or create line (the time-base kind of the OSAL f34759d and 7.0.1 data has `delete` and `stored-name` only), and
  a kind whose file has no such macro is absent (the timer-callback, condition-variable and console kinds of f34759d).
- **The layer's own clears and the failed-create rollback.** Only stores in the kind's own file are entries; the
  identifier layer's clear of the stored name and its rollback of a failed create are in no entry, so the OSAL data has
  no `clear` or `retire` line.
- **A documented return on a function declared void** is written as a collated return (`return=status by=doc` with a
  `ret` line).  The facts mark such a row unverified from 2026-11-18 (static_facts.md 5w); the scan does not.
- **The argument role of a domain kind says what the parameter's values are, not what the function does** (a run-status
  role may stand on the pointer parameter of a check).  The engine does not name an effect from it alone
  (static_facts.md 5w).
- **The severity constants of a status space** are data rows (`status-space severity`); the outcome class rule reads
  their values, not their names.

## 8. Revision 2 (2026-11-18): name-space entries of the object-id generation

Committed before the scan is changed and before any data file it gives.  It replaces what section 4 (N) says about the
kind of an entry and adds the layer's own operations.  Sections 1-3, 5 and 6, generation T of section 4 and the
`framework_semantics_*` and `p0_declarations_*` files are unchanged.  Grounds: the exclusions of section 7 found by review
(2026-11-18); judgement rules 8.13 items 9, 12 and 13 (`plan/ovm_rev1_20261116/JUDGEMENT_RULES_REV1.md`), which need the
lookup and create of every kind, the layer's clears and the rollback of a failed create.

### 8.1 The kind of an entry

The kind of a name-space operation is **the argument bound to the parameter by which the layer function selects its
table**, at the call of that layer function in the body of the operation's function.  The per-file kind macro of revision
1 is one way that argument is spelled; it is not the rule.

- Per component the data head lists the layer functions the scan follows, each with its definition line and the index
  of the table-selecting parameter:
  `layer-fn <role> <function> def=<file>:<line> kind-param=<index>`, roles `lookup`, `create`, `get`, `create-finalize`,
  `delete-finalize`, `init`, `slot-search` (a role that takes no kind has `kind-param=-`).
- The index is not written by hand: it is the position of the one parameter of the definition whose declared type is
  the component's object-kind type (a new anchor of the component list, section 1).  A component whose version declares
  the kind as a plain integer has the index as an anchor value, checked by the scan against the definition's
  declarator, and the data line says `kind-param=<index> by=anchor`.
- The position differs between layer functions of one version.  Read in the OSAL tree f34759d
  (`osal/src/os/shared/src/osapi-idmap.c`, sha256 `706e2f7f…`): the kind is parameter 0 of the lookup by name (`:962`)
  and of the allocation (`:1146`), and parameter 1 of the functions that take the lock mode first (`:288`, `:910`,
  `:948`, `:1000`).  The other four components are not read here: their lines come from the scan, and the scan step
  reports them per component.
- The argument is resolved to a constant of the component's kind range (macro name or enumerator, with its value and
  definition line).  A call whose argument the scan cannot resolve is a line `kind-unresolved <function>
  at=<file>:<line>` and is counted per component; it is never guessed.
- Consequence: a kind whose file has no per-file macro, and a function that passes the kind constant directly, get
  their `lookup` and `create` lines (section 7, first exclusion of 2026-11-18).

### 8.2 Operations of a kind (lines under `kind`)

`lookup`, `create`, `delete`, `stored-name` and `other-store` as in revision 1, found by the kind of 8.1.  Added:

```
  rollback <create function> def=<file>:<line> at=<file>:<line> status-arg=<i> out-arg=<j>
```

the failed-create rollback inside that create: `at=` is the line of its call of the layer's `create-finalize` function,
`status-arg` the argument that carries the operation status, `out-arg` the argument that carries the out id.

A kind that has no public lookup or create of its own (its records are made inside another kind's function) is listed
with a line `not-covered <reason>` under it; nothing is left out silently.

### 8.3 Operations of the layer (once per component)

The layer's own clears and its finalize functions apply to every kind.  They are statements of the component, at the
top level of the file, never lines under a kind:

```
layer-op clear-table <function> def=<file>:<line> at=<file>:<line> form=fill
layer-op clear-slot <function> def=<file>:<line> at=<file>:<line> form=assign field=<name field>
layer-op rollback <function> def=<file>:<line> status-param=<i> out-param=<j>
layer-op delete-finalize <function> def=<file>:<line> status-param=<i>
```

- `clear-table`: the fill of the whole table in the layer's initialisation.  `clear-slot`: the store of the cleared value
  into the name field in the layer's search for a free record.  `rollback`: the layer's `create-finalize` function, with
  the parameter that carries the operation status and the one the out id is stored through.  `delete-finalize`: the
  layer's function that ends a delete.
- The data states where these statements are; it does not say what a clear means for a lifetime.  Whether the slot
  clear can end a live generation is read from the facts (the `lifetime end:` line of the relations, `docs/static_facts.md`
  5x), not from this file.
- Why a top-level statement.  The present reader of these files (plan rules revisions 3 and 4,
  `lib/llvm/plan_gen.cpp` `read_namespaces`) takes an indented `clear` line as an operation of the kind or table above it
  and plans a store site of that entry from it; an indented operation before any kind is refused (`an operation before
  its kind or table`).  A component-level entry written as such a line would be read as one kind's operation, or would
  be refused for the wrong reason.  A top-level word outside the reader's lists is refused as a whole
  (`is no statement of the namespace data`): the present reader cannot read a revision-2 file at all, and it never takes
  a component-level entry for an operation of a kind.  Kept check of the statement forms against a Python mirror of the
  reader's three tests: research `records/closure-texts-20261118/out/ns_statement_check_2.txt` (19 lines of a revision-2
  file, 9 refused, among them every `layer-fn`, `layer-op`, `rollback`, `not-covered` and `kind-unresolved` line; a mirror, not
  the tool: the build that adds the new reader checks the real one with a fixture of each form).

### 8.4 New data files

- Revision-2 data is written to **new file names**: `semantics/framework_namespaces2_<component label>.txt`, with the head
  lines `semantics-data 2` and `rule semantics coverage rule revision 2 (2026-11-18)`.
- The five files `semantics/framework_namespaces_<component label>.txt` of revision 1 are not touched: kept plans name them
  by path and by sha256 (`input namespace-data` lines of their sidecars), and a regeneration of a kept plan reads them
  again.  `semantics_scan.py` keeps generating and checking them by the revision-1 rule, byte for byte.
- The name is chosen so that the present check does not list the new files before the scan is changed: it lists the
  files of `semantics/` by `^(framework_semantics|framework_namespaces|p0_declarations)_.*\.txt$`
  (research `env/tools/semantics_scan.py:1080`), which `framework_namespaces2_…` does not match.  After the change the
  check regenerates and compares both sets.
- No tool reads the new files until the kz-static build that adds their reader.  Which set a plan was made from is on
  its command line and in its sidecar (`input namespace-data` lines with sha256); a plan names one set only.
- The lint `case-ids-data` covers the new files as it covers every file of `semantics/`.

### 8.5 What the scan step reports (kept outputs, per component)

The `layer-fn` lines with their definition lines; kinds found, and of them those the revision-1 files did not have;
`kind-unresolved` and `not-covered` counts with the lines; the name-storing writers of the name field that lie in a
function of an entry over all such writers; the count of each new line kind; a diff of the entry lines of the
revision-1 file against the revision-2 file; and, as its last check, the regeneration of one kept plan with the present
tool on the untouched revision-1 files.

### 8.6 What revision 2 does not cover

Operations reached through an accessor function instead of a field path (section 7); the library calls inside the
name-initialising macro and the length checks (they are read from the facts at the positions these files give, by the
plan rules, `docs/plan_manifest.md` section 10); the documented return of a function declared void (the facts mark it,
`docs/static_facts.md` 5w; the scan does not); the platform support package and the applications.
